# コンパイルされた eval の制限

`eval` は 3 つのバックエンドすべてで動作します。インタプリタでは完全なツリーウォーク評価器そのものです。WASM コンパイラと JVM コンパイラは、フォームを実行時に実行する小さなツリーウォークインタプリタ（`_eval`/`_apply`/`_store` とヘルパー `_envLookup`/`_lookup`）を出力に埋め込みます。そのため、別個の評価器やパーサーは不要です。

コンパイルされた `eval`（WASM および JVM）は、レキシカル環境と永続的なグローバル環境を実装し、インタプリタとの一致を目指しています。自己評価アトム、変数参照、クロージャ、特殊フォームと高階関数（`let`、`lambda`、`cond`、`while`、`setq`、`setf`、`push`、`pop`、`funcall`、`apply`、`mapcar`、`mapc`、`reduce`、ネストした `eval` など）、組み込みマクロ、および任意の関数や解釈されたクロージャの適用はすべて、インタプリタと同じように動作します。すべてを列挙するのではなく、相違点を以下に挙げます。

## コンパイルされた `eval` の制限

コンパイルされた `eval`（WASM および JVM）がインタプリタと異なるのは、以下の場合だけです。

- **実行時に構築された `lambda` はラムダリストキーワードを解釈しません。** コンパイルされた `defun`/`lambda` フォームは `&optional`/`&rest`/`&key` をサポートし（コンパイル時に脱糖されます）、そのようなコンパイル済み可変長関数を `eval` から呼び出すことはできます。しかし eval されるフォームの中にのみ存在する lambda、例えば `(eval '(funcall (lambda (&rest r) r) 1 2))` はパラメータを位置的に束縛し — `&rest` は通常のパラメータ名として扱われます — 引数の個数も検査しません。ラムダリストキーワードを持たない実行時 lambda は、インタプリタと同様に引数の個数の誤りを `program-error` として通知します。プログラム自身のトップレベル定義が [`compile`](../reference/functions/compile.md) に渡す定義は事前にコンパイルされるため、この制限を受けません。
- **グローバル変数はコンパイルされたコードと `eval` で共有されます。** `setq`/`defvar`/`defparameter`/`defconstant` は、その値を実行時 `eval` のグローバル環境にミラーします。そのため、eval された式は、コンパイルされたプログラムが定義したグローバルを読むことができます（例: `(setq add10 (make-adder 10))` の後に `(eval '(funcall add10 100))` は `110` を返します）。eval された代入（`setq`、`setf`、`push`、`pop`）はコンパイルされた変数にも書き込むため、コンパイルされたコードからも見えます。スペシャル変数（プログラムの、または eval されたフォームの `defvar`/`defparameter`）は、コンパイルされたコードと同じく現在の動的束縛を通して読み書きされ、それを束縛する eval された `let` は動的に束縛します。そこから呼ばれた関数はその束縛を読みます。`(set ...)`（または `(setf (symbol-value ...) ...)`）も両方に書き込みます。ミラーされるのはグローバル変数だけです。トップレベルフォームの*レキシカル*変数 — `let`/`loop`/`do` の変数 — はミラーされません。これは `eval` が空のレキシカル環境で評価するという Common Lisp の規定に一致します（`(let ((x 5)) (eval 'x))` はどのバックエンドでもグローバルの `x` を読み、それが無ければ `unbound-variable` を通知します）。
- **`pprint-logical-block` はサポートされません。** それ以外の組み込みマクロと、`block`、`return-from`、`tagbody`、`go`、`catch`、`throw`、`unwind-protect`、`progv`、`flet`、`labels` は動作します。実行時展開の表がこれらを受け持ち、eval された `defvar` はその名前をスペシャルにします。`pprint-logical-block` は、関数が見つからない演算子と同じく、その名前の `undefined-function` を通知します。実行時 `load` が読むファイルの中の `in-package`、`defpackage`、`declaim` は処理されず、`nil` を返します。
- **eval されたフォームが定義したシンボルマクロは eval されたフォームにだけ存在し、プログラムのトップレベルの `define-symbol-macro` はコンパイルされたコードにだけ存在します。** eval された `define-symbol-macro` の名前は、以後の eval されたフォームから展開形を通して読み書きされます。プログラムのトップレベルのものは `defmacro` と同じくコンパイル時に消費されるので、eval されたフォームからは見えません。eval された `macrolet` の `&environment` パラメータは nil です。
- **`setf` の place として届くのは `car`、`cdr` とその合成、`first` から `tenth`、`rest`、`nth`、`gethash`、`aref`、`svref`、`row-major-aref`、`elt`、`char`、`schar`、`getf`、`get`、`slot-value`、`symbol-value`、およびプログラムが定義する `(setf name)` 関数を持つ place（`defclass` のアクセサを含む）です。** 構造体アクセサや eval された `defun` だけが定義する `(setf name)` 関数など、それ以外の place に代入する eval されたフォームは何も代入しません。
- **フォームから届く標準の関数、変数、マクロは、プログラムがそのフォームをどう作るかで決まります。** 関数は、出力にコンパイルされた関数のレジストリを通じて解決されます。ほとんどの関数は常に存在します。`typep`、`coerce`、`aref`、`format`、`error`、`sqrt` など、およびマクロの実行時展開は、それを名指しするプログラムにだけコンパイルされ、プログラムがデータとして綴ったフォームはそれらを名指ししたことになります。`(eval '(typep x 'integer))`、`(eval (list 'aref v 0))`、`(eval '(dolist (x l) (print x)))` は動作します。実行時に読む、または組み立てるフォーム（`(eval (read))`、`(eval (intern name))`、実行時 `load`）はどの名前でも指せるので、そのようなプログラムは標準の関数と変数をすべて持ち、その分だけ大きくなります。例外は、`--component` ではモジュールを非同期モードにする `sleep` と、ライブラリ定義の枝刈りをすべて止める `load` で、これらはプログラム自身が名指しする必要があります。
- **`defmacro` とバッククォートはコンパイル時のみです。** コンパイルパスでは、ユーザーマクロはコンパイラの実行前に完全展開され（定義も取り除かれ）、バッククォートのテンプレートはリーダーで展開されます。コンパイル済みプログラムの実行時 `eval`/`read` は `defmacro` もバッククォート文字も認識しません。 `macroexpand`/`macroexpand-1` も同様です: リテラルのクォートされた引数を持つ呼び出しはコンパイル時に展開結果へ畳み込まれ、実行時 `eval` ではこれらの関数はエラーを通知します（対照的に `gensym` はファーストクラスのラッパーを持つため動作します）。
- **`defstruct` はコンパイル時のみです。** トップレベルの `defstruct` はコンパイル前に生成関数へ展開されるため、コンストラクタ/アクセサ/述語を `eval` から呼び出すことはできますが、eval されるフォームの中で新しい構造体を定義したり、アクセサを `setf` の place として使うことはできません。`#S(...)` リテラルも同様にコンパイル前に解決されるため、`eval` の中では認識されません。
- **CLOS サブセットはコンパイル時のみです。** `defstruct` と同様に、トップレベルの `defclass`/`defgeneric`/`defmethod` はコンパイル前に展開されます。総称関数・reader/accessor・コンストラクタを `eval` から呼び出すことはできますが、eval されるフォームの中でクラスやメソッドを定義することはできません。
- **`rontolisp` パッケージの関数はサポートされません。** `rontolisp:version`、`rontolisp:fetch`、`rontolisp:http-handler`、`rontolisp:await`、`rontolisp:futurep`、`rontolisp:json-parse`、`rontolisp:json-stringify` は直接コンパイルされます（定数、インライン呼び出し、または組み込まれるライブラリ関数）。実行時 `eval`/`load` では `undefined-function` を通知します。

これらの相違は設計に由来します。実行時 `eval` は、実際に出力にコンパイルされた関数のコンパイル時レジストリに対して名前で演算子を解決し、組み込み関数はコンパイルされたコードと共有されます。
