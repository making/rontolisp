# CLAUDE.md

**Build Commands:**

```bash
./mvnw clean spring-javaformat:apply compile                    # Compile application
./mvnw clean spring-javaformat:apply package                    # Build executable JAR (-exec classifier)
./mvnw spring-javaformat:apply test                             # Run all tests
```

## Architecture Overview

Three execution modes share a common frontend (reader) and AST:

```
Source string
  -> LispReader (reader pkg) -> List<LispVal> (AST)
    -> [LispMacroExpander] -> expanded AST               # macro expansion (cond/and/or/setf -> if/let/progn/setq/rplaca/rplacd; defun is a special form, internally canonicalized to setq+lambda by the compilers)
    -> LispEvaluator (eval pkg)                          # interpret
    -> JvmLispCompiler (codegen.jvm) -> byte[] (.class)  # compile to JVM
    -> WasmLispCompiler (codegen.wasm) -> byte[] (.wasm) # compile to WASM
```

`am.ik.jvm` and `am.ik.wasm` are **language-independent** bytecode generation libraries ported from [bfc](https://github.com/making/bfc).

Package dependency direction (no cycles allowed):

```
cli -> eval, codegen.*
codegen.jvm -> compiler, am.ik.jvm
codegen.wasm -> compiler, am.ik.wasm
compiler -> rontolisp (AST types only)
eval, reader -> rontolisp (AST types only)
```

## Key Design Constraints

- **Lisp-2 (Common Lisp-style namespaces)**: Functions and variables live in separate namespaces in all three backends. A bare symbol is a variable reference only (interpreter: `The variable X is unbound`; compilers: `Cannot compile symbol ...`); a symbol in call position resolves in the function namespace only (a `let`-bound `car` never shadows the function `car`); a function value is obtained via `(function name)` / `#'name` (a `function` special form; lexer emits a `Token.FunctionQuote` for `#'`) or `symbol-function`. `funcall`/`map`/`reduce` accept symbols as function designators (interpreter: at runtime via `apply`; compilers: a literal `(quote name)` in function position is statically rewritten to `(function name)` by `compiler.FunctionDesignators.normalize`). `defun` defines into the function namespace and returns the function name symbol. **Per backend**: the interpreter keeps two maps in `Environment` (`lookup`/`define` for variables, `lookupFunction`/`defineFunction` for functions; all builtins are registered with `defineFunction`) and `LispEvaluator` handles `defun`/`function` natively (`SPECIAL_OPERATORS` lists the names that have no function value, so `#'if` errors). The compilers collect only real `(defun ...)` forms in Pass 1 (a top-level `(setq f (lambda ...))` binds a variable to a closure; call it with `funcall`); `Jvm/WasmFunctionFormCompiler` compiles `(function name)` to the closure that a bare function symbol used to compile to, synthesizes `(lambda (x) (cadr x))` for car/cdr compositions, and supports `symbol-function` only with a quoted literal. The eval runtimes keep a second global function namespace (`_fenv` field on JVM, `GLOBAL_FENV` wasm global) where the runtime `defun` installs bindings; `_eval`'s bare-symbol path no longer falls back to the function registry, operator resolution checks `_fenv` then the registry, a `function`/`symbol-function` special form resolves the namespace, and `_apply` coerces string symbols (designators) through it. The arity dispatch functions (`_invoke_N` / `FUNC_DISPATCH_BASE+N`) fall back to `_apply` for interpreted closures (`funcId == -1`) when the eval runtime is present, so a runtime-loaded function can flow through compiled `funcall`/`map`/`reduce`. `FreeVarAnalyzer` skips the operator position and `(function name)` designators (they are not variable references).
- **JVM Class Version 50 (Java 6)**: Avoids mandatory StackMapTable (required from version 51+).
- **WASM function types outside rec group**: wasmtime's WASI host requires plain `(func ...)` types for imports. Only the cons struct goes inside a rec group.
- **symbolp/stringp**: Quoted symbols and string literals share runtime representation. Distinguished by leading `"` character (`charAt(0) == '"'`).
- **consp in JVM**: Both cons cells and function references use `Object[]`. Distinguished by `arr[0] instanceof Integer`.
- **Three-pass compilation**: Pass 1 collects defuns. Pass 2a compiles defun bodies, 2b compiles top-level, 2c iteratively compiles lambda bodies. Top-level must compile before lambda iteration.
- **`do`/`return` and the `%block` non-local exit boundary**: `do` is a macro (`LispMacroExpander.expandDo`) that expands to a `let`/`while` loop with parallel-stepped variables (multiple stepped vars are assigned through temporaries to preserve parallel semantics). `do`/`dolist`/`dotimes` all wrap their expansion in the internal `%block` special form (`LispNames.BLOCK_INTERNAL`, a `CL_INTERNALS` symbol), which establishes the boundary that `return` (`LispNames.RETURN`, a `cl` special form) exits. `return` is a non-local exit to the **nearest** enclosing `%block` (so it leaves only the innermost loop and skips that loop's result form). Implemented per backend: interpreter throws `LispReturnSignal` (a stack-trace-free control-flow exception) caught by `evalBlock`; JVM stores the value into a dedicated local and `goto`s the block exit (`JvmBlockCompiler`/`JvmReturnCompiler`, tracked via `Ctx.blockTargets`) — storing-then-jumping keeps the operand stack empty at the merge point, which the version-50 inference verifier needs, and dead code after the `goto` is tolerated only because of that lenient verifier; WASM emits a `block (result (ref null eq))` and `return` does a `br` whose relative depth is `Ctx.wasmCtrlDepth - marker` (`WasmBlockCompiler`/`WasmReturnCompiler`), where `wasmCtrlDepth` is incremented only by the `if` (+1) and `while` (+2) compilers — the only inline forms that keep a WASM control structure open across a nested user subexpression. Consequence: `return` is supported where the surrounding operand stack is empty (an `if`/`when` branch or a loop-body statement), not mid-expression. `FreeVarAnalyzer` expands `do` like `dolist`. The early-exit scan macros `member`/`assoc` are themselves expanded through `do`/`return` (`expandMember`/`expandAssoc` build a `(do ...)` form and delegate to `expandDo`), using an `(atom cursor)` end-test so the `do`-to-`while` negation does not become a double negation. The runtime `_eval` interpreters do not know `do`/`return`/`%block` (README "Compiled `eval` limitations").
- **`%` prefix convention**: Internal helper functions that are not part of the public Lisp API use a `%` prefix (e.g., `%remf-tail`). These are implementation details used by macros and should not be called directly by users. They are registered in `Environment.java` and have dedicated compiler classes (`Jvm<Name>Compiler`, `Wasm<Name>Compiler`), but are not documented in the README.
- **Built-in function wrappers**: `BuiltinFunctionWrappers` (compiler pkg) generates synthetic `(setq name (lambda ...))` defuns for built-in operators. These are injected in Pass 1 of both compilers so that built-in operators like `+`, `car` can be used as first-class function values via `#'+`/`#'car` (passed to `map`, `reduce`, `funcall`). The wrapper body uses the operator in call position, where `compileCons` inlines it. User defuns with the same name take priority. The `(setq name (lambda ...))` shape is purely the wrappers' internal encoding consumed by `extractSetqLambda`; user-written top-level setq-lambda is NOT a function definition (Lisp-2).
- **JVM method name mangling**: The JVM spec forbids `/`, `<`, `>` in method names. `JvmLispCompiler.mangleMethodName()` maps these to `$div`, `$lt`, `$gt`, `$le`, `$ge`, and `:` (from package-qualified user symbols) to `$colon`.
- **Packages**: A small namespace system with three built-in packages: `cl` (standard functions/macros/special forms/variables), `cl-user` (default, empty, uses `cl`), and `rontolisp` (does not use `cl`; owns `version`, `list-functions`, `list-macros`, `list-special-forms`). The whole system is implemented as a single read/compile-time pass, `PackageResolver` (root `am.ik.rontolisp`), that runs before the evaluator (top-level entry of `LispEvaluator.eval`) and before both compilers (`JvmLispCompiler.compile`/`WasmLispCompiler.compile`). **Design decision**: resolving at the pass rather than at runtime keeps the evaluator, both compilers, `LispMacroExpander`, and the embedded read/load/eval runtimes untouched. The pass tracks the current package (driven by `in-package`), enforces the package discipline (an unqualified `cl` symbol in a package that does not use `cl` is the one hard error, `LispPackageException`), and rewrites every form into a canonical shape the existing backends already handle: `cl` symbols and `cl-user` user symbols become bare names, non-default-package symbols become `pkg:name` (so `rontolisp:version` is registered under that exact key in `Environment` and dispatched by `Jvm/WasmVersionCompiler`), `*package*` becomes a quoted current-package symbol, and `(in-package P)` is consumed. The introspection functions `rontolisp:list-functions`/`list-macros`/`list-special-forms` (optional package-designator argument, default `:cl`) are also normalized by the pass (designator literal validated and rewritten to a keyword), implemented at runtime in `Environment.registerPackages` (interpreter; `cl-user` lists the live global function namespace) and as compile-time constants by `Jvm/WasmIntrospectionCompiler` (`cl-user` is a snapshot of the Pass-1 user defun names exposed via `Ctx.userDefunNames`); shared listing/filtering logic lives in `PackageIntrospection` (root). The model is generic over `PackageRegistry`/`LispPackage`, so adding a package (or a future `defpackage`) is a registry change, not a resolver change. `cl`'s symbol set lives in `PackageRegistry.CL_SYMBOLS`, derived as the union of the categorized sets `CL_SPECIAL_FORMS`/`CL_MACROS`/`CL_FUNCTIONS`/`CL_VARIABLES`/`CL_INTERNALS` (single source of truth; `LispEvaluator.SPECIAL_OPERATORS` is `PackageRegistry.specialOperatorNames()`). Limitations are listed in the README "Packages" section. Tests: `PackageResolverTest`, and package cases in `LispEvaluatorTest`/`JvmLispCompilerTest`/`WasmLispCompilerIntegrationTest`.
- **`read`/`load` are supported in all three backends**: A runtime reader/parser is emitted into the compiled output (like `eval`). `read-line` (returns raw string) is also supported in all three modes.
  - *Interpreter*: `read` calls `LispReader.readFromString()`; `load` reads a file with `Files.readString` and evaluates each form in the global environment.
  - *JVM*: `JvmReadRuntimeBuilder` emits a recursive-descent reader (`_read`/`_readExpr`/`_readList`/`_readAtom`/`_readStr`/`_classify`, plus `_load`) into the generated `.class`, assembled with the shared `JvmAsm` label-based assembler. Because the JDK is on the classpath at runtime it has full parity (`Long.parseLong`, `new BigInteger`, `Double.parseDouble`, `java.nio.file`). `load` reads the file and evaluates every form via the `_eval` runtime, so it forces the eval runtime to be emitted. Gated by `programUsesSymbol(READ)`/`programUsesSymbol(LOAD)`.
  - *WASM*: `WasmReadRuntimeBuilder` emits `_intern`/`_read_expr`/`_read_list`/`_read`/`_load` (always present, stubbed when unused, to keep the fixed function indices stable). The reader walks linear-memory bytes between a cursor (`READ_CURSOR_ADDR`) and end (`READ_END_ADDR`). Symbols are interned via `_intern`, which scans a compile-time `(offset,length)` blob (so a runtime-parsed symbol resolves to the same offset the eval runtime compares against) and falls back to a growable runtime intern table (`RT_INTERN_BASE`) for symbols absent at compile time (e.g. a lambda parameter inside a loaded file) so repeated occurrences stay consistent. Integers are limited to `i31` (no float/big-integer parsing). `load` reads the file via the WASI `path_open` import (added as import index 2, shifting every defined-function index by one) relative to the first preopened directory (fd 3), so it must be run with `--dir`. Both `read` and `load` add a `defun` special form to the WASM/JVM `_eval` so loaded files can define functions.
- **File streams (`with-open-file`/`open`/`close`/`write-line`, stream-taking `read-line`) are supported in all three backends**: `with-open-file` is a plain macro (`LispMacroExpander.expandWithOpenFile`) that expands into `open`/`close` around a `let`, so no backend needed a new special form. A stream value is an opaque integer handle whose meaning is backend-local: the interpreter and JVM index a stream table (interpreter: a map captured in `Environment.registerIO`; JVM: a growable static `_streams` array emitted by `JvmIoRuntimeBuilder`), while WASM uses the WASI file descriptor itself (boxed i31), so `open`/`close`/`write-line` map directly onto `path_open`/`fd_close`/`fd_write` (`WasmIoRuntimeBuilder`; `fd_close` is always-imported at index 3, which shifted every defined-function index by one, like `path_open` before it). **Design decision**: the `:direction` option must be a literal `:input`/`:output` keyword so both compilers resolve the file mode at compile time (`Jvm/WasmOpenCompiler.staticMode`) and no runtime keyword handling is needed; consequently `open` has no `BuiltinFunctionWrappers` entry (`#'open` is unsupported in compiled code, like `load`). The WASM `open` resolves paths against the first preopened directory (fd 3), so output also requires `--dir` — which is why the ci-spec.yaml cases (run without `--dir` in CI) have no file I/O cases. In `--component` mode these same `path_open`/`fd_read`/`fd_write`/`fd_close` imports are satisfied by the adapter over `wasi:filesystem@0.3.0` (`read-via-stream`/`append-via-stream`, driven through `stream`/`future`; see the `--component` bullet), so file I/O works there too (also needs `--dir`). The runtime `_eval` interpreters do not know these forms (README "Compiled `eval` limitations").
- **`--dynamic` (late binding) for the JVM/WASM compilers**: Opt-in flag (CLI `--dynamic`; `JvmLispCompiler(className, dynamic)` / `WasmLispCompiler(dynamic)` constructors; threaded into both `Ctx` objects as a `dynamic` boolean). By default a call or variable reference that cannot be resolved statically throws `Cannot compile: <name>` (in `JvmFunctionCallCompiler.compileDirectCall` / `JvmExprCompiler.compileSymbolRef` and the WASM equivalents). When `dynamic` is set, those sites instead emit a runtime fallback via the embedded `eval`: a call `(f a b)` becomes `_apply(_eval('(function f), null), (list a b))` (operator resolved in the runtime function namespace), an unresolved `#'f` becomes `_eval('(function f), null)`, and a bare reference `x` becomes `_eval('x, null)` (variable namespace only). Arguments are compiled normally so enclosing compiled locals stay visible; only operator/variable resolution is deferred. Implemented by `Jvm/WasmDynamicCallCompiler` (build the quoted AST and recurse through the normal expr compiler, then `INVOKESTATIC _eval`/`_apply` (JVM) or `call FUNC_EVAL`/`FUNC_APPLY` (WASM)). Because the fallback needs the eval runtime, `dynamic` forces `usesEval = true` (same effect as a program using `eval`/`load`). Primary use case: compile an interpreter-tested source that defines functions via `load` without rewriting calls into `(eval ...)`. Tests: `*LispCompilerTest#dynamic*`.
- **`--component` (WASI 0.3 / Preview 3 output) for the WASM compiler**: Opt-in flag (CLI `--component`; `WasmLispCompiler(dynamic, component)` constructor; threaded as a `component` boolean). Default output stays a Preview 1 core module (no regression); when set, the output is a fully **Preview-3-native** WASI 0.3 **component** runnable with `wasmtime run -W gc=y -W component-model-async=y -W component-model-async-stackful=y -W component-model-more-async-builtins=y` (wasmtime 46+). The Preview 2 output was REPLACED, not kept in parallel -- no `--component-p3` flag, no backward-compat path (active development). **WASI 0.3 is fundamentally different**: the `wasi:io` package is GONE; all byte I/O flows through the built-in component-model `stream<u8>` / `future<T>` types and the async canonical ABI, and `wasi:cli/run@0.3.0` is an `async func`. **Design decision -- least-invasive "adapter" wrapping is PRESERVED via stackful async lift**: the rontolisp core module is emitted unchanged from Preview 1 (it still imports the eight `wasi_snapshot_preview1` functions, all `FUNC_*` indices stable, `WasmLispCompiler` I/O path untouched), and an adapter core module (`adapter.wat`) implements them over WASI 0.3 with the async canon built-ins. The component's `run` export is lifted as a **stackful** async export (an ordinary `canon lift` against an `async` function type -- `ComponentWriter.asyncFuncTypeResultType`; NO callback), so the synchronous `stream.write`/`stream.read`/`future.read` built-ins the adapter calls block COOPERATIVELY and the adapter stays straight-line code (no callback state machine, no `task.return`). The adapter: `fd_write` does stdout via `wasi:cli/stdout.write-via-stream(stream<u8>) -> future` and files via `wasi:filesystem.append-via-stream` (each call is a full `stream.new` -> push iovecs -> `stream.drop-writable` (EOF) -> `future.read` await cycle, so no per-fd write offset is tracked); `fd_read` does stdin via `wasi:cli/stdin.read-via-stream() -> (stream, future)` and files via `wasi:filesystem.read-via-stream(offset) -> (stream, future)` (caches the readable stream per fd, advancing it; `stream.read` writes straight into the shared-memory destination; the read future is dropped immediately, EOF = stream status, not the future); `random_get`/`clock_time_get`/`environ_*` bridge `wasi:random`/`wasi:clocks` (`system-clock`, renamed from 0.2's `wall-clock`; `monotonic-clock`)/`wasi:cli/environment`. A preview1 file fd is `100 + slotIndex`; adapter scratch + fd table live in page 5. **error-code nominality gotcha**: `wasi:cli` and `wasi:filesystem` expose DISTINCT `error-code` enums, so their `future<result<_, error-code>>` are distinct types needing separate built-ins (`future-read-cli`/`future-drop-cli` vs `future-read-fs`/`future-drop-fs`); `stream<u8>` is structural and shared. The filesystem `error-code` is a VARIANT with a string-bearing `other` case, so `future-read-fs` needs the realloc canon option (`ComponentWriter.canonFutureRead(ty, mem, realloc)`); the cli error-code is a plain enum (memory only). The only core-module changes in component mode (in `WasmLispCompiler.compile`): import the linear memory instead of defining it, and `_start` becomes `()->i32` returning `0`, exported as `run`. **Shared canonical-memory module** (avoids the instantiate-before-memory cycle / lazy funcref trampoline): a tiny `mem.wat` (6 pages) exporting `memory` + bump `cabi_realloc` is instantiated first; the canonical lowering, the stream/future built-ins and both main modules use it. The component assembly lives in `WasmComponentBuilder` (codegen.wasm), using `am.ik.wasm.ComponentWriter` (the language-independent component-model encoder; its async-canon-ABI primitives -- `definedStream`/`definedFuture`/`definedResultErr`/`asyncFuncTypeResultType` + `canon stream.*`/`future.*` built-ins -- are GENERAL and intended for reuse by a future language-level async, not tied to the adapter). Three fixed byte blobs are loaded from classpath resources under `.../codegen/wasm/component/`: `import-block.bin` (the unified component type+import section for the 9 imported WASI 0.3 interfaces: import instances 0 `wasi:cli/types`, 1 `cli/stdout`, 2 `cli/stdin`, 3 `cli/environment`, 4 `clocks/system-clock`, 5 `clocks/monotonic-clock`, 6 `filesystem/types`, 7 `filesystem/preopens`, 8 `random/random`; defines component types 0-11, so the next free type index is 12) and the helper core modules `mem.wasm` / `adapter.wasm`. `WasmComponentBuilder.build` does all remaining wiring programmatically (alias the cli/fs error-code + descriptor types and the 10 WASI funcs, define stream/future/result types as component types 12-21, lower the WASI funcs + emit the stream/future canon built-ins as core funcs 1-20, group them as the adapter's `"w"` import, instantiate mem/adapter/rontolisp, lift `run` async, export `wasi:cli/run@0.3.0`); the indices and per-function canon options were read off `wasm-tools dump` of a generated reference. Each artifact was validated with `wasm-tools validate -f component-model -f cm-async -f cm-async-stackful -f cm-more-async-builtins` and run with `wasmtime run`. The `.bin`/`.wasm` resources are registered for native image in `resource-config.json` (wildcard patterns). **These blobs are generated** -- sources live OUTSIDE the resources tree under `src/wasm-component/`: `mem.wat`/`adapter.wat` (core-module sources), `uni.wit` (imports-only world; the async `run` export is wired by the builder, not expressible through `wasm-tools component new`) + vendored `deps/` (official WASI 0.3.0 WIT) + stub `core.wat`, and `regen.sh`. To change them, edit the sources, run `src/wasm-component/regen.sh`, re-derive the wiring constants from `wasm-tools dump`, and re-test. `src/wasm-component/README.md` has the procedure. Component encoders are pinned by golden-byte tests in `ComponentWriterTest`; end-to-end component runs are covered by `WasmLispCompilerIntegrationTest` (Docker, fresh wasmtime). README "Compile to a WASI 0.3 component" lists the limitations. **Real WASI 0.3 services**: `random`/clocks/getenv are 0.3-native (a preview1-style `random_get` is imported in BOTH modes to keep static function-import indices identical; `WasmRandomCompiler` branches on `Ctx.component`). The defined-function index constants in `WasmLispCompiler` are written relative to `IMPORT_FUNC_COUNT`. **NOT YET PORTED**: `rontolisp:fetch` -- `WasmComponentBuilder.build` throws `UnsupportedOperationException` for `usesHttp`; the async `wasi:http@0.3.0` port is pending. The P2 http blob sources (`uni-http.wit`/`adapter-http.wat`/...) and generated resources were removed.
- **`get-universal-time` / `get-internal-real-time` / `get-internal-run-time` / `getenv`**: time and environment built-ins. Time is implemented in all three backends: interpreter (`Environment`, `System.currentTimeMillis`/`nanoTime`) and JVM (`JvmTimeCompiler`, via a `systemOps` methodref map on `Ctx` mirroring `mathOps`) return an **integer**; WASM (`WasmTimeCompiler`) reads WASI `clock_time_get` (a preview1-style import bound to the real host clock in Preview 1 and to `wasi:clocks@0.3.0` system/monotonic through the adapter in component mode) and returns a **float** (`float_struct`), because the magnitudes exceed the 31-bit `i31` integer range -- an `f64` holds them exactly, and the value is meant for comparisons/differences (printing the raw large float traps in rontolisp's existing float printer, which truncates to i32). `getenv` is implemented in all three backends: interpreter/JVM (`JvmGetenvCompiler`), and WASM via a `_getenv` runtime helper (`WasmGetenvRuntimeBuilder`, a new always-present defined function) that scans the WASI environ buffer (`environ_sizes_get`/`environ_get`, bound to the real host in Preview 1 and to `wasi:cli/environment`'s `get-environment` list -- decoded into a preview1-style environ buffer by the adapter, `wasi:cli/environment@0.3.0` -- in component mode) and returns a quoted heap string. The component mem module is 4 pages (the canonical realloc heap is page 1+, the environ scratch buffer page 3) and its `cabi_realloc` aligns the result; the rontolisp module is correspondingly 4 pages in both modes. Registered in `LispNames`/`PackageRegistry.CL_FUNCTIONS` (so `list-functions` includes them; introspection counts moved 158 -> 162). `get-universal-time` is seconds since the 1900-01-01 Common Lisp epoch (Unix epoch + 2208988800). The WASM `clock_time_get`/`environ_sizes_get`/`environ_get` imports are added in both modes (Preview 1 binds the real host functions; component mode binds the adapter's `wasi:clocks@0.3.0`/stub implementations), keeping the static function-import indices identical across modes.
- **`rontolisp:fetch` (outgoing HTTP, JavaScript `fetch`-style)**: a `rontolisp`-package function (not CL standard). `(fetch url [options-plist])` where options accepts `:method` (default `"GET"`; one of GET/HEAD/POST/PUT/DELETE/OPTIONS/PATCH, matched case-insensitively and sent canonicalized to upper case), `:headers` (an alist of `(name . value)` string pairs) and `:body` (a request body string, e.g. for POST/PUT), returning the plist `(:status N :body "..." :headers alist)`. Implemented in all three backends. Interpreter (`eval/HttpSupport.java`) and JVM (`JvmFetchRuntimeBuilder` emits a self-contained `_fetch` method into the generated class; needed adding `ConstantPool.addInterfaceMethodref` + `INVOKEINTERFACE` for `HttpClient`/`HttpResponse`/`Map` interfaces) both use the JDK `java.net.http.HttpClient`. **WASM is component-only** (`WasmFetchCompiler` throws in Preview 1 mode; the whole point is there is no host `wasi:http` for a core module). **Design decision -- separate http blob variant so non-fetch components do not require `-S http=y`**: a component that merely *imports* `wasi:http` fails to instantiate without `wasmtime run -S http=y`, so the base `import-block.bin`/`mem.wasm`/`adapter.wasm` are kept unchanged and a parallel `import-block-http.bin`/`mem-http.wasm`/`adapter-http.wasm` set (sources `uni-http.wit` world `uni-http`, `core-http.wat`, `mem-http.wat` 16 pages, `adapter-http.wat`; same `regen.sh`, `deps/http` vendored WASI 0.2.0) adds `wasi:io/poll` + `wasi:http/types` + `wasi:http/outgoing-handler`; `WasmComponentBuilder.build(core, usesHttp)` picks the variant, and `WasmLispCompiler` emits the variant only when the program uses fetch. The whole outgoing-request state machine (parse URL, build outgoing-request with the method discriminant, append request headers, obtain the `outgoing-body` and stream the request body in <=4096-byte chunks via `outgoing-body.write`+`blocking-write-and-flush`+`outgoing-body.finish` when one is given, `outgoing-handler.handle`, `pollable.block`, `future.get`, read status/headers/body, drop resources) lives in `adapter-http.wat` exporting one `http.fetch` import (12 i32 params -- `method` discriminant, url ptr/len, request-body ptr/len read straight from the shared memory, request-header buffer ptr/len, and the status/header/body out-pointers); the rontolisp core serializes request headers to a page-4 buffer, calls the import, and rebuilds the result plist via four runtime helpers (`WasmFetchRuntimeBuilder`: `_fetch_str`, `_fetch_plist_get`, `_fetch_ser_headers`, `_fetch_deser_headers`). The `:method` is resolved statically by `WasmFetchCompiler.methodDiscriminant` (a literal maps to the WASI http method variant discriminant; an unsupported literal is a compile error; a runtime-computed method falls back to GET), while the `:body` value is read out of the options plist at runtime. Adding the four `outgoing-body` WASI functions (`outgoing-request.body`, `outgoing-body.write`/`finish`, `[resource-drop]outgoing-body`) meant regenerating `import-block-http.bin` (they are pruned out of the imported instance type unless `core-http.wat` declares them) and re-deriving the `WasmComponentBuilder.buildHttp` wiring constants from `wasm-tools dump`. **Index-stability trick**: adding the `http.fetch` import would shift every defined-function index, so function index `FUNC_FETCH` (= the old `IMPORT_FUNC_COUNT`, 8) is reserved in BOTH modes -- the import in component+fetch mode, an unused trap stub otherwise -- and `FUNC_START` bumped to 9 uniformly, so the 57 static `FUNC_*` constants stay valid across modes (calling `pollable.block` also forces `wasi:io/poll` to component instance 1, shifting every other component instance index by one in the http variant -- handled in `buildHttp`). **Canonical-ABI gotcha**: `error-code` is 8-byte aligned (it has a u64-bearing case), so in `handle`'s `result<future, error-code>` the future handle is at offset 8 (not 4), and `future.get`'s `option<result<result<incoming-response, error-code>>>` nests the discriminants/handle at offsets 0/8/16/24. A failed request (e.g. a refused connection) is detected via the inner result discriminant and returns nil, never a trap. A statically-known unsupported `:method` (a literal `(list :method "X" ...)`/`(quote (:method "X" ...))`) is rejected at compile time; a runtime-computed method is treated as GET. Tests: interpreter/JVM unit tests use a local `HttpServer`; `WasmLispCompilerIntegrationTest` has a deterministic Docker error-path test and `-S http` gate test, plus an opt-in (`RONTOLISP_HTTP_E2E=1`) local-wasmtime success test. README "HTTP requests" lists the limitations. **Browser playground**: `java.net.http` cannot be compiled by GraalVM Web Image (TLS/sockets), so a web-profile substitution (`src/web/java/.../eval/Target_HttpSupport.java`) routes the interpreter`'s fetch to a synchronous `XMLHttpRequest` (`web/BrowserHttp.java`, `@JS`); sync XHR is used because the interpreter call is synchronous and a WASM guest cannot await a Promise without JSPI. So fetch works in the playground subject to CORS. Verified end-to-end in Chrome 149.
- **`eval` is supported in all three backends** (interpreter, WASM, JVM):
  - *Interpreter*: registered as a `LispFunction` in `LispEvaluator`'s constructor (not in `Environment.createGlobal()`) to avoid a circular dependency. Evaluates the argument in the global environment.
  - *WASM*: a runtime tree-walking interpreter with lexical + global environments, emitted into the module by `WasmEvalRuntimeBuilder` (split out of `WasmRuntimeBuilder`) and invoked by `WasmEvalCompiler`. It comprises five functions -- `_lookup` (registry name-offset -> record address), `_env_lookup` (offset + env -> binding cons or null), `_eval` (`(form, env) -> value`), `_apply` (`(fn, argList) -> value`), and `_store` (`(place, value, env) -> value`) -- plus a WASM global (`GLOBAL_ENV`, a mutable `(ref null eq)`) holding the persistent top-level environment. They appear only when the program actually calls `eval` (`WasmLispCompiler.programUsesEval`); otherwise trivial stubs keep the fixed function indices stable (the global is always present but unused). Dispatch is enabled for every registered arity when eval is used. Three key tricks: (1) because the `StringTable` deduplicates strings, a quoted symbol (e.g. `'car`) and a `let`/`lambda`/`setq` name compile to the same data offset, so both variable lookup and operator resolution are plain `i32` offset comparisons rather than byte-wise string compares; a compile-time registry blob (records of `nameOffset, funcId, arity`) is appended after the string data and scanned by `_lookup`. (2) An environment is an association list of `cons(name, value)` bindings (empty = `ref.null eq`); lexical lookup misses fall through to `GLOBAL_ENV`, and `setq` mutates an existing binding's (mutable) cdr or prepends a new binding to `GLOBAL_ENV`, so definitions persist across `eval` calls. (3) Interpreted closures created by `lambda` reuse the compiled closure struct `{i32 funcId, (ref null eq) env}` with the sentinel `funcId == -1` and `env = cons(lambdaTail, capturedEnv)`, while compiled functions are applied via the arity dispatch functions; `_apply` handles both, so `funcall`/`map`/`reduce` (implemented inside `_eval` using `_apply`) work with interpreted closures too. Registry-resolved calls evaluate exactly the registered arity (extra args ignored, matching the compiler's binary comparison operators) to avoid dispatch traps. `_store` (type `TYPE_CALLABLE_BASE+2`) is the shared assignment primitive: for a symbol place it mutates the lexical/global binding (or creates a global one), and for an accessor place it mutates the resolved cons (`(car x)`/`c[ad]+r` set car/cdr, `(cdr x)` sets cdr, `(nth n x)`/`(second/third/fourth x)` walk then set car). `setq`, `setf`, `push` and `pop` all delegate to `_store`. `_eval` supports self-evaluating atoms, lexical/global variable references, `quote`/`if`/`progn`/`let`/`lambda`/`cond`/`and`/`or`/`when`/`unless`/`while`/`dotimes`/`setq`/`setf`/`push`/`pop`/`eval` (nested)/`funcall`/`map`/`reduce`/`list`, variadic `+ - * /`, `car`/`cdr` compositions (`cadr`, ... matched by the `c[ad]+r` name pattern), the numbered accessors `first`/`second`/`third`/`fourth`/`nth`, and application of any registered function or interpreted closure. `while` and `dotimes` loop natively inside `_eval` (the `dotimes` loop variable is held in a mutable binding cell that is reused each iteration). Remaining differences from the interpreter (binary comparison operators, >7-param functions, zero-arg arithmetic traps) are listed in the README "Compiled `eval` limitations".
  - *JVM*: a runtime tree-walking interpreter emitted into the generated `.class` by `JvmEvalRuntimeBuilder` and invoked by `JvmEvalCompiler`, mirroring the WASM design with five `private static` methods -- `_lookup` (`(Object name) -> Object[]{Integer funcId, Integer arity}` or null), `_envLookup` (`(Object name, Object env) -> binding cons or null`), `_eval` (`(Object form, Object env) -> Object`), `_apply` (`(Object fn, Object argList) -> Object`), and `_store` (`(Object place, Object value, Object env) -> Object`) -- plus a mutable `private static Object _genv` field holding the persistent top-level environment. They are emitted only when the program actually calls `eval` (`JvmLispCompiler.programUsesEval`); unlike WASM, **no stubs are needed** because JVM methods are referenced by name+descriptor, not by fixed index. When eval is used, dispatch methods for every arity `0..MAX_CALLABLE_ARITY` (7) are force-generated so `_apply` can dispatch by argument count. Runtime value representation is shared with the compiled output: `null`=nil, `Long`=integer, `Double`=float, `String`=symbol (or string literal when it starts with `"`), `Object[2]`=cons, and `Object[]` whose first element is an `Integer`=function value (`{Integer funcId, captures...}`); interpreted closures created by `lambda` use the sentinel `Object[]{Integer(-1), lambdaTail, capturedEnv}` where `lambdaTail = ((params) body...)`. JVM differs from WASM in two simplifications enabled by the JVM object model: operator/variable/special-form resolution uses `String.equals` and `instanceof` directly (no string-offset registry blob -- `_lookup` is an `if`-chain over the compiled functions), so quoted symbols and binding names need not share an interned offset. Bytecode is assembled by a small label-based `Asm` helper (JVM has no structured control flow, so branches are back-patched). A key constraint: the generated class uses **version 50** and relies on HotSpot's failover to the type-inference verifier (no `StackMapTable`); that verifier is flow-insensitive about `instanceof`, so (a) `String`/array methods on values held in `Object` slots must be preceded by an explicit `checkcast` (`aloadStr`/`idx`/`arrLen` helpers), and (b) a slot read after a conditional guard must be definitely assigned on every path (e.g. `_store` initializes `TARGET` to null up front). Supported forms and the limitations (binary comparison operators, >7-param functions, zero-arg arithmetic edge cases, `let` binding-list shape) are identical to WASM and listed in the README "Compiled `eval` limitations".

## Development Workflows

### Implementation Order

When adding a new built-in function or special form:

1. **Interpreter** (`LispEvaluator` / `Environment`) -> run `LispEvaluatorTest`
2. **JVM compiler** -> run `JvmLispCompilerTest`
3. **WASM compiler** -> run `WasmLispCompilerIntegrationTest`
4. Add a case to `src/test/resources/ci-spec.yaml` if the feature should be covered end-to-end (see `CiSpecE2eTest`)
5. Update Built-in Functions / Compiler Limitations in README and `ReadmeExamplesTest`

### Adding a New Built-in Function

1. **LispNames.java / PackageRegistry.java**: Add the name constant in `LispNames`, and add it to `PackageRegistry.CL_SYMBOLS` so the package resolver treats it as a `cl` symbol (otherwise it is misclassified as a user symbol and unqualified use in the `rontolisp` package would not be rejected).
2. **Environment.java**: Add in `createGlobal()` using `env.define("name", new LispFunction(...))`.
3. **JVM compiler**: Create `Jvm<Name>Compiler.java`, add case in `JvmExprCompiler.compileCons()`.
4. **WASM compiler**: Create `Wasm<Name>Compiler.java`, add case in `WasmExprCompiler.compileCons()`. Use `WasmEmitHelper.castI31GetS()` to unbox to `i32` and `ref.i31` to re-box.
5. **BuiltinFunctionWrappers.java**: Add a wrapper entry in `WRAPPER_DEFS` with the appropriate arity and body AST so the function can be used as a first-class value.

### Adding a New Macro

Macros expand into existing primitives (`if`, `let`, `progn`, `rplaca`, `rplacd`) at the AST level. `LispMacroExpander` (in `am.ik.rontolisp` package) is shared by the evaluator and both compilers.

1. **LispMacroExpander.java**: Add a `public static LispVal expand<Name>(LispCons cons)` method that returns the expanded AST. Also add the macro name to `LispNames` and `PackageRegistry.CL_SYMBOLS` (it is a `cl` symbol).
2. **LispEvaluator.java**: Add case in `evalCons()` switch: `return eval(LispMacroExpander.expand<Name>(cons), env);`
3. **JvmExprCompiler.java**: Add case: `JvmExprCompiler.compileExpr(LispMacroExpander.expand<Name>(cons), ctx, className);`
4. **WasmExprCompiler.java**: Add case: `WasmExprCompiler.compileExpr(LispMacroExpander.expand<Name>(cons), ctx);`

No per-compiler class is needed since macros reuse existing compilation paths.

5. **First-class value support** (required if the macro should be passable to `map`/`reduce`/`funcall`):
   - **Environment.java**: Register as `LispFunction` so the interpreter can resolve it in value position.
   - **BuiltinFunctionWrappers.java**: Add a wrapper entry using the expanded body form (e.g., `(+ a 1)` for `1+`) so the compilers can resolve it in value position.
   - Both registrations are needed: `Environment` for the interpreter, `BuiltinFunctionWrappers` for JVM/WASM compilers. Omitting `Environment` causes `Undefined symbol` errors in interpreter/native-image mode.

### Adding a New Special Form

1. **LispEvaluator.java**: Add case in `evalCons()` switch. Special forms receive unevaluated arguments.
2. **JVM compiler**: Create `Jvm<Form>Compiler.java`, wire in `JvmExprCompiler.compileCons()`.
3. **WASM compiler**: Create `Wasm<Form>Compiler.java`, wire in `WasmExprCompiler.compileCons()`.

### Verifying WASM Output Manually

```bash
echo '(print (+ 1 2))' > test.lisp
java -jar target/rontolisp-0.1.0-SNAPSHOT-exec.jar test.lisp -o test.wasm
wasmtime --wasm gc test.wasm    # requires wasmtime 14+
```

### Verifying the Native Image End-to-End (run locally before every push)

`./mvnw test` (JVM) **skips `CiSpecE2eTest`** because `-Drontolisp.binary` is
unset, so a stale `ci-spec.yaml` expectation passes the JVM run and only the
CI `native-image` job catches it. To avoid that round trip, reproduce the CI
job locally and run it yourself before pushing — always after editing
`ci-spec.yaml`, and after any change that can shift cross-backend output (a new
built-in/macro/special form, anything touching introspection like
`list-functions`/`list-macros`/`list-special-forms`, or a runtime behavior
change). Requires GraalVM `native-image` and `wasmtime` on `PATH` (build ~30s):

```bash
# 1. Build the native binary (same as the CI native-image job)
./mvnw -V --no-transfer-progress -Pnative clean package -DskipTests

# 2. Run the cross-backend E2E driver against the native binary
#    (interpreter / JVM / WASM in one run; names the exact failing case)
./mvnw -V --no-transfer-progress \
  -Dtest=CiSpecE2eTest -DfailIfNoTests=false \
  -Drontolisp.binary="$PWD/target/rontolisp" \
  test
```

A failure prints `[case '<name>' on <BACKEND>` with the offending lines; fix
the `ci-spec.yaml` `expected` (or the backend) and re-run step 2 only (the
binary does not need rebuilding unless Java sources changed).

## Development Requirements

- Java 25+
- No external dependencies for core libraries (reader, eval, codegen, am.ik.jvm, am.ik.wasm)
- Spring Java Format enforced via Maven plugin
- Use modern Java features (Records, Pattern Matching, Sealed Types, Text Blocks, etc.)
- Avoid circular references between classes and packages
- `src/test/resources/ci-spec.yaml` is the single source of truth for the cross-backend end-to-end test (`CiSpecE2eTest`, package `am.ik.rontolisp.e2e`). Each case is `name` + `source` (Lisp) + `expected` (exact output lines, with an optional `expectedByBackend` override). The cases share global state and run IN ORDER, so the driver concatenates them into one program, runs the native binary once per backend (interpreter / JVM / WASM Preview 1 / WASM as a WASI 0.3 component via `--component` + `wasmtime run -W gc=y -W component-model-async=y -W component-model-async-stackful=y -W component-model-more-async-builtins=y`), and slices the output back per case — a failure names the exact case, not just a line number. The `WASM_COMPONENT` backend reuses each case's `expected` (or its `wasm` `expectedByBackend` override) because the ci-spec program is deterministic and does no file I/O / random / time, so component output matches Preview 1. Add a case here when adding a feature; there is no separate expected file to keep in sync. The driver only runs when `-Drontolisp.binary=<path>` is set (so `mvn test` on the JVM skips it); CI's `native-image` job runs it after building the binary.
- README code examples verified by `ReadmeExamplesTest`
- WASM integration tests skipped if Docker unavailable
