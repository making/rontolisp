# Reader features (`#+`/`#-`, `*features*`, block comments, `#.`)

The `.todo/054` Phase-2 read-layer additions, implemented almost entirely in the frontend (`reader` package) — no per-backend codegen. The one thing that is NOT frontend-only is the run-time `*features*` variable (todo-181, below): the reader decides its initial value, the backends hold it. The **runtime** readers emitted into compiled output (`JvmReadRuntimeBuilder` / the WASM runtime reader) do NOT know any of this, like backquote (documented in `read-load-limitations.md`).

**`Features` (reader pkg)**: the active feature set. Constants `INTERPRETER`/`JVM`/`WASM` = `rontolisp` + one backend feature (`rontolisp-interpreter`/`rontolisp-jvm`/`rontolisp-wasm`) + `unicode`; `of(...)` for tests (no implicit `unicode` — a test asks for exactly what it lists). **`unicode` (2026-07-27)** is the portable spelling (CLISP/ECL/CMUCL/LispWorks; SBCL says `sb-unicode`) of "this implementation's characters are code points, not octets", which is true of every backend — see `.kb/characters-code-points.md`. It is a CLAIM LIBRARIES ACT ON, not decoration: cl-postgres' `#+(or sb-unicode unicode ics openmcl-unicode-strings abcl)` header picks `strings-utf-8` vs `strings-ascii`, and the ascii branch announces `client_encoding SQL_ASCII` and then writes one octet per code point, so `(exec-prepared ... (list "お茶"))` sent `0x00`-bearing garbage the server rejected AND left the connection desynced. The feature was absent until a Japanese string went through the driver; the hand-authored `cl-postgres-deps.asd` had the ascii file pinned WITH the missing feature as its stated reason, which is the shape to watch for — a workaround whose comment records the root cause instead of fixing it. Adding it was safe because it is the only `#+unicode` site in the loadable corpus (uiop's is gated behind other implementations, uax-15's is `#+utf-16`); re-check that when a new library lands. `contains()` is case-insensitive and strips `:`/`#:`; `isEnabled(LispVal)` evaluates a feature expression (`and`/`or`/`not`, bare or keyword spelling; `LispNil` = false, preserving the `#+nil` comment idiom). Deliberately NO `:common-lisp` (do not lie). A `Features` is the READ-time set and is immutable for the duration of a read; the run-time `*features*` list is a separate, ordinary special seeded from it (see below) — `(setq *features* ...)` moves that list and nothing about how the source was read.

**The FOURTH target-shape feature (todo-530)** is `Features.JVM_SERVLET`'s
`rontolisp-servlet`, selected when `-o` ends in `.war`: the JVM set widened with the
fact that a servlet container owns the port, so the `rontolisp:http-handler` directive
registers its handler and returns (`.kb/http-server.md`, "The fifth transport"). It is a
feature and not an internal compiler flag for the reactor's reason exactly — the
`clack-handler-rontolisp` shim branches on features and on nothing else (`.kb/clack.md`,
`.todo/532`).

**The three TARGET-SHAPE features beside the backend one**: `WASM_REACTOR` adds `rontolisp-reactor` (`--no-wasi` or `--no-gc`: the module owns no WASI world and its entry points are exports a host calls — `.kb/clack.md`), and `--component` widens whichever WASM set is in force with `Features.COMPONENT` = `rontolisp-component` (todo-341 Phase 2b). The second is NOT redundant with the first: a `--component --no-wasi` build is a reactor and carries BOTH, while what a source usually needs to branch on is the BOUNDARY — `rontolisp:wasm-import` and the `:bytes` type are core-module-only, so a program declaring one writes `#-rontolisp-component` to stay compilable both ways (`examples/cloudflare-workers/httpbin/worker.lisp`, built as a core module by `httpbin/` and as a component by `httpbin-component/`). Added in `RontoLispCli` beside the reactor choice, so it reaches every frontend read (shims and `.asd` component files included) exactly like the rest of the set. Pinned by `RontoLispCliTest.aComponentBuildReadsTheSourceWithTheComponentFeature`.

The THIRD (todo-351) is `Features.BODY_IMPORTS` = `rontolisp-body-imports`, added when a build really declares the reactor's `:bytes` body imports: a `--no-wasi` wasm-GC core module on the streaming boundary (`--host-boundary=streaming`, the default). It is the first target-shape feature that follows a FLAG rather than the output shape alone, and that is the reason it exists at all -- it REPLACED `#+(and rontolisp-reactor (not rontolisp-component))` in `examples/cloudflare-workers/httpbin/worker.lisp`, a guard that enumerated two of the targets that cannot carry the imports instead of naming the imports. That spelling silently included `--no-gc` (a reactor with no packed-array representation for `:bytes` at all) and could not have expressed "the flag turned them off" in any combination of target features. **The rule it illustrates**: name the thing the source is branching on, not the targets that happen to lack it -- a feature is additive (`with` cannot switch one off), so the complement has to be spellable as `#-NAME`, and it only reads correctly when NAME is the fact. Pinned by `RontoLispCliTest.theStreamingBoundaryReadsTheSourceWithTheBodyImportsFeature` -- ONE source with a `#+rontolisp-body-imports` declaration and a `#-` fallback, compiled three ways, the declaration surviving only in the streaming build. Note what that has to assert: the FEATURE is invisible to Java (nothing reads it back), so the only thing that can pin it is a source that branches on it, exactly as `aComponentBuildReadsTheSourceWithTheComponentFeature` does for `#-rontolisp-component`. `theEnvelopeBoundaryBuildsAModuleWithNoBodyImports` beside it pins the MODULE's imports, which is a different claim.

**Per-system widening (`Features.with`, `.todo/204`)**: an ASDF system may DECLARE features with the `:rontolisp-features (...)` defsystem option — the static encoding of a `.asd` that pushes onto `*features*` from an `eval-when`, which cannot reach the reads of the system's COMPONENT FILES on its own (a push is only ever read back inside the file that writes it, see `FeaturePushes` below). Each loader widens ITS OWN base set with the declaration (`Features.with`, additive only: nothing may switch a backend feature off and claim to be that backend) and reads that system's own component files with the result; a dependency keeps the outer set. Mechanics and the two pinning tests: `.kb/asdf.md`. Since `.todo/236` the `.asd`'s OWN `(eval-when ... (pushnew :F *features*))` is read into the same place (`AsdfSystems.collectFeaturePushes`) — the announcement idiom fast-io opens with — so an upstream file and a bundled replacement widen identically. **It is a CROSS-FILE mechanism, and that is what it is for**: the push in a `.asd` reaches a `#+` in that same `.asd` for free now (`FeaturePushes`), so what this adds is carrying the declaration OUT of the `.asd` — to the system's `:if-feature`/`(:feature ...)` clauses and its component reads, and nothing else. The same widening reaches the SHIM sources: `ShimLibraries.forms` takes the target backend's features instead of hardcoding INTERPRETER, so `bordeaux-threads`' `#+rontolisp-wasm nil` `*supports-threads-p*` is true per backend (`.kb/mutexes.md`).

**Threading**: `LispReader.readAllFromString(input, features)` (1-arg overload = INTERPRETER). Reading happens once at the frontend, so the set a compiled program's `#+` conditionals were resolved against is fixed at compile time (the run-time `*features*` list starts there and the program may move it): `RontoLispCli.compileToFile` picks `WASM` iff the output file ends `.wasm` (incl. `--no-gc`/`--component`), else `JVM`; interpret/REPL use the default. `LoadInliner.Ctx` carries the features so loaded/spliced files read with the target set (5-arg `inline` overload; short overloads default INTERPRETER); the playground (`src/web/java`, `-Pweb`!) passes JVM/WASM per compile entry point. `Environment`'s runtime `read`/`read-from-string` and `LispEvaluator.loadFile` use the 1-arg default (correct: interpreter).

**`#P"..."` (pathname literal)**: the lexer emits `Token.PathnameOpen` and `LispReader` builds the pathname VALUE directly — a `LispInstance` over the fixed `LispLayout.PATHNAME` (todo-304, `.kb/pathnames.md`); no registry is needed because the layout is a constant, and the instance is self-evaluating like a folded `#S(...)`. Only `#P` immediately followed by a `"` is the dispatch; anything else still reads as a symbol (`#PFOO`), preserving the pre-`#P` tokenization, and the `#+`-skip's generic tail skips a string directly following a `#`-prefix so a guarded `#P"..."` disappears whole. Seeded by quri's `etld.lisp`, whose `#.(asdf:system-relative-pathname :quri #P"data/effective_tld_names.dat")` needs it inside a read-time-eval datum. Pinned by `LispReaderTest`.

**Lexer (`LispLexer`)**: new `#`-dispatch cases before the `#\`/`#(`/radix cases — `#|...|#` (nesting, `skipBlockComment`), `#+`/`#-` (`readFeatureConditional`), `#.` (error, or tolerant skip). The feature expression is parsed by a mini reader over symbols/lists only (`readFeatureExpr`). A **failing** guard skips the next datum at the RAW character level (`skipDatum`): strings/escapes, line+block comments, `#\)` char literals, quote/backquote/unquote prefixes, `#(`/`#2A(` opens, nested `#+`/`#-` (skips feature expr + guarded form, like `*read-suppress*`), and `#.`. This is the point: a skipped form may use syntax rontolisp cannot parse. A **passing** guard just continues tokenizing.

**`*features*` is a VARIABLE on every backend, never a read-time substitution (todo-181)**: `LispNames.FEATURES_VAR`, in `PackageRegistry.CL_VARIABLES`, seeded with the target's feature names as an ordinary special holding a list — the interpreter in `Environment.createGlobal`, the compile paths from `LispMacroExpander.injectMvSpillGlobal` (a `(defvar *features* '(:A :B ...))` emitted only when the program mentions the name, like the printer-mode variables beside it). A program pushes onto it, `setq`s it and BINDS it exactly like any other special — and the binding is DYNAMIC on every backend, which the interpreter needed told (`LispEvaluator`'s `specialVars` seed, beside `*read-eval*`): the compile paths get it free from the injected `defvar`, so without the seed a `(let ((*features* ...)) (uiop:featurep :x))` — the shape upstream's own `(&optional (features *features*))` invites — bound lexically on the interpreter and dynamically everywhere else. That divergence is what the four-backend pin is for; it did not show up until a callee read the variable. `RontoLispCli` hands the compilers the set it READ with (`Jvm/WasmLispCompiler.runtimeFeatures`, defaulted per backend by `LispMacroExpander.backendFeatures` for a direct-compiler caller — unit tests, the playground), so a run-time `(member :rontolisp-component *features*)` and the `#+rontolisp-component` beside it cannot disagree.

The reader USED to substitute the symbol with `(quote (...))` on the compile paths, `pi`-style, "so a compiled program's feature set is fixed at compile time". That was two bugs, not a design: every `push`/`setq` was silently a no-op, and in a BINDING position it put a cons where a variable name goes, so the compile died with `LispCons cannot be cast to LispSymbol` in `FreeVarAnalyzer` — which is what `clack:clackup`'s `(let* ((*features* (cons :clackup *features*))) ...)` hit, breaking every clack/tiny-routes/ningle example on both compile backends at once. **The rule it illustrates**: read-time substitution is for CONSTANTS (`pi`, `array-dimension-limit`, `char-code-limit`, `lambda-list-keywords`). A name a program may bind or assign has to survive to the backend as a name. Beware the workaround shape it leaves behind — `uiop-os.lisp` had renamed upstream's `(&optional (*features* *features*))` parameter to dodge it, with a comment recording the root cause instead of fixing it.

**A source's own feature push IS visible to its own `#+`** (`reader.FeaturePushes`, todo-181): a top-level `(pushnew :F *features*)` / `(push :F *features*)`, bare or inside an `eval-when`/`progn`, widens the feature set the file is read with. Real CL has no gap here because `load` and `compile-file` both process a file FORM AT A TIME — which is why the announcement idiom (push in the header, `#+` on it below) is written at all: fast-io, trivial-utf-16, cl-json's float-lattice probe. **Why the decision is "the reader announces" rather than "load goes form at a time"**: the reader is the ONE layer the interpreter and all three compile backends share, so whatever it decides they agree on by construction, and none of them needs an evaluator to reach it. Form-at-a-time loading would have been an interpreter-only fix, re-opening the very cross-backend divergence the item was about — on the compile path "read the program" cannot depend on values the program computes at run time. Mechanics: `LispReader.readAll` calls `FeaturePushes.widen` first, which is gated on the text containing `*features*` at all (the scan is a second, provenance-free parse — `LispReader.readAllForScan`, which records no positions and swallows read errors so the real read reports them) and loops to a fixpoint, so a push revealed by an earlier push lands too.

Two limits, deliberate: **only a LITERAL keyword push is seen** — a value the program computes (`(pushnew (intern name :keyword) *features*)`, or trivial-utf-16's `(case char-code-limit (#x110000 (pushnew :utf-32 *features*)))`) stays invisible on every backend, because honoring it means running the program's code to decide how the program's own text is read; a source needing that declares it statically with the ASDF `:rontolisp-features` option instead -- or, since `.todo/401`, by depending on a built-in system that ANNOUNCES the feature (`trivial-features` -> `:unix`, `:little-endian`); one channel, three spellings (`.kb/asdf.md`). And the widening is WHOLE-FILE rather than positional (a `#+` above the push sees it too), because reading is one pass over the token stream and in the idiom the push is the header. Re-evaluation trigger: if the reader ever becomes incremental (lexing one top-level form at a time), the positional rule becomes free and the literal-only limit does not. Pinned by `LispReaderTest.readOwnFeaturePush*`, `JvmLispCompilerTest`/`WasmLispCompilerIntegrationTest`'s `*FeaturePushIsVisibleToTheSameSourcesConditionals` + `featuresIsAnOrdinarySpecialVariable`, `LispEvaluatorTest.evalFeaturesIsAnOrdinarySpecialVariableAndItsOwnPushIsRead`, and the four-backend ci-spec case `reader-features-own-push-is-visible`.

**`array-dimension-limit`** (todo-146, jzon's `(1- array-dimension-limit)` / `(#.array-dimension-limit)` bounds): substituted in `readSymbol` like `most-positive-fixnum`, backend-dependent — 2147483639 (the interpreter's `Environment` global, kept for `symbol-value`) on interpreter/JVM, `2^30 - 1` on WASM (inside i31). A read-time literal, which is sound for it and was not for `*features*` above: it is a CL CONSTANT, so no program may bind or assign it.

**`#.`**: three lexer modes. Normal mode = clear `LispReadException` ("#. read-time evaluation is not supported"; previously it silently mis-lexed as a `#.` symbol) — today only the playground COMPILE buttons still hit it (their `frontend` pipeline has no macro-time marker-resolution pass; the error is the honest answer there). Marker mode (`LispReader.readAllWithReadEvalMarkers`, `LispLexer.ReadEvalMode.MARKER`) wraps each `#.` datum in a `(%read-eval datum)` cons; consumers resolve the markers per top-level form just before it runs. Consumers: `LispEvaluator.loadFile` (global env), `RontoLispCli.interpret` (same), both REPLs (`ReplBuffer.eval`, the playground's `evalLine` — only a buffer textually containing `#.` pays for the marker read), the interpreter's RUNTIME `read`/`read-from-string` (todo-233, the fast-http `` #.`(eval-when ...) `` defconstant generator: `Environment.readRuntimeDatum` reads a `#.`-bearing datum in marker mode and applies the resolver `LispEvaluator` installed via `Environment.setReadTimeEvalResolver` — a bare `Environment` keeps the error-mode read, matching the compiled embedded readers), and the COMPILE PATH — `RontoLispCli.compileToFile` + `LoadInliner.spliceFile` read with markers whenever the source textually contains `#.`, and `UserMacroExpander.expand` resolves them via `LispEvaluator.resolveReadTimeEval` against its macro-time evaluator (marker presence alone activates the pass, before package resolution, so a datum sees the defuns/defvars of preceding forms). **A datum in a SPLICED file also sees that file's `*load-pathname*`/`*load-truename*`**, which the same loop establishes from `LoadInliner`'s `%begin-file` bracket -- the deferred resolution is exactly why it has to: the bracket's own lowering is a `setq` statement that runs far too late (todo-428, `.kb/load-inliner.md`). A datum reading such a `defvar` FORCES its lazy value thunk (`.kb/defmacro-backquote.md`) — this is the SECOND forcing site and the one a reader would not infer from "macros read globals": cl-ppcre's ~200 `(declare #.*standard-optimize-settings*)` sites reach the macro-time evaluator only this way, so narrowing the forcing to the macro-expansion entry point would break it on all four backends. A marker SPLIT into code position by a backquote template resolves through the `%read-eval` identity instead: an Environment function on the interpreter, a 1-arg identity emit in `Jvm/WasmExprCompiler`. Tolerant mode (`LispLexer.ReadEvalMode.SKIP_UNREADABLE`; `LispReader.readAllSkippingReadEval`, used only by `AsdfSystems.parseAsdSource`, and `LispReader.readFirstForm`) emits the same `%read-eval` marker, and for a datum it cannot re-lex a `(%read-eval-unreadable "RAW TEXT")` marker carrying the source text (`LispNames.READ_EVAL_UNREADABLE`). **It prints nothing** (todo-310): the lexer is the one layer that cannot know whether the position is load-bearing, and in a `.asd` most `#.` sits in metadata the parse discards, so the marker travels to the consumer and `AsdfSystems` decides — silent in an ignored option, hard error quoting the raw text where the value would pick a dependency or a source file (`.kb/asdf.md`). **`*read-eval*`** (`LispNames.READ_EVAL_VAR`, in `PackageRegistry.CL_VARIABLES`): seeded `t` in `Environment.createGlobal` and proclaimed special (the `LispEvaluator` initializer, next to `*print-escape*`); `resolveReadTimeEval` checks the current — dynamic-first — value before evaluating any marker and signals "cannot read #. while *read-eval* is nil" (CLHS), which covers every consumer above including the compile path's macro-time resolution. The variable exists on the INTERPRETER only: the compiled runtime readers signal on `#.` unconditionally (`.kb/read-load-streams.md`), so there is nothing for the variable to gate there. Pinned by `evalRuntimeReadSharpDotEvaluates` / `evalReadEvalNilMakesSharpDotSignal` / `evalSharpDotGeneratedDefconstants` (LispEvaluatorTest), `compileAndRunReadTimeEvalGeneratedDefconstants` (JVM), `readTimeEvalGeneratedDefconstants` (WASM) and the ci-spec case `reader-sharp-dot-generated-defconstants`.

**A marker value that is a SYMBOL in an evaluated position splices QUOTED (todo-244)**: `resolveReadTimeEval` has two entries. The plain one substitutes every value RAW — the runtime `read` family's contract, where the whole form is data. `resolveReadTimeEvalInCode` (what `loadFile`, `RontoLispCli.interpret`, both REPLs (`evalBuffer`, the playground's `evalLine`) and `UserMacroExpander` call — every consumer whose form is about to be EVALUATED; only the runtime `read` family keeps the raw entry) wraps a non-keyword SYMBOL value in `quote`, so the value stands for the OBJECT it renders — sxql's `(intern name #.*package*)` splices the package value, which rontolisp renders as a plain symbol where real CL's package object would self-evaluate; the quote restores the object semantics. **Every other value splices raw, exactly like CL's object splice** — notably a CONS value in code position IS code (fast-http's `` #.`(eval-when ...) `` defconstant generator top-levels the built list as the form; a caller wanting list DATA spells `'#.` as it must in CL — an earlier draft that quoted cons values too broke the fast-http ci-spec case). Position rules inside the walk: a marker inside a well-formed `(quote DATUM)` still splices raw (the datum is data), a whole `defpackage` form is data (alexandria-2 splices its re-export list as `(:export . #.(let ...))` — quote-wrapping there broke the clause), and a marker inside backquote construction code arrives as the reader's renamed TEMPLATE variant, which always spliced quoted. Downstream of the splice, the public `eval` re-resolves the substituted form, so the quoted symbol resolves as quoted data into the current package's spelling — which is why `packageDesignator` (intern/find-package/...) now takes a symbol designator by its MEMBER name (`LispSymbol.memberName`, CL's symbol-name rule: the qualifier says where the symbol lives, not what it names). Pinned by `loadSharpDotSymbolValueInCodePositionIsTheObject` (LispEvaluatorTest) and the `#.` leg of the `sxql-enablement-language-group` ci-spec case.

**`#:foo`**: still lexed as a plain symbol whose name keeps the `#:` prefix (NOT renamed — a defpackage/asdf designator needs the original name, so gensym-style freshness is out of scope). `PackageResolver.resolveSymbol` passes `#:`-prefixed symbols through unresolved (like keywords/`&`-markers); `PackageResolver.designator` and `AsdfSystems.designator/symbolName` strip the prefix.

ci-spec cases: `reader-block-comments`, `reader-feature-conditionals`, `reader-per-backend-features` (first use of `expectedByBackend`), `reader-features-variable`. Unit pins: the feature-conditional block in `LispReaderTest`, `loadedFilesAreReadWithTheGivenFeatures` in `LoadInlinerTest`.

`#N@(...)` (added for ironclad, 2026-07-25): a vector literal whose element
WIDTH is dropped — `#32@(#x428A2F98 ...)` reads exactly like `#(...)`. In
ironclad this syntax comes from a `set-dispatch-macro-character` handler
returning a `(make-array n :element-type '(unsigned-byte N) :initial-contents
'(...))` form, and rontolisp arrays are generic, so the literal vector IS that
form's value. Native in `LispLexer` because a user dispatch macro cannot extend
the Java-side reader: `set-dispatch-macro-character` is an accepted no-op
returning `t`, `copy-readtable` a no-op returning nil, and `*readtable*` a
variable seeded nil (`LispNames.COPY_READTABLE` and friends) — enough for the
`(defparameter *lib-readtable* (copy-readtable nil))` header idiom to load. Any
OTHER user dispatch character is therefore silently not honored: its literals hit
the ordinary lexer, which is a read error unless they happen to parse.

`#L(...)` / `#nL(...)` (added for iterate, 2026-08-27): the SharpL
abbreviation, a lambda whose arguments are named `!1`, `!2`, ... positionally --
`#L(list !2 !3)` reads as `#'(lambda (!1 !2 !3) (list !2 !3))`. Native for the
same reason `#N@(` is: iterate installs it with
`set-dispatch-macro-character`, which is a no-op here, and without it
`#L!2` (iterate.lisp:773) lexes as ONE symbol named `#L!2` and every clause
breaks at use. The arity is the highest `!n` the datum mentions unless `#nL`
spells it out (a smaller count is a read error); a datum whose first element is
itself a cons other than a `lambda` call is a LIST of body forms, iterate's own
`list-of-forms?`. Upstream binds gensyms and redirects the `!n` onto them with
`symbol-macrolet` purely for hygiene against a macroexpansion inside the body;
naming the parameters `!n` directly is the equivalence iterate's own
documentation states, and the `(declare (ignore ...))` it emits for the
unmentioned arguments is dropped (no rontolisp backend has the style warning it
suppresses). **Inside a backquote template the lambda cannot be built as a
datum** -- iterate's unioning clause is
`` `(... (delete-if #L(member !1 var :test ,test) ...)) `` -- so
`LispReader.readSharpLTemplate` reads the datum RAW once (where an unquote is a
marker cons) to get the arity, rewinds, and lets the ordinary template machinery
build the body; the lambda is then assembled around it by construction code
(`(list 'function (list 'lambda '(!1) BODY-CODE))`). `readRawTemplate` has its
own case, so a `#L` inside a NESTED backquote goes through the CLtL2 path whole.

Symbol single-escapes (added for parse-number, 2026-07-05): a backslash in a
symbol token makes the NEXT character part of the name verbatim -- even a
terminating one -- and is itself dropped (`LispLexer.readSymbol`), so locals
like parse-number's `\(-pos` read as a symbol named `(-pos`. `|...|` multiple
escape (added for jzon, 2026-07-18): everything between the pipes -- whitespace
and terminating characters included -- is part of the name, case verbatim, and
a backslash inside still escapes the next character. The compiled runtime
readers know neither syntax, matching the other frontend-only reader features
above.
