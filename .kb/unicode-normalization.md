# Unicode normalization (`eval/unicode-normalization.lisp`)

**Invariant: a normalization form is Common Lisp written here from Unicode Standard Annex
#15, over tables a running JDK answered; a text below the first code point its form changes
reads no table; nothing of a JDK or of ICU is copied.** Since k29 (2026-11-19). Spliced by
`eval/UnicodeNormalizationLibrary` the `UriLibrary` way (gate `%UNORM-`,
[source-language.md](source-language.md), "The run-time libraries' name gate"), outside the
front ends' libraries in `CompileFrontend.expand`. One entry,
`(rontolisp::%unorm-normalize text compat compose)`: NFD, with `compose` NFC, with `compat`
NFKD, with both NFKC. Its one caller so far is the Java subset's `java.text.Normalizer`
(`normalize0`, a `native` of the library source); it is its own library and not `java.lisp`
because nothing in it is Java's -- a string's elements are code points on every front end.
Provenance: [java-frontend-provenance.md](java-frontend-provenance.md).

## The forms

- **One pass, no array.** Each code point's decomposition is fed to a state of four slots:
  the last starter, the marks after it (kept in canonical order as they come: a mark goes
  behind the marks of its class and the lower ones), the characters written, the
  composites. A starter settles what came before it: where the form composes, each mark
  joins the starter if they have a composite and no kept mark before it is of its class or
  a higher one, the new starter joins it if no mark was kept, and what is left is written.
  Hangul is arithmetic both ways (the Unicode Standard's section 3.12); a syllable is fed
  whole where the form composes.
- **Three steps of cost.** (1) A scan for the first code point at or above the form's
  limit -- U+00C0 for NFD, U+0300 for NFC, U+00A0 for the two compatibility forms --
  answers the text itself and reads no table. (2) From there a scan by table: a text of
  "quiet" code points -- no entry, a Hangul syllable or a composite where the form
  composes, a compatibility mapping where the form is canonical -- is in the form already.
  What makes that sound: every code point that can be the SECOND of a composition has an
  entry (a mark its class, a starter the class 0, the Hangul vowels and trailing consonants
  among them), and a composite whose own decomposition starts with such a code point is
  marked not quiet (12 in Unicode 16: U+113C5 and the like). (3) Any other text is
  rewritten whole, and answered as itself when the result is equal.
- **The answer is the text itself whenever it is in the form.** A JDK answers the same
  object only sometimes (a lone mark under NFC comes back as an equal copy), so identity
  is not compared anywhere (`doc/*/java/deviations.md`).
- **No number of a combining class is kept, only the order of the classes**: no form reads
  more, and the public API of a JDK shows no more.

## The tables

`unicode-normalization-tables.lisp` is generated by `UnicodeNormalizationTablesTest` from
the running JDK's public `java.text.Normalizer` and pinned to it (the
`RegexUnicodeTablesTest` way; the Unicode notice of `THIRD-PARTY-NOTICES.txt`). Asked of
JDK 25 (Unicode 16), every code point:

- its NFD (2,081 canonical mappings outside the Hangul syllables) and its NFKD where that
  differs (3,848 compatibility mappings, stored whole);
- a composite is a code point NFC keeps although NFD takes it apart (961); its pair is the
  one code point of its NFD, and the composition of the others, that NFC composes to it.
  A composite is stored as its pair, which is both its decomposition (the first of the
  pair is decomposed again) and the composition's entry;
- a mark is a code point NFD moves across one of two marks of different classes (930), and
  the classes (55) are ordered by which of two marks NFD writes first;
- the Hangul syllables are held to the arithmetic.

What the run time relies on is asserted there: no code point has both a class and a
mapping. The encoding is the regex tables' base-32 digits; the mappings are headed by the
distance from the code point before and a kind, a mapping's first code point is a distance
from the one before of its sort, and a run of compatibility mappings to consecutive code
points (the full-width and the mathematical letters) is one entry (`%unorm-read`).

## Cost

Measured 2026-11-19 (Linux x86-64, GraalVM JDK 25.0.5, wasmtime 49).

- **Size of the tables' text**, in base-32 digits, canonical / compatibility: absolute
  code points 12,716 / 22,449 B (13,169 with whole canonical decompositions in place of
  pairs); the first code point as a distance 11,062 / 17,824; with the runs 14,010 for the
  compatibility mappings; with the length folded into the head, what ships: 21,298 B of
  mappings and 1,671 B of classes. A string literal is a byte a character in a `.wasm`
  (1,000 -> 11,000 characters: 1,937 -> 11,938 B).
- **Hash tables, not sorted vectors**: a composition is found by its first code point, and
  the mappings come sorted by the composite. `sort` is 16 KB of wasm (1,323 -> 17,977 B),
  `make-hash-table` with `gethash` 3.3 KB (-> 4,606 B), 22 to 30 ns a lookup. The
  sequence functions' `reverse` over the short lists brought 8 KB (59,943 -> 52,032 B
  without it), so the lists are reversed by a loop.
- **What a program pays**: YAVI's classic example 616,785 -> 655,275 B of wasm (the
  component 620,879 -> 659,541, the jar 240,951 -> 255,602): the tables' 23 KB and 14 KB
  of functions. The form is a field there, so all four travel; a call with a constant
  form is not specialized. A program of one `Normalizer.normalize` call is 94,707 B
  against 19,410 without, most of it what a first enum and a first interface call bring.
- **Time**, ns a call, wasm / the compiled jar / JDK 25, best of five rounds of 20,000:

  | Text | Form | wasm | jar | JDK |
  |---|---|---|---|---|
  | 55 ASCII characters | NFC | 1,870 | 282 | 48 |
  | 29 kana and kanji, composed | NFC | 2,328 | 401 | 83 |
  | 61 Latin characters with composites | NFD | 13,147 | 9,143 | 850 |
  | 28 characters with loose marks and jamo | NFC | 6,359 | 4,094 | 1,423 |

  The first read of the tables is 4.5 ms on wasm. The ASCII scan is what a Java `charAt`
  loop costs there (1,450 ns for the same 55 characters).
- **The result is built as a `StringBuilder` is** (`vector-push-extend` on a character
  vector, `%normalize-string` of it): 60 to 80 ns a character on wasm where `write-char`
  to a string stream is 150 to 220; the Latin row above was 25,385 ns over a stream.
- **Not `%string-code` for the scans**: it renders a mutable character vector whole at
  each read (a 56-character scan 35 us against 2.3), and a caller that is not Java may
  hand one.

## Tests

- `UnicodeNormalizationTablesTest`: the shipped tables are the running JDK's; the
  interpreter answers as the JDK for every code point of the tables and its neighbours,
  every pair, and 30,000 seeded texts, each in the four forms; a text below its form's
  limit leaves the tables unread. The same comparison over 208,930 texts was run once.
- `java-spec.yaml` `a-normalizer-puts-a-text-in-the-four-forms`: four backends, a JDK's
  lines.
