# `gensym` + `macroexpand`/`macroexpand-1`

`gensym` returns the ordinary symbol `#:<prefix><n>` (no uninterned symbols; default prefix `G`, matching CL's uppercase convention -- `.todo/640`) and is implemented in all three backends — interpreter (`Environment`, per-environment `AtomicLong`), JVM (`JvmGensymCompiler`, static `_gensymCtr` int field declared unconditionally like `_col`), WASM (`FUNC_GENSYM` runtime function slotted before `FUNC_USER_BASE` like the mod/rem helpers, `WasmGensymRuntimeBuilder` bump-allocates prefix bytes + decimal digits at `HEAP_PTR_ADDR`, counter word at `GENSYM_CTR_ADDR`=144).

The prefix must be a **literal** string on the compile path (like `open`'s `:direction`); a 0-arg `BuiltinFunctionWrappers` entry makes `#'gensym` work. `PackageRegistry.splitQualified` exempts `#:`-prefixed names from package qualification — expanded macro bodies reach `PackageResolver` on the compile path, and without the exemption `#:G1` errors as package `#`.

Gotcha: the interpreter shares ONE counter between macro-expansion time and run time while the compile path expands macros in a separate macro-time evaluator, so gensym names printed at runtime diverge across backends once any macro body calls gensym earlier in the program (ci-spec `gensym-and-macroexpand` documents the ordering rule). Second cause on the compile path: the macro-time counter is bumped by whatever that evaluator evaluates, and since macro-time globals are LAZY (`.kb/defmacro-backquote.md`) that is demand-driven -- a `(defvar *x* (gensym))` nobody reads at expansion time no longer advances it, so a later macro-body gensym is `#:G1` where it used to be `#:G2`. Generated names are bound inside their own expansion, so this renumbers without rebinding; the ci-spec case is unaffected because it prints only RUNTIME gensyms, whose counter belongs to the compiled program.

`macroexpand-1`/`macroexpand` are interpreter-native (`LispEvaluator.macroexpand1/macroexpand`, registered in `registerEval` because they need `userMacros`; built-in macros via `LispMacroExpander.expandBuiltinMacro`, whose case list must stay in sync with `PackageRegistry.CL_MACROS`); they expand the top-level operator only. Since todo-378 they also answer CL's `expanded-p` SECOND value — on the interpreter through the `%mv-spill` channel (`LispEvaluator.expandedWithFlag`), on the compile paths as the literal `(values 'expansion expanded-p)` the fold below emits. There is deliberately NO wrapper and no Jvm/Wasm compiler for either function: the macro table does not exist at runtime.

**Invariant (todo-378): whatever `macro-function` says about an operator, `macroexpand-1` must not contradict it.** On the compile path `UserMacroExpander` folds a literal `(macroexpand[-1] 'form)` to `(values 'expansion expanded-p)` (its activation gate also triggers on macroexpand calls without any defmacro), so the fold matches the interpreter exactly. A COMPUTED argument is the shape the fold cannot decide, and it reaches the `LispPreludeLibrary` definition, which answers the form unchanged with `expanded-p` nil UNLESS its operator has a `macro-function` — then it signals "a compiled program cannot expand a macro at run time", the same answer `macro-function`'s own expander stub gives when called. Answering a macro call with ITSELF is what the identity defun used to do, and it makes the standard `(do ((step form (macroexpand-1 step))) ((not (macro-function (first step))) ...))` loop — rove's `form-steps`, `.todo/372` row 8 — spin forever on the compiled backends while terminating on the interpreter. The re-evaluation trigger: the day a compiled program carries a runtime macro table, both the stub and this signal become real expansions and the divergence goes away together. The identity half is still what lets a portable code walker (ironclad's `trivial-macroexpand-all`) compile.

Because the prelude bodies consult `macro-function`, a surviving `macroexpand`/`macroexpand-1` call also triggers `UserMacroExpander.emitMacroFunctionTable` (`usesMacroIntrospection`): without the program's own macro names in that table, a USER macro call would be answered with silence where a built-in macro call signals.
