# `gensym` + `macroexpand`/`macroexpand-1`

`gensym` returns the ordinary symbol `#:<prefix><n>` (default prefix `G`). **Invariant: whatever `macro-function` says about an operator, `macroexpand-1` must not contradict it.**

## Where
- `gensym`: `Environment` (per-env `AtomicLong`) / `JvmGensymCompiler` (static `_gensymCtr`) / `FUNC_GENSYM` before `FUNC_USER_BASE` + `WasmGensymRuntimeBuilder`, counter at `GENSYM_CTR_ADDR`=144. Prefix must be a LITERAL string on the compile path; a 0-arg `BuiltinFunctionWrappers` entry makes `#'gensym` work. `PackageRegistry.splitQualified` exempts `#:` names, else `#:G1` errors as package `#`.
- CL's other `gensym` shape, a non-negative integer argument, is the suffix ITSELF under the default `G` prefix and never touches the counter (`(gensym 5)` is `#:G5`; the next plain `(gensym)` gets the number it would have anyway) -- `Environment`'s `LispInteger` arm, `JvmGensymCompiler`/`WasmGensymCompiler`'s literal-`LispInteger` branch (a plain compile-time constant symbol, `JvmEmitHelper`/`WasmEmitHelper.compileStringLiteral`, never routed through the counter-carrying `_gensymCtr` field or `FUNC_GENSYM`). Before todo a42 a non-literal-string argument on the compile path fell through to `expandComputedGensym` unconditionally -- which princs WHATEVER value it's given as a PREFIX and appends a fresh throwaway `(gensym "")` suffix -- so `(gensym 5)` silently printed `#:51` there (a wrong answer, not a compile error) while the interpreter rejected any non-string outright; both now accept the integer shape. `expandComputedGensym` still exists, but only literal-string and literal-`LispInteger` prefixes reach the compilers' direct branches -- a genuinely non-literal argument (a variable, a call) that turns out to be an integer AT RUNTIME still falls through it uncaught, which is `expandComputedGensym`'s pre-existing scope, not touched by a42.
- `macroexpand[-1]`: interpreter-native `LispEvaluator.macroexpand1/macroexpand` (`registerEval`); built-ins via `LispMacroExpander.expandBuiltinMacro`, whose case list must stay in sync with `PackageRegistry.CL_MACROS`. Top-level operator only; no wrapper, no Jvm/Wasm compiler. A symbol expands when it names a symbol macro of the environment argument (`.kb/symbol-macrolet.md`). Expands exactly the names `macro-function` claims (`isMacroName`); natively-run CL macros through `expandNativeMacro`, `handler-case` and the definers to internal forms `foldNativeExpansion` turns back (`.kb/symbol-runtime-api.md`). `expandBuiltinMacro` has no class registry, so a `typecase` clause naming a type it cannot resolve (the program's class, struct, deftype) expands to `(typep x 'name)` -- decided where it runs -- instead of `Unsupported type specifier` (cl-environments' walker expands every `typecase`, 2026-11-07); with a registry the compilers still refuse an unknown type.
- `expanded-p`: `%mv-spill` (`LispEvaluator.expandedWithFlag`) / the `(values 'expansion expanded-p)` fold in `UserMacroExpander`. A COMPUTED argument reaches the `LispPreludeLibrary` definition (form unchanged, nil) UNLESS its operator has a `macro-function`, which signals. A surviving call triggers `UserMacroExpander.emitMacroFunctionTable` (`usesMacroIntrospection`).
- `macroexpand-all` (2026-11-07): `rontolisp::%macroexpand-all form [env]`, trivial-macroexpand-all's arm (`eval/TrivialMacroexpandAllForms`, tier 4, [asdf.md](asdf.md)), answering `(values expansion t t)` as SBCL's arm does. `eval/MacroexpandAll` walks the code positions `CallSiteWalk` knows, outermost first: a global, `macrolet` or built-in macro through `macroexpand1` (a `macrolet`'s macros pushed with `pushLocalMacro` while its body walks, a `flet`/`labels` name shadowing a macro), a symbol macro SUBSTITUTED where it is referenced (shadow-aware) and the result walked -- so its expansion expands only at a reference: petalisp's `transform` binds each candidate variable to a symbol macro whose expansion calls a local macro that records it, and an eager expansion of the bindings (what `UserMacroExpander` does to a non-top-level `symbol-macrolet`) records them all. A natively-run built-in (`defun`, `handler-case`) stays and is walked by shape: its expansion is an internal form no walk knows. No compiler macro applies. The compile paths' prelude answers `(values form nil nil)`, the library's "not expanded": a program keeps no macro table at run time, while a macro calling it as the compile runs is answered by the compile-time evaluator. SWANK's `swank-macroexpand-all` keeps its own display walk (natively-run macros expanded, no local scopes). Pinned by ci-spec `gensym-and-macroexpand` (a macro finding the variables an expression mentions, all four).

## Traps
- Gensym numbering diverges across backends: the compile path expands in a separate macro-time evaluator whose globals are LAZY (`.kb/defmacro-backquote.md`). ci-spec prints only RUNTIME gensyms.
- Answering a macro call with ITSELF spins the standard `macroexpand-1` loop (rove's `form-steps`) forever on compiled backends; the identity half is what lets ironclad's `trivial-macroexpand-all` compile.
