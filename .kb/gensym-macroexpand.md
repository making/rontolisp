# `gensym` + `macroexpand`/`macroexpand-1`

`gensym` returns the ordinary symbol `#:<prefix><n>` (no uninterned symbols; default prefix `g`) and is implemented in all three backends — interpreter (`Environment`, per-environment `AtomicLong`), JVM (`JvmGensymCompiler`, static `_gensymCtr` int field declared unconditionally like `_col`), WASM (`FUNC_GENSYM` runtime function slotted before `FUNC_USER_BASE` like the mod/rem helpers, `WasmGensymRuntimeBuilder` bump-allocates prefix bytes + decimal digits at `HEAP_PTR_ADDR`, counter word at `GENSYM_CTR_ADDR`=144).

The prefix must be a **literal** string on the compile path (like `open`'s `:direction`); a 0-arg `BuiltinFunctionWrappers` entry makes `#'gensym` work. `PackageRegistry.splitQualified` exempts `#:`-prefixed names from package qualification — expanded macro bodies reach `PackageResolver` on the compile path, and without the exemption `#:g1` errors as package `#`.

Gotcha: the interpreter shares ONE counter between macro-expansion time and run time while the compile path expands macros in a separate macro-time evaluator, so gensym names printed at runtime diverge across backends once any macro body calls gensym earlier in the program (ci-spec `gensym-and-macroexpand` documents the ordering rule).

`macroexpand-1`/`macroexpand` are interpreter-native (`LispEvaluator.macroexpand1/macroexpand`, registered in `registerEval` because they need `userMacros`; built-in macros via `LispMacroExpander.expandBuiltinMacro`, whose case list must stay in sync with `PackageRegistry.CL_MACROS`); they expand the top-level operator only and return just the expansion (no `expanded-p` — no multiple values). On the compile path `UserMacroExpander` folds a literal `(macroexpand[-1] 'form)` to `(quote expansion)` (its activation gate also triggers on macroexpand calls without any defmacro); a computed argument is left in place and fails as `Cannot compile`; there is deliberately NO wrapper and no Jvm/Wasm compiler for them (the macro table does not exist at runtime).
