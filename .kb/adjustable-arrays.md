# Fill-pointer / adjustable / displaced arrays (`copy-array` surface)

The extended-array surface cl-utilities' `copy-array` touches, DONE on all four backends (interpreter, JVM, WASM Preview 1, WASM component):

- `make-array` options `:fill-pointer`, `:adjustable`, `:displaced-to` / `:displaced-index-offset`.
- `fill-pointer` (+ `setf`), `array-has-fill-pointer-p`, `adjustable-array-p`, `array-element-type`.
- `vector-push` / `vector-pop` / `vector-push-extend`.
- `adjust-array`, `array-displacement` (two values), `copy-array`.

The verbatim cl-utilities `copy-array` runs everywhere (`LispEvaluatorTest.clUtilitiesCopyArrayRunsOnInterpreter`, `JvmLispCompilerTest.compileClUtilitiesCopyArray`, `WasmLispCompilerIntegrationTest.compileClUtilitiesCopyArray`, ci-spec `fill-pointer-arrays-cross-backend`). `--no-gc` rejects the whole surface with its usual compile error (`--no-gc: unsupported operation 'vector-push' ...`).

## Shared semantics
- Only rank-1 arrays may have a fill pointer (`:fill-pointer t` = the vector size, an integer = that value, range-checked). The fill pointer is the effective length (`length`, `#(...)` printing, the sequence view) while `aref`/`row-major-aref` still reach the full backing store.
- `vector-push-extend` grows any fill-pointer vector regardless of `:adjustable`; the flag is reported VERBATIM by `adjustable-array-p`. SBCL answers `T` for any non-simple array, so a displaced view diverges (both conforming; CLHS leaves "actually adjustable" implementation-defined).
- `array-element-type` returns the type the array REMEMBERS being asked for; a displaced view's answer is its TARGET's. On the compile path it still expands to the LITE `(if (stringp x) 'character t)` (`LispMacroExpander.expandArrayElementType`) in a program that can build no typed array; `Jvm`/`WasmExprCompiler` route it to `compileElementType` (the full dispatch, displacement walk included) when `ctx.usesFloatArray || ctx.usesIntArray || ctx.usesTypedArray`.
- `%set-fill-pointer` is the internal `setf` target wired in `LispMacroExpander.expandSetf`.
- Interpreter/JVM errors carry `fn: message` text ("vector-pop: empty vector"); WASM traps (`unreachable`). Compiled `list` argument evaluation is right-to-left, so tests sequence side-effecting pushes/pops through separate bindings.
- First-class values (`#'vector-push` etc.) go through `BuiltinFunctionWrappers.ARRAY_FILL_POINTER_FUNCTIONS` (fill-pointer, array-has-fill-pointer-p, adjustable-array-p, array-element-type, vector-push, vector-pop, vector-push-extend in its 2-arg form, plus make-array), gated like `HASH_FUNCTIONS`: both compilers inject the group only when `programUsesAnyArrayOp`, so wrappers and helpers stay gated together. `#'make-array` is a variadic wrapper (`variadicMakeArray`) whose runtime keywords are re-extracted with `getf` — a `:displaced-to` argument selects the view shape (carrying `:fill-pointer`/`:adjustable` too), everything else the general shape; `:element-type` is accepted and ignored, which is what makes cl-utilities' `apply #'make-array` work.

## Strings as arrays
### Mutable character vectors
`make-array :element-type 'character` — with or without `:fill-pointer`/`:adjustable` — builds a mutable string on every backend.
- Interpreter: a mutable `LispString` (char[] buffer + fill pointer + adjustable flag).
- JVM: the GENERAL array representation holding character elements, marked by a **length-4** slot-0 header `Object[]{dims, fp, adj, null}` built by `_charVecMake`. Displacement detection is `header.length > 4` (displaced = length 5, or 7 for a string VIEW) at `emitResolveDisplacement` / `_arrayDispTarget` / `_arrayDispOffset`.
- WASM: **meta offset i31 == 1** (an ordinary array's is 0; a displaced array's data slot is a cell, so the marker is unambiguous, and `%array-disp-offset` reports the offset only when the data slot IS a cell).
- The whole fill-pointer surface (push/pop/push-extend, setf fill-pointer, `%array-become`, `_rmGet`/`_rmSet`) runs on it unchanged, and the marker survives `adjust-array` because become mutates the header in place.

**Mutability is the MARKER's, not the fill pointer's**: a `make-array :element-type 'character` (hence a `make-string`) with no `:fill-pointer` leaves the fill-pointer slot NIL on every backend, and `setf char`/`setf aref` still write every slot. The JVM used to default that slot to the capacity, so `(array-has-fill-pointer-p (make-string 3))` answered `T` there and `NIL` everywhere else and in SBCL — and the value could not be told from a `:fill-pointer`-built one, which is what `(typep s 'simple-string)` / `simple-string-p` ask (`.kb/declarations-type-checks.md`).

### A plain `(make-string n)` IS a character vector
`LispMacroExpander.expandMakeString` (shared by the interpreter and both compilers) lowers to `(make-array n :element-type 'character :initial-element c)`. `make-sequence` reaches it through `expandMakeSequence`.

**Trap this fixes**: the old lowering `concatenate`d one character per iteration into a fresh IMMUTABLE string — O(n^2), and because the result was immutable the `(%arrayp seq)` test in `expandReplace` / `expandScharSetFunctional` was false, so `(replace buf x)` took its FUNCTIONAL branch and had the result discarded in statement position. s-sql's verbatim `strcat` therefore sent PostgreSQL a BLANK string of the right length, silently. If a future change makes `make-string` build anything other than the character vector, that whole "allocate a buffer, write into it" class regresses. Pinned by ci-spec `make-string-mutability-cross-backend` and `PostmodernE2eTest`'s `runtimeSql*` leg.

Consequences, all decided:
- **The JVM array gate includes `make-string`**: `Ctx.usesArrays` is `programUsesAnyArrayOp(program) || usesFloatArray || usesIntArray` (plus the forced-group term below), and both backends' `programUsesAnyArrayOp` list `MAKE-STRING` and `MAKE-SEQUENCE` alongside `MAKE-ARRAY` (they lower to it during `compileExpr`, after the scan). A string-only program that allocates a buffer pulls in the array runtime and grows — deliberate, since a scan for "does this program mutate the string" cannot see mutation through a call (`strcat` mutates its own local), which is the bug. `make-string` also joined `ARRAY_FILL_POINTER_FUNCTIONS`.
- `eq`/`eql` on a make-string result answers like any computed string — content on the interpreter and JVM, identity on WASM (WASM strings carry an id field; `_eq` compares it). CL leaves it unspecified; the ci-spec case deliberately does not cover it.
- `--no-gc` is unaffected (`make-string` was already unsupported; its `make-array` takes float element types only).
- The functional branches stay: a LITERAL string is still immutable, so `expandReplace` / `expandScharSetFunctional` keep their `%arrayp`-false paths.

### On-demand normalization into the immutable runtime string
JVM `_strv(Object)` (`JvmArrayRuntimeBuilder`, emitted under the array gate) renders the active prefix quote-framed; WASM `_charvec_to_str` (a fixed always-emitted function right after `FUNC_WRITE_STR_GC` — `FUNC_VEC_BASE`/`FUNC_USER_BASE` shifted by one, reusing the unary `TYPE_CALLABLE_BASE + 0` signature, capture-aware scratch so mid-capture normalization cannot clobber `*-to-string` output).

Insert points: the string-op compile sites (subseq, string=/-equal, case/trim/concat, write-string, string designator, read-from-string, make-string-input-stream, intern, make-symbol) — NOT char/schar/elt, which read the ELEMENT through `_charRef` / `_str_char_ref` rather than rendering per index (`.kb/string-index-cost.md`). The last four were WASM-only until a plain `make-string` result reached them on the JVM, where `_readFromString` and `intern`/`make-symbol`'s quote strip both `checkcast String` and threw `ClassCastException`; `%make-string-input-stream` was the one missed then, found via jose (every string out of trivial-utf-8's `make-string` + `(setf char)` loop into cl-json's `decode-json-from-string`). Plus the shared runtime bodies — JVM `emitArrayBranch` of `_lispToString`/`_lispToDisplayString` (which covers equal-hash-table keys, keyed by rendered string) and `_eqv`'s equals fallback; WASM the entries of `_equal`, `_hash`, `_print_val`, `_princ_val`.

On the JVM everything is gated on `Ctx.usesArrays` so array-free programs stay byte-identical; on WASM the helper is always emitted.

**A PREDICATE does not normalize.** `stringp` was in the WASM list and is the one caller that never wanted the string: its `TYPE_CELL` arm called `_charvec_to_str` and `ref.test`ed the result, i.e. answered an O(1) question by rendering every element (10.2 s for 200,000 calls on an 8192 vector, exactly linear, while the interpreter and JVM were flat).

The shape decision is its own runtime function, **`_charvec_p`** (`FUNC_CHARVEC_P`, `WasmStringRuntimeBuilder.buildCharvecPBody`, appended right after `FUNC_CHARVEC_TO_STR`, `((ref null eq)) -> i32` reusing `TYPE_RAT_GET`): the eight `ref.test`s down to the marker compare and nothing else, 213 bytes. `stringp` calls only that; `_charvec_to_str` opens with it and then renders, so the marker invariant has ONE owner. Inlining the tests per site was rejected on measurement: a call frame is under 5 ns and essentially all of the 9 ms is the eight tests, which inlining still pays. Now flat in the length for every `TYPE_CELL` shape, and 58 bytes SMALLER overall; a program that never reaches the arm is byte-identical at `--optimize`. Pinned by `WasmLispCompilerIntegrationTest.compileStringpClassifiesEveryCellShape` and `compileStringpOverACharVectorIsConstantTime` (a ratio between two lengths, so the pin is machine-independent).

Not done, deliberately: the OTHER callers (and the JVM's `_strv`) still re-render on every call, because the rendered string is never written back into the cell. Caching it would fix the class but a character vector is MUTABLE, so every write reaching it would have to invalidate the cache and missing one is silent wrong output.

### String mutation flows through shared expansions
`expandReplace`, `expandFill` and `expandScharSetFunctional` branch at runtime on `(%arrayp seq)` — a vector (char vector included) is written in place via `%row-major-aset` + `elt` and returned; an immutable string keeps the functional rebuild (fresh string; the setf form still requires a variable place). `fill` is `replace` with a constant source plus one arm: a LIST target has its `car`s rewritten with `rplaca`, and the string rebuild splices a `(make-array n :element-type 'character :initial-element item)` filler between head and tail. The interpreter writes a string in place through `LispString.setCharAt`, so that deviation is compile-path-only.

ONE exception: a string LITERAL is never written in place on any backend, `%schar-set` included, because the literal is the source constant (`.kb/string-write-runtime.md`). `replace`/`fill`/`nstring-*` do not yet honour that and still corrupt a literal on the interpreter. `nstring-upcase` / `nstring-downcase` / `nstring-capitalize` are prelude Lisp that folds with the NON-destructive sibling and walks `%nstring-replace`'s `(setf (aref s i) c)` over the result, inheriting the same split (a mutable character vector comes back `eq` everywhere; an immutable string is rebuilt on the compile paths while the interpreter folds the caller's object). The RETURN value is correct on all four either way.

`lowerCharacterInitialContentsMakeArray` lowers rank-1 character `:initial-contents` to a fresh string copy (`subseq` of a stringp contents, else `coerce 'string`) — both compilers try it BEFORE the general `:initial-contents` lowering. Default `:initial-element` for a char vector is `#\Space`.

Lite residue: `adjust-array` on a NON-adjustable char vector returns a general (unmarked) vector; `#'make-array`'s variadic wrapper has no `:element-type` cue, so it builds an unmarked vector; char reads past the fill pointer see the rendered (fp-bounded) content. E2E ci-spec `mutable-strings-cross-backend`; unit `compileCharVector*` / `compileScharSetfMutatesCharVectorInPlace` / `compileJzonAccumulatorPattern`.

### Array-info readers accept every string representation
`array-dimensions`, `array-rank`, `array-total-size`, `array-dimension`, `array-row-major-index`, `array-has-fill-pointer-p` and `adjustable-array-p` accept the immutable header-less string, the mutable character vector and the displaced string view, on all four backends. The three shape readers and the row-major index lower through `array-dimensions` (`LispMacroExpander.expandArrayRank` and friends), so ONE string arm per backend carries them — `JvmArrayRuntimeBuilder._arrayDims` (an `instanceof String` arm over `_strCharCount`, ahead of the `ArrayList` header cast) and `WasmArrayCompiler.compileDims` (a `ref.test TYPE_STRING` arm over `_str_char_count`). The two predicates guard the header read with a shape test and answer NIL otherwise (`emitHeaderSlotToBool`; `compileHasFillPointer` / `compileAdjustableArrayP`), so a headerless string is nil rather than a cast trap.

The dimension is the **CAPACITY**, never `length`: a capacity-5 character vector with fill pointer 2 answers `(5)` / rank 1 / total size 5 while `length` answers 2. Pinned by `LispEvaluatorTest#theArrayShapeReadersAcceptEveryStringRepresentation`, `JvmLispCompilerTest#compileTheArrayShapeReadersAcceptEveryStringRepresentation`, `WasmLispCompilerIntegrationTest#arrayShapeReadersAcceptEveryStringRepresentation` and ci-spec `string-array-shape-readers-cross-backend`.

### `char`/`schar`/`aref` and the fill pointer
`aref`/`row-major-aref` reach the FULL backing store on every backend, strings included: `Environment.charRef` and `%schar-set` bound by `capacity()`, not `LispString.length()`. CL is explicit that `char`, `schar` and `aref` ignore fill pointers. Pinned by ci-spec `string-fill-pointer-inactive-slots` (read AND write through `aref`).

**`char`/`schar` PAST the fill pointer are still three-way divergent** and the ci-spec case deliberately does not cover them: the interpreter returns the slot, the JVM throws a raw `String.offsetByCodePoints` exception, both WASM backends return `#\Nul` (they materialize the string at its fill-pointer length and have no bounds check at all — writing past the end silently APPENDS). That is the general missing-bounds-check gap, not a fill-pointer question.

## A COMPUTED `:element-type`
The recognizers read the designator at EXPANSION time, so a `:element-type` held in a variable or produced by a call (`(stream-element-type s)`) used to fall through to the general array — and with `stringp` false, a `read-sequence` into it read BYTES from a character stream. `LispMacroExpander.lowerRuntimeElementTypeMakeArray` (tried first by `Jvm`/`WasmArrayCompiler`, before the `:initial-contents` lowerings) turns such a call into a runtime `member` dispatch: the character designators pick the `:element-type 'character` allocation, anything else drops the keyword and takes the general one — the packed float / `(unsigned-byte N)` arrays are OPTIMIZATIONS of the general array, so that is always a correct answer, just not always the packed one. "Literal" means a `(quote ...)` form, the unquoted `(unsigned-byte 8)` compound shape, or a bare symbol in `LITERAL_ELEMENT_TYPE_NAMES`. The interpreter needs no lowering (its `make-array` reads the designator at run time).

## The JVM array gate is a CONSEQUENCE, not a prediction
**Invariant: on the JVM the array runtime is emitted whenever the emitted bytecode calls it, no matter which lowering introduced the call.** A source-name scan alone could not be right by construction — several lowerings introduce an array primitive only during `compileExpr`, AFTER the scan, and JVM method resolution is lazy, so the class verified and threw `NoSuchMethodError` the first time the branch ran.

How it works in `JvmLispCompiler`:
1. The scan stays — it decides `Ctx.usesArrays`, which changes CODE, not just emission (the `_strv` normalization at string-op sites, the character-vector arm of `stringp`, the array print branch), so it must be known before any body compiles.
2. After the class bytes are assembled, `JvmClassShaker.unresolvedSelfMethods` (in `am.ik.jvm`, language-independent) walks every emitted body and reports each own-class method some `invoke*` names but the class does not declare.
3. A reported name is matched against the per-group rosters (`JvmArrayRuntimeBuilder.METHOD_NAMES`, `JvmHashRuntimeBuilder.METHOD_NAMES`, the eval runtime's four methods + `_lookup`). A match means the gate under-predicted, so `compile` RE-RUNS with the group forced on — the build a source that DID mention an array operator would have produced. Each retry strictly grows the forced set, so the loop terminates.
4. Anything unmatched is an internal inconsistency; the compile fails loudly naming the call and its callers.

The rosters in step 3 are the one thing written by hand, so `JvmRuntimeGroupNamesTest` pins each against what its builder emits, both directions. WASM has no equivalent gap (it emits array builtins inline; its `programUsesAnyArrayOp` only excludes wrapper groups).

**The check covers EVERY caller, wrappers included.** It briefly skipped calls referenced only by injected wrappers (`#'+`, `#'reverse`, `#'sort`, `#'subseq`, `#'string=`, ... ~33 of them called `_aref1`), because without the skip every class carried ~35 KB of array runtime. The skip was sound but cost the check its strength (a genuinely reachable dangling call inside a wrapper was invisible — `#'funcall`'s `(apply f r)` was exactly that). The skip is gone because its cause is: **each lowering that dispatches over the sequence representations takes an `arraysExist` flag and drops the array arm when false.** The interpreter and both WASM backends pass `true`; the JVM passes `Ctx.usesArrays`.

| lowering (`LispMacroExpander`) | what the flag drops |
| --- | --- |
| `expandCoerce` | the vector scan behind `'list` / `'string` (`coerceVectorToList`) |
| `expandElt` | the `aref` arm of the string/list/array dispatch |
| `expandMap` | the same `aref` arm in the per-element read |
| `seqResultDispatchForm` (private; `wrapSortForStringSeq`, `expandReverse`, `expandRemoveDuplicates`, `expandRemove`, `expandRemoveIf`, `expandRemoveIfNot`, `expandSubstitute` forward the flag) | the `__seq_vec` binding and the `(coerce __seq_res 'vector)` rebuild |
| `expandSubseqCompat` | the whole rewrite — it exists only to reach the array arm, so it returns `null` and the compiler emits its plain `%subseq-core` |
| `expandReplace` | the destructive `%row-major-aset` loop, leaving the functional string rebuild |
| `expandVectorp` | the whole ARRAY arm, leaving `stringp` alone — once `vectorp` checks the RANK its array arm reads `array-dimensions`, and `vectorp` has an injected wrapper EVERY program carries until the shaker runs, so an ungated read put `_arrayDims` in `(print 1)` |

**Reading and BUILDING are gated differently, and that is why this is sound.** Dropping a READ of an array element is a local fact: no array exists, so no read can run. Dropping a form that CONSTRUCTS an array is not — only the caller's guard can say it is dead. So `expandCoerce` gates the reading direction only, and the one builder-dropping place is `seqResultDispatchForm`, which rebuilds a vector result exactly when the INPUT was a vector. Every other coerce-to-vector keeps its builder and is caught by step 3. `(print (+ 1 2))` went 186,066 -> 127,630 bytes (-31%). Pinned by `JvmLispCompilerTest.anArrayFreeProgramReferencesNoArrayRuntimeHelper` plus `compileSequenceOperatorsWithoutTheArrayRuntime`.

**The array-gated wrapper set is complete.** Ten wrapper bodies were never behind the flag dispatch and called `_aset1`/`_charVecMake`/`_arrayMake`/`_aref1`/`_arrayDims` UNCONDITIONALLY: `fill`, `coerce`, `vector`, `read-sequence`, `write-sequence`, `svref`, `array-rank`, `array-dimension`, `array-total-size`, `array-row-major-index`. Each is injected in every class, so an array-free program forced `GROUP_ARRAYS` on and re-ran the whole compile. Fixed the `#'funcall` / `APPLY_USING_FUNCTIONS` way (`.kb/eval-runtime.md`): reference-gate wrapper and runtime on the same fact instead of flag-gating the body. All ten joined `ARRAY_FILL_POINTER_FUNCTIONS`; `LispMacroExpander.usesGeneralArrayOp` already named most, so only `fill`/`read-sequence`/`write-sequence` were new — and `WasmLispCompiler`'s own `programUsesAnyArrayOp` got the same three, so the two scans cannot drift. Pinned by `aProgramThatNeverNamesAnArrayOperatorCarriesNoArrayRuntime` / `namingOneOfTheArrayWrappersBringsTheArrayRuntimeBack`.

The packed `_fv*` / `_iv*` tiers need no equivalent: `Ctx.usesArrays` is true whenever `usesFloatArray` / `usesIntArray` is, and an `aref` only compiles to `_ivAref1` / `_fvAref1` when that tier is emitted.

The `%class-designator` dispatch (what `class-of` lowered to before the metaobject migration) was the one lowering whose gated call was NOT behind such a test: its `cond` chain included a `hash-table-p` clause unconditionally, so every class that compiled one referenced `_hashP`. `expandClassDesignator` now takes a `hashTablesExist` flag (interpreter and both WASM backends pass `true`; the JVM passes `Ctx.usesHashTables`) and drops its `hash-table-p` clause when no hash table can exist — the same reasoning as `JvmStringpCompiler`'s character-vector arm.

Why this shape: scanning the expanded program is unavailable (expansions are lazy, per-site, inside `compileExpr`), and emitting the group unconditionally would end array-free byte-identity (`.kb/emitted-output-determinism.md`). Step 2 costs one linear pass per build; step 3 a second compile only for a program that trips a gate.

**`(setf (elt s i) v)` is the worked example** and needed a semantic fix too: `expandSetf`'s `ELT` branch yielded `(%aset seq i v)` for everything non-`consp`, so a STRING target reached `%aset` — `NoSuchMethodError` on the JVM, `cast failure` on both WASM backends, only the interpreter right. It now carries the same three-way dispatch `(setf (aref s i) v)` has — `consp` -> `rplaca`, `stringp` -> the `schar-set` rebuild, else `%aset` — with the same restriction: only a VARIABLE place takes the string arm. Pinned by ci-spec `setf-elt-cross-backend`, `LispEvaluatorTest.evalSetfEltDispatchesOverListStringAndVector`, `JvmLispCompilerTest.compileSetfEltOnAStringMutatesIt` + `compileSetfEltOnAVectorAndAList`, `WasmLispCompilerIntegrationTest.compileSetfEltDispatchesOverListStringAndVector`. The string arm is a CALL now (`%schar-set-runtime`, one spliced defun per program, `.kb/string-write-runtime.md`).

Two long-latent bugs of the same family, fixed at source rather than by retry:
- **`#'funcall` died with `NoSuchMethodError`**: its wrapper body is `(apply f r)` -> the eval runtime's `_apply`, but the wrapper was emitted in EVERY class while `_apply` stayed gated on the SOURCE mentioning `eval`/`apply`. `(reduce #'funcall fns)` (cl-utilities' `compose`) hit it. Rule now: a wrapper whose body needs a gated runtime is injected exactly when the program references the operator as a value, and that reference forces the runtime on. Pinned by `JvmLispCompilerTest.compileFuncallAsAFirstClassValue`.
- **`_tlsConnect` instantiated a constructor not always emitted**: the socket group is emitted for any TCP/TLS operator but `<init>` was gated on `tls-connect` alone. a `tcp-connect`- or `tls-listen`-only program declared no constructor. `needsInstanceCtor` follows the socket gate now. (The X509TrustManager interface and its three methods stay on `usesTlsConnect`: nothing calls them from bytecode — JSSE does.)

Costs, deliberate: any program using `(setf (elt ...))` pulls in the array runtime; and the `_top$N` chunk budget dropped 40000 -> 24000 because the string arm cost ~6 KB per site and a single top-level form cannot be split under the JVM's 65535-byte method cap. **Re-evaluation trigger**: with the arm out of line the marginal cost of one more site is **293 bytes, not 5,042**, so 24000 is not the number the corpus needs — re-measure (compile with the budget set to 1 and read `-Drontolisp.jvm.debug-method-sizes=true`, which ranks top-level chunks alongside defuns and lambdas) before treating it as load-bearing.

## The growth policy of `vector-push-extend`
The capacity a full vector grows to is OBSERVABLE (`array-dimension` reads it back; a sized sequence type tests it, `(typep v (list 'string (array-dimension v 0)))`), so it is ONE policy for all four backends even though CLHS leaves the default extension implementation-dependent. Stated once, in `am.ik.rontolisp.ArrayGrowth`:
- a SUPPLIED `extension` is added verbatim (`cap + ext`);
- with no extension the capacity DOUBLES (`GROWTH_FACTOR`), off a floor of `MIN_CAPACITY` = 1 for the zero-capacity vector;
- `NO_EXTENSION` = 0 is the "argument not supplied" sentinel, so ONE runtime entry point serves both arities. CLHS requires a supplied extension to be positive, so zero or negative takes the default.

Those are SBCL 2.2.9's numbers. Growing by one element per push — what the compile paths did by passing a literal `1` — makes a push loop quadratic, and a push loop is how programs build strings and buffers.

The interpreter CALLS `ArrayGrowth.grownCapacity` from BOTH representations (`LispArray.vectorPushExtend`, `LispString.vectorPushExtend` — the latter used to double from a floor of 8 on its own). Generated code cannot call the class, so both compile paths EMIT the same arithmetic inline against its constants (`JvmArrayRuntimeBuilder._vectorPushExtend`, whose `ext` argument is the sentinel when `JvmArrayCompiler` had no third argument; `WasmArrayCompiler.compileVectorPushExtend` + `emitDefaultGrownCapacity`). Cost of the branchy formula over `cap + max(ext, 1)`: +15 bytes once per JVM program (one runtime helper), ~23 bytes per WASM call site (no helper to share) — not worth hoisting.

Pinned by `LispEvaluatorTest.vectorPushExtendGrowthPolicyIsDoubling`, the `compileVectorPushExtendGrowthPolicyIsDoubling` twins, and ci-spec `vector-push-extend-growth-cross-backend`. The older `fill-pointer-arrays-cross-backend` case never reads a dimension after a growth run, which is why the divergence went unnoticed; keep the growth numbers in the new case.

## A slot the growth OPENS holds the element type's zero
**Invariant: an array slot nobody wrote holds its array's remembered element type's own zero, on all four backends, no matter WHICH operation opened it — `make-array`'s allocation, `vector-push-extend`'s growth, or `adjust-array`'s.** Those slots are below the DIMENSION, so `aref` may read them even though they are above the fill pointer.

Before this the compile paths opened them with a RAW NULL (`JvmArrayRuntimeBuilder._vectorPushExtend`'s `list.add(null)`, `WasmArrayCompiler.compileVectorPushExtend`'s `array.new` with a null init), so a grown CHARACTER vector CRASHED (JVM `NullPointerException`, wasm `cast failure`) where the interpreter answered a character; and `adjust-array`, whose expansion allocated a plain general array, filled with `nil` on every backend, so a `double-float` vector adjusted without `:initial-element` read back `NIL`.

The fill is ONE question with ONE answer per element type (`ArrayElementTypes.defaultElement`), asked of the ARRAY rather than of a literal designator — the internal primitive `%array-default-element`:
- **Interpreter**: `Environment.arrayDefaultElement` switches on the representation (`LispString` -> the character zero, `LispIntVector` -> 0, `LispFloatArray` -> 0.0, `LispArray` -> `defaultElement(elementTypeCode())`). `LispString` now fills its grown and `adjust-array`ed slots with `ArrayElementTypes.DEFAULT_CHARACTER` (its `int[]` buffer zero-filled to `#\Nul` before). The `adjust-array` built-in defaults `init` to the ARGUMENT's own zero and carries `elementTypeCode()` into the resized copy.
- **JVM**: `_arrayDefaultElement(o)` reads the SAME header facts `_arrayElementType` reads, in the same order — a `String` argument is a character array; a length-4 header is the character-vector marker; a displaced or string-view header (slot 3 non-null) and a plain length-3 one remember nothing; otherwise header slot 4 holds the element type VALUE (an `Object[]` cons for `(unsigned-byte n)`, the name string otherwise). `_vectorPushExtend` calls it ONCE per growth.
- **wasm**: `compileArrayDefaultElement` mirrors `compileArrayElementType`'s four-representation dispatch, and `emitDefaultElementForHeader` reads the meta MARKER word. Marker 1 (the mutable character vector) is checked ALWAYS — no `make-array :element-type` scan can predict it, because any mutable string carries it — and markers 2..7 are gated per width on `Ctx.typedArrayCodes` exactly as `emitRememberedElementType`'s arms are.

`adjust-array` reaches it through its EXPANSION: `expandAdjustArray` always spells `:initial-element`, using `(%array-default-element a)` when the call gave none.

**The character fill is `#\Space`, not SBCL's `#\Nul`** (`.kb/array-literals.md`). The general (`t`) vector keeps `NIL` where SBCL answers `0`, deliberate. Cost: a constant per JVM program (one helper); per SITE on wasm (~51 bytes for a push-extend site, ~240 for an `adjust-array` site). A program using neither operator compiles to the same bytes. Pinned by `LispEvaluatorTest.aSlotOpenedByGrowthTakesTheElementTypeZero`, the `compileASlotOpenedByGrowthTakesTheElementTypeZero` twins in `JvmLispCompilerTest` and `WasmLispCompilerIntegrationTest`, and ci-spec `opened-slot-fill-cross-backend`.

## The adjusted COPY remembers the element type
**Invariant: `adjust-array` never changes an array's element type. An `:adjustable` array keeps its own identity and with it its type; a NON-adjustable one answers a FRESH array STAMPED with the adjusted array's type.** Before this an adjusted character vector came back a general vector (`stringp` NIL, `array-element-type` T) where the interpreter and SBCL answer T / CHARACTER.

**The stamp COPIES the type word; it does not re-derive the representation** — that is what makes it affordable. Spelling `:element-type (array-element-type __adj_a)` on the expansion's `make-array` measured **+4,264 bytes (+39%)** on a one-site program, because a runtime designator turns one allocation into the seven-arm dispatch and `Ctx.typedArrayCodes` would count every `adjust-array` program as every specialized width. The internal primitive `%array-adopt-element-type (new old)` moves one word instead (+303 on the same program, a fourteenth of the price):
- **Interpreter**: `LispArray.adoptElementType`, the one writer of the `elementTypeCode` field. `Environment.arrayElementTypeCode` is the single per-representation answer, shared with `%array-default-element`.
- **JVM**: `_arrayAdoptElementType(dst, src)` reads the SAME header facts `_arrayDefaultElement` reads and writes the stamp in the SAME two shapes the allocator uses — the length-4 character-vector marker for a RANK-1 character type, header slot 4 otherwise (a length-3 header grows to hold it; a packed length-6 one already has it). A `dst` that is already a character vector, or displaced (slot 3 non-null, where slot 4 is the offset), keeps what it has.
- **wasm**: `compileArrayAdoptElementType` copies the meta MARKER word verbatim — one `struct.set`, unconditional (a guard costs more than it saves). Because the word is COPIED rather than decoded there are NO per-code arms, so nothing for the per-width `Ctx.typedArrayCodes` gate to predict. `emitRememberedMarker` reads it with `emitRememberedElementType`'s guards.

**An IMMUTABLE string is a legal `adjust-array` argument on the compile paths.** `(adjust-array "abc" 5)` used to die in the expansion's primitives (JVM `String cannot be cast to ArrayList`, wasm `cast failure`), and so did `(array-dimensions "abc")` and friends — the same hole one level down, every shape reader expanding through `array-dimensions`. `_arrayDims` / `compileDims` answer a string's length in code points as its one dimension, and `%array-disp-target` / `%array-disp-offset` answer nil / 0 (a string VIEW is a header, never a runtime `String`).

**Still NOT adjustable: a PACKED vector.** The interpreter signals `adjust-array: not applicable to a packed integer vector` / `... packed float array`, and so does the JVM (`_ivRequireGeneral` / `_fvRequireGeneral`, reached through `%array-disp-target`'s `emitRequireGeneralIfPacked`; a program with no packed float array emits no `_fvRequireGeneral`, so the default build stays byte-identical). Wasm has no custom trap-message channel here for EITHER representation — `castCellGet0` traps `cast failure` — the parity bar that backend can meet.

Pinned by `LispEvaluatorTest.anAdjustedCopyKeepsTheElementType`, the `compileAnAdjustedCopyKeepsTheElementType` twins in `JvmLispCompilerTest` and `WasmLispCompilerIntegrationTest`, and ci-spec `adjusted-copy-element-type-cross-backend` (one program, one expected text, all four backends, every answer SBCL 2.2.9's but the two deliberate deviations).

## `sort`/`nreverse`/`stable-sort` keep a vector's fill pointer and identity
**Invariant: `sort`, `nreverse` and `stable-sort` permute a fill-pointered or adjustable vector/string IN PLACE — same object, same fill pointer, same adjustable flag, same total size — on all four backends, matching SBCL.** Before this `seqResultDispatchForm`'s vector/string arm always answered a FRESH, SIMPLE rebuild, so a fill-pointered array lost its fill pointer entirely (`(fill-pointer (sort v #'<))` signalled `array has no fill pointer`; surfaced through `practicals-1.0.3/Chapter27/database.lisp`'s `sort-rows`/`delete-rows`).

- The fix is a second flag, `destructive`, on `seqResultDispatchForm`, private to the three permuting callers (`wrapSortForStringSeq`, `wrapNreverseForStringSeq`, `expandStableSort` — all literal `true`). `false` (`expandReduce`, `expandRemoveDuplicates`, `expandRemove`, `expandRemoveIf`, `expandRemoveIfNot`, `expandSubstituteIf`) is unchanged: those five are non-destructive by CLHS and their fresh simple rebuild is NOT to be made identity-preserving.
- **The destructive rebuild is `(replace __seq_in <fresh-rebuild>)` — answering THAT CALL's result, not `__seq_in` forced.** `replace`'s array arm mutates in place and returns its target, so for a vector this is `__seq_in` either way. For a STRING it is not: a program-text literal cannot be written in place, so `replace`'s string arm copies and answers the COPY. `(progn (replace __seq_in <rebuild>) __seq_in)` was tried first and is wrong — it discards that copy and answers the UNSORTED literal (`(sort "cab" #'char<)` came back `"cab"`, caught by `compileAndRunSequenceReturningFunctionsOnStrings` and `compileSequenceOperatorsWithoutTheArrayRuntime` on the JVM suite).
- The INTERPRETER takes a separate path, `Environment.seqResultDestructive`, since its native `sort`/`stable-sort`/`nreverse` never routed through the macro expander's dispatch: it writes `LispString`/`LispArray`/`LispIntVector` in place directly (bypassing the `REPLACE` builtin, which cannot take a LIST source into a STRING target — `requireString` demands a literal `LispString`) and takes the same source-literal branch (`sourceLiteral()` -> `copyForBulkWrite()`).
- **It does NOT touch the backing store beyond the active length**: `list`'s length is always the original's active length for all three callers (a pure permutation), so SPARE capacity is untouched.

**`delete`/`delete-if`/`delete-if-not`/`nsubstitute`/`nsubstitute-if(-not)` are the OTHER side of the same bug**: these five had NO vector/string arm at all (only a cons splice/`rplaca` loop), so a vector or string argument was a SILENT NO-OP (`(delete 1 (vector 3 1 2))` answered `#(3 1 2)`). Each now routes through a RUNTIME check (`LispMacroExpander.deleteOrSubstituteDispatch`, `(or (stringp seq) (vectorp seq))`) to its `remove`/`substitute` family's vector/string handling, so a vector/string comes back a FRESH sequence (NOT identity-preserved — deliberately out of scope). On the interpreter this reaches THREE code paths per family: raw `env.defineFunction` closures (`Environment.removeValues`/`substituteValues`), `LispEvaluator.deleteIfValues`/`nsubstituteIfValues` (routed to `removeIfValues`/`substituteIfValues`), and each operator's `evalCons`/`compileCons` macro-expansion path for direct calls and `funcall`/`apply` — all had to move together or `(delete-if ...)` and `(funcall #'delete-if ...)` would answer differently.

**Re-evaluation trigger**: if a caller needs `delete`/`nsubstitute`-on-a-vector to be `eq` to its argument, the honest fix is in-place compaction (shift survivors down, pull the fill pointer back), which is what SBCL does.

Pinned by `LispEvaluatorTest.evalSortNreverseStableSortKeepFillPointerAdjustableAndIdentity` / `evalDeleteNsubstituteFamilyOnVectorsAndStrings`, `JvmLispCompilerTest`'s `compileAndRunSortNreverseStableSortKeepFillPointerAdjustableAndIdentity` / `compileAndRunDeleteAndNsubstituteFamilyOnVectorsAndStrings`, `WasmLispCompilerIntegrationTest`'s `sortNreverseStableSortKeepFillPointerAdjustableAndIdentity` / `deleteAndNsubstituteFamilyOnVectorsAndStrings`, and ci-spec `sort-nreverse-stable-sort-keep-fill-pointer-adjustable-and-identity` / `delete-and-nsubstitute-family-on-vectors-and-strings`.

## adjust-array
`(adjust-array array new-dims &key initial-element fill-pointer)` on every backend: elements are preserved at the subscripts valid in BOTH shapes (per-subscript, not flat — resizing a matrix keeps `(i, j)` at `(i, j)`); an `:adjustable` array is adjusted IN PLACE and returned itself (`eq`), otherwise a fresh array is returned; without an explicit `:fill-pointer` the old one carries over (make-array range-checks it against the new size, so shrinking below it errors like CL); rank mismatch signals; `:displaced-to` AS A KEYWORD to `adjust-array` is rejected, but a DISPLACED ARGUMENT is legal (it un-displaces first). Opened cells take the element type's zero and the result carries the argument's element type. An IMMUTABLE string is a legal argument everywhere; a PACKED vector is not.

Implementation split, chosen to keep the n-dimensional copy logic OUT of per-backend codegen:
- **Interpreter**: a real `Environment` built-in (`adjustArray` in `Environment.java`, runtime keyword parsing) over `LispArray.become(other)` (replaces dims/data/fillPointer in place, keeps the adjustable flag).
- **Compile path**: `LispMacroExpander.expandAdjustArray` — a Lisp-level expansion over existing primitives (`make-array` with the carried-over `:fill-pointer`/`:adjustable`, `array-dimensions`, `array-total-size`, two-arg `floor` for subscript decomposition, `row-major-aref` / `%row-major-aset`) plus `%array-become` per backend, `%array-default-element` for the fill and `%array-adopt-element-type` for the copy's declared type. JVM `_arrayBecome`: header dims/fp copy + ArrayList resize/copy; WASM: three inline `struct.set`s swapping the header's dims car, meta fp and data slot. Both compilers dispatch `ADJUST_ARRAY -> compileExpr(expandAdjustArray(cons))`.

### `adjust-array` on a displaced array un-displaces it first
`expandAdjustArray` calls `%array-undisplace` (a thin wire onto the un-displace machinery built for `vector-push-extend`'s growth) UNCONDITIONALLY — not only when `:adjustable` — so the answer is the same whichever branch (`%array-become` vs a fresh copy) the rest takes. The interpreter's `Environment.adjustArray` calls `array.undisplace()` at the same point; the `LispString` arm's `str.adjustCapacity` already called it, so only its own now-redundant `displacedTo() != null` refusal dropped.

**Ordering trap**: the call must be PART of `a`'s own `let*` binding (`(a (%array-undisplace <array-expr>))`), not a later body statement. Every other binding that reads `a` — `od` (`array-dimensions`), above all `newArr`'s `%array-adopt-element-type` stamp — must see the ALREADY-undisplaced state, because a still-displaced array's marker/offset word is genuinely ambiguous on the compile backends (the single word doubles as the offset while displaced and only becomes the resolved element-type marker after the undisplace); reading it one binding too early silently answers "remembers nothing". Placed as a body statement it crashed `compileAnAdjustedCopyKeepsTheElementType` with `ClassCastException: String cannot be cast to ArrayList`, because `%array-undisplace` runs on EVERY argument including a literal immutable string. Both `_arrayUndisplace` (JVM) and `WasmArrayCompiler.compileArrayUndisplace` now open with the same `instanceof`/`ref.test TYPE_STRING` check `_arrayDispTarget`/`compileDispTarget` had. A packed array needs no such guard: the JVM call site (`compileUnary`, shared with `compileDispTarget`/`compileDispOffset`) runs `emitRequireGeneralIfPacked` first (`JvmLispCompilerTest.compilePackedFloatArrayRejectsAdjustArray`); wasm traps on the cell cast (`WasmLispCompilerIntegrationTest.compileAdjustArrayTrapsOnAPackedFloatArray`).

A NON-adjustable displaced argument diverges from SBCL by the SAME pre-existing rule every other non-adjustable `adjust-array` argument does (SBCL treats a displaced array as not simple and adjusts in place regardless of `:adjustable`). CLHS leaves further use of the OLD array unspecified once it is not `:adjustable`, so the un-displace runs on it too.

Wiring for `%array-undisplace`: `LispNames.ARRAY_UNDISPLACE` (`%ARRAY-UNDISPLACE`), the `CL_INTERNALS` entry in `PackageRegistry`, the `usesGeneralArrayOp` gate list in `LispMacroExpander`, and a case in `Jvm`/`WasmExprCompiler.compileCons` calling `JvmArrayCompiler.compileArrayUndisplace` / `WasmArrayCompiler.compileArrayUndisplace`. No `Environment` registration: `adjust-array` is not expanded through `LispMacroExpander` on the interpreter, so the primitive is compile-path-only.

Pinned by `LispEvaluatorTest.adjustArrayUndisplacesADisplacedArgument`, the `compileAdjustArrayUndisplacesADisplacedArgument` twin in `JvmLispCompilerTest` and `WasmLispCompilerIntegrationTest`, and ci-spec `adjust-array-undisplaces-cross-backend` — beside the pre-existing `LispEvaluatorTest.aDisplacedViewCarriesItsOwnFillPointerAndAdjustableFlag` / `aFullDisplacedViewUndisplacesWhenItGrows`, their `compileADisplacedViewCarriesItsOwnFillPointerAndAdjustableFlag` / `compileAFullDisplacedViewUndisplacesWhenItGrows` twins, and ci-spec `displaced-fill-pointer-cross-backend`.

## Displacement (`:displaced-to`)
Lite semantics everywhere: a displaced array cannot be combined with `:initial-element`/`:initial-contents` (compile-time `UnsupportedOperationException` on JVM/WASM since make-array keywords are literal; runtime error on the interpreter) — the one combination CLHS forbids. `:displaced-index-offset` requires `:displaced-to`. The view is bounds-checked at creation (`total + offset <= target total`). Chains (view of view) resolve transitively, and access follows the CURRENT storage of each hop, so a view keeps aliasing an adjustable target after `vector-push-extend`/`adjust-array` grow it in place (`displacedArraySeesTheTargetGrowInPlace` / `compileDisplacedArrays` / ci-spec `adjust-displaced-arrays-cross-backend`). Rank may differ from the target's (vector view over a matrix row).

`array-displacement` returns target + offset as TWO values via the syntactic multiple-value tier: `isMvProducerForm`/`lowerMvProducer` recognize it and read `%array-disp-target` / `%array-disp-offset` over one temp; in an ordinary context `expandArrayDisplacement` yields the primary. No `%mv-spill` involvement.

### Displacing a STRING
`(make-array n :element-type 'character :displaced-to s :displaced-index-offset k)` over a STRING answers a **string view**: `stringp`, `length` n, the target's characters from k on, printing/`string=`/`subseq`/`char` seeing the slice, `array-displacement` reporting target and k — and NO copy. Views chain, each hop resolved at access time.

**The TARGET decides the shape, not `:element-type`.** The portable substring idiom (`cl-ppcre/util.lisp`'s `nsubseq`, and with it every `regex-replace` with a FUNCTION replacement and every `:sharedp t` entry point) passes the target's own `(array-element-type sequence)`, a RUNTIME value, so a rule keyed on the element type would not fire for the one caller that matters. Both compilers keep the `:displaced-to` branch AHEAD of the runtime-element-type lowering and decide the shape at run time inside the displacement helper. `eval/ClPpcreSharedSubseq`'s copying rewrite is retired and the verbatim definition runs on all four backends (`ClPpcreE2eTest`). Answering a COPY from `make-array` was explicitly not the fix — it would make every other library's displacement silently stop aliasing.

**Writing through a view reaches the target's storage where the backend has one.** The interpreter's strings are all mutable. On the compiled backends the mutable CHARACTER VECTOR is that storage, and a `copy-seq`/`subseq` result IS one (`.kb/string-write-runtime.md`), so a view over the common allocated-string case writes THROUGH on all four backends (`compileDisplacedStringViewOverACopySeqResultWritesThrough`). What remains immutable is a LITERAL (and `concatenate` / `string-upcase` / `format nil` results until their own flip): such a view is built without a copy and READS through, and the first write PROMOTES — the view's target slot is replaced by a character vector holding the same characters, the store lands there, the view is mutable from then on, `array-displacement` reports the promoted vector, and the original string value is untouched (exactly as `(setf (char s i) c)` re-binds rather than writes).

Per backend:
- **Interpreter**: `LispString` gained `displacedTo`/`displacedOffset`/`viewLength` beside the fill-pointer fields; `storage()`/`base()` walk the chain and every read/write (`value`, `charAt`, `setCharAt`, `capacity`, `length`, `replaceInPlace`) goes through them. A view has no fill pointer and is not adjustable, so `setFillPointer`/`vectorPushExtend`/`adjustCapacity` reject it. `Environment`'s `make-array` returns the view when `:displaced-to` is a `LispString` (rank-1, bounds-checked against the target's capacity), and `%array-disp-target`/`%array-disp-offset` accept a `LispString`.
- **JVM**: the header-LENGTH tag gained **7 = displaced string view** (`{dims, null, null, target, offsetLong, null, null}`), chosen by `_arrayMakeDisplaced` when the target is a `String` or an array whose own header is a character vector (4) or a string view (7); a String target is bounds-checked with `_scount`. `stringp`'s length-4 arm accepts 7 too, and `_strv` renders a 7-header by resolving the chain (a character-vector target element by element from the resolved base, a String target in ONE `substring` between two `_cpoff` translations). `emitResolveDisplacement` ends the walk on a non-ArrayList target with the offset folded in, so one test (`header.length > 4 && header[3] != null`) tells `_rmGet`/`_rmSet` they landed on a string: `_rmGet` reads `_cpoff` + `codePointAt` and boxes `int[]{cp}`, `_rmSet` promotes through `_strToCharVec` (in `METHOD_NAMES`, so it lives and dies with the array gate).
- **WASM**: no new heap type and no new `FUNC_*` index. A string view stores the TARGET STRING in the header's data slot (where an array view stores the target cell), which makes the shape self-describing. `WasmArrayRuntimeBuilder.emitResolve` leaves the final header in its cursor local and folds in this view's own offset when the data slot is a `TYPE_STRING`; `_arr_get` reads it with `_str_char_at` and boxes a `TYPE_CHAR`, `_arr_set` builds the promoted character-vector cell INLINE and `struct.set`s it into the `(meta . data)` cons. Offsets stay in CHARACTER units on both sides. `_charvec_p` answers true for a string data slot and recurses one hop for a cell one; `_charvec_to_str` reads the element through `_arr_get` when the data slot is not a buckets array; `%array-disp-target`/`%array-disp-offset` treat a string data slot as a target.

### A displaced view is not a BARE view
**Invariant: `make-array :displaced-to` accepts `:fill-pointer` and `:adjustable`, on all four backends, and the fill pointer is the VIEW's own.** CLHS forbids only `:initial-element` / `:initial-contents` beside `:displaced-to`; the other two are explicitly allowed, and "a growing view over a bigger backing store" is an ordinary CL idiom.

**Both header layouts already had the slots**: a JVM displaced header is `{dims, fp, adj, target, offsetLong}` (7 for a string view) with slots 1/2 simply written null, and a wasm header's meta chain is `(fp . (adj . offset))` with the same two null. The make-array half was one argument pair threaded through `_arrayMakeDisplaced` / `compileMakeDisplaced` (both reusing the existing fill-pointer resolution — JVM's extracted `emitResolveFillPointer`, wasm's shared `_arr_fp` — against the VIEW's own element count, never the target's), plus the interpreter's view constructors. No header length moved, no marker changed.

What DID need work, the three operations that reach the data:
- **`vector-push` / `vector-pop` write and read THROUGH.** Both used to touch the array's own storage directly (`ArrayList.set(1 + fp)` on the JVM, the header's data slot on wasm, `this.data[fp]` in `LispArray`), which a view does not have. They now go through the displacement-aware element primitives every `aref`/`aset` already used — JVM `_rmGet`/`_rmSet`, wasm's shared `_arr_get`/`_arr_set` (a CALL, which is why routing them through it made the wasm sites SMALLER), interpreter `readFlat`/`writeFlat`. A string view's push writes into the target string, promotion on an immutable target included.
- **A full view UN-DISPLACES when it grows.** `vector-push-extend` past the view's span copies the current contents into storage of its own and drops the displacement, so growth never runs off the end of someone else's array; `array-displacement` answers nil/0 from then on. That is SBCL 2.2.9's behavior. One implementation per backend: `LispArray.undisplace` / `LispString.undisplace`, JVM `_arrayUndisplace` (in `METHOD_NAMES`), wasm `_arr_undisplace` (`FUNC_ARR_UNDISPLACE`, appended after `FUNC_ARR_CHECK_RANK` so no index above shifts, reusing `TYPE_CALLABLE_BASE + 0`).
- **The shape and the element type survive the un-displacement.** The JVM's header LENGTH is the tag, so 7 becomes 4 and 5 becomes 3, or 5 again with the resolved element type in the freed OFFSET slot; wasm's meta OFFSET word doubles as the element-type marker, so the freed word becomes the chain end's own marker (copied VERBATIM). A grown string view is still `stringp`.

`_strv` (JVM) also learned the view's fill pointer: a length-7 header used to render its whole dimension, and the shared `emitActiveLength` now answers "fill pointer when present, else dims[0]" for the character-vector arm and the string view alike. `#'make-array`'s variadic wrapper carries the two keywords into its displaced branch.

Diffed against SBCL 2.2.9: every answer identical EXCEPT `adjustable-array-p` over a view (the recorded divergence above).

### Un-displacing keeps the VIEW's own element type
**Invariant: un-displacing never changes `array-element-type`, on all four backends, whichever operation reaches it.** An array's element type is fixed when it is made, and `adjust-array` answers an array of the SAME element type, so whatever a view answered while displaced is what it must answer once it owns its storage. (An earlier fix had wasm chain-resolving the target's type only at the un-displace, i.e. `adjust-array` CHANGING an element type; the two "broken" backends were the conforming ones.)

Character-ness travels regardless, because it is a REPRESENTATION fact rather than a remembered designator: a view over characters holds characters, stays a character vector, stays `stringp`, and answers `CHARACTER` on both sides. The JVM reads that off the view's OWN header length (7 -> 4).

SBCL is not a usable oracle for a mismatched view: it ENFORCES the element-type compatibility rontolisp's lite displacement does not check ("Can't displace an array of type T into another of type (UNSIGNED-BYTE 8)"). State the repro in the form SBCL accepts (the view spelling the SAME `:element-type` as its target) to get an oracle back.

### A displaced view's element type is its TARGET's
**Invariant: a `:displaced-to` view answers the element type of the array it is a view OF, resolved through the whole chain, on all four backends — and that is the view's own declared `:element-type` in every program a conforming implementation accepts.** Before this the keyword was parsed and dropped on the displaced arm, so a `(unsigned-byte 8)` view over a `(unsigned-byte 8)` target answered `T` where SBCL answers `(UNSIGNED-BYTE 8)`.

**Resolving beats recording.** A view owns NO storage: its elements are the target's. CL requires the two element types to be type-equivalent and SBCL ENFORCES it, so recording the declared type and resolving the target's are observationally identical on every program SBCL runs — they differ only where SBCL refuses to run. Resolving is also self-consistent with the TARGET deciding the SHAPE: a `character`-declared view over a general array is not `stringp` and should not claim `CHARACTER`. And resolving costs no representation at all (no per-array word: a JVM header slot the displaced header has no room for, a wasm meta cons every array would pay for).

**SBCL oracle trap**: a mismatched view whose value is only asked for its `array-element-type` is CONSTANT-FOLDED and the `make-array` deleted, so the error never fires and the test looks like it passed. Force the array to exist — read an element.

- **Interpreter**: the displaced `LispArray` constructor inherits `target.elementTypeCode` (was `ArrayElementTypes.T`). Inherited at BIRTH rather than resolved per read, because the type never changes and the target already resolved its own, so one hop IS the whole chain — and `undisplace()` then needs no special case. A `LispString` view is unaffected (`CHARACTER` by representation).
- **JVM**: `_arrayElementType` HOPS instead of answering `t` — `while (header.length > 4 && header[3] != null) o = header[3]` — then reads slot 4 as before. `_arrayUndisplace` walks the same chain before replacing the header and builds a length-5 `{dims, fp, adj, null, et}` (the freed OFFSET slot taking the resolved type) instead of a length-3 one when the chain remembered anything; 7 -> 4 for a string view is unchanged. No length TAG moved: 5-with-`header[3]`-null is the shape `_arrayMakeTyped` already builds.
- **wasm**: `emitRememberedElementType` opens with the same `block`/`loop` walk `emitResolve` uses (hop while the data slot `ref.test`s as `TYPE_CELL`) then reads the chain end's marker word; only a STRING chain end can still reach the `t` arm. `_arr_undisplace` copies the chain end's marker VERBATIM.

Cost: **+49 wasm per `array-element-type` SITE** (that backend emits the dispatch inline), **+23 or +148 per JVM PROGRAM** (+23 for the hop inside the shared `_arrayElementType`, +125 more only when `_arrayUndisplace` is also emitted). Both are constant in the number of ARRAYS, which a recorded word would not have been; ~0.03-0.16% on real programs. Making the wasm walk a shared function would save ~200 bytes on a 500 KB program at the cost of a new `FUNC_*` index in the component blobs — not worth it, and the sites are `array-element-type`'s, never `aref`'s.

**A second conformance gap closed itself**: the slots a `vector-push-extend` growth OPENS in an un-displaced view take the RESOLVED type's own zero, since `_arrayDefaultElement` / `emitDefaultElementForHeader` read the type the un-displace just recorded. A grown `(unsigned-byte 8)` view reads `0` past its old span where all four backends read `NIL` — SBCL's answer.

**Still NOT checked**: rontolisp does not enforce `:displaced-to`'s element-type compatibility, so a mismatched view is constructible and answers its target's type rather than its declared one — a difference that exists only in programs no conforming implementation runs.

Pinned by `LispEvaluatorTest.aDisplacedViewAnswersItsTargetsElementType` and `unDisplacingKeepsTheViewsOwnElementType`, the `compileADisplacedViewAnswersItsTargetsElementType` / `compileUnDisplacingKeepsTheViewsOwnElementType` twins in `JvmLispCompilerTest` and `WasmLispCompilerIntegrationTest`, and ci-spec `adjust-array-undisplaces-cross-backend`.

### A PACKED vector is a displacement target
**Invariant: `make-array :displaced-to` accepts a PACKED integer vector or packed float array as the target, on all four backends, and the view reads and writes that unboxed storage with the target representation's own element semantics.** This is the construction CLHS's `:displaced-to` element-type rule is WRITTEN for, and it was the one shape every backend refused (interpreter `MAKE-ARRAY expects an array`, JVM raw `ClassCastException: [J cannot be cast to ArrayList`, wasm bare `cast failure` — two HOST-level crashes on ordinary user input).

The premise that made this look expensive was stale: `emitResolveDataAndIndex` is no longer inline at every `aref`/`aset` site on wasm, having moved into the shared `_arr_get` / `_arr_set` bodies at FIXED indices, so the walk's third arm is a per-PROGRAM cost, not per-site.

What the view IS: an ordinary general-array view whose data slot holds the packed value. No new representation, no header-length or marker change.
- **Interpreter**: `LispArray.displacedTo` widened from `LispArray` to `LispVal` (a `LispArray`, `LispIntVector` or `LispFloatArray`; a view over a STRING is a `LispString` view). `readFlat`/`writeFlat` walk while the target is a `LispArray` and END on a packed one, reading with that representation's widening and writing with its masking/narrowing; the element type is inherited at birth from the target, packed widths mapping to their own `ArrayElementTypes` codes. `Environment`'s displaced arm bounds-checks against `LispIntVector.length()` / `LispFloatArray.totalSize()`.
- **JVM**: the same length-5 `{dims, fp, adj, target, offsetLong}` header with a `long[]` / `double[]` / `float[]` in slot 3, so nothing reading a header LENGTH moved. `emitResolveDisplacement` already stopped on a non-`ArrayList` target, so only the arm it hands off to learned the three packed shapes: `_rmGet`/`_rmSet` dispatch `long[]` (element at `[1 + flat]`, which the 1-based index already IS), `double[]`/`float[]` (`[1 + rank + flat]`) and only then the String. `_arrayMakeDisplaced` sizes a packed target from its own length, `_arrayElementType` answers a packed hop's representation, and `_arrayUndisplace` records that answer in the freed offset slot through one shared `emitPackedElementTypeInto` — the shapes `_ivElementType` / `_fvElementType` answer and `_arrayDefaultElement` reads back. The float store goes through the shared `_dbl` coercion.
- **wasm**: `emitResolve`'s trailing "fold in this view's own offset" test became "the data slot is not the buckets array" (one byte, now covering the packed end as well as the string end). `_arr_get` gained a packed read arm; `_arr_set` a packed WRITE arm that answers the value AS STORED by calling `_arr_get` back on the ORIGINAL index (kept in a local before the walk folds it) rather than carrying a second copy of the read — 118 bytes of every array program. `emitTargetDimsProduct` sizes a packed target (`array.len` for an integer vector, the dims product for an farray), `emitRememberedElementType` answers for a packed chain end, `_arr_undisplace` records that marker, and `emitDataSlotIsTarget` became the same "not buckets" test (which made it SMALLER). The array printer's element read falls back to `_arr_get` when the chain ended on a packed target. `--simd` travels: the farray arms take the vblock `_v_get`/`_v_set` path, so `buildArrGetBody`/`buildArrSetBody`/`buildArrUndisplaceBody` take the flag.

Cost: **+382 wasm / +392 class per array-using PROGRAM**; +0 per `array-element-type` site (the packed arm sits inside `emitRememberedElementType`'s existing `typedArrayCodes != 0` guard); +86 wasm per `make-array :displaced-to` site; +84 class for the first `:displaced-to` in a program. ~0.1-0.2% on real programs. **Bought by every array program, including one that never displaces.**

**Two deliberate divergences from SBCL, both pre-existing and this surface's own rule**: a store of an out-of-range integer through the view MASKS to the element width where SBCL signals a type error (`.kb/packed-integer-vectors.md`), and rontolisp still does not enforce `:displaced-to` element-type compatibility.

**Unpinned edge**: the VALUE a store THROUGH a view answers differs at all three packed float widths and at `(unsigned-byte 8)` — the interpreter answers the value as given (`(setf (aref view 0) 0.1)` is `0.1` over a `single-float` target, `300` over `(unsigned-byte 8)`), the JVM the value as stored (`0.10000000149011612`, `44`), which is what a store straight into the target answers on BOTH. The element that lands is the same everywhere; only the store form's own value diverges. Keep it out of ci-spec and the parity tests until someone needs it aligned; aligning means changing the interpreter's `LispArray` displaced store.

Pinned by `LispEvaluatorTest.aPackedVectorCanBeADisplacementTarget` / `aViewOverAPackedTargetUndisplacesWhenItGrows`, the `compileAPackedVectorCanBeADisplacementTarget` / `compileAViewOverAPackedTargetUndisplacesWhenItGrows` twins in `JvmLispCompilerTest` and `WasmLispCompilerIntegrationTest`, and three legs of ci-spec `adjust-displaced-arrays-cross-backend`.

#### The packed-displacement arms' 382-byte tax: measured, NOT gated
A program-level gate ("can this program build a packed vector" AND/OR "does it call `make-array` with `:displaced-to`") would skip the packed arms in `_arr_get`/`_arr_set`/`_arr_undisplace`. **Measured and NOT implemented.** All three tracked real programs (zlib+chipz, cl-ppcre, jzon+deps) would fully qualify — zlib builds a packed `(unsigned-byte 8)` buffer but never displaces; cl-ppcre displaces (`nsubseq`) but only onto STRINGS and can build no packed vector at all (its `make-array`s are `'fixnum`/`'character`/`'(or null fixnum)`, none packed per `JvmArrayCompiler.packedIntElementWidth`/`isSingleFloatElementType`/`isDoubleFloatElementType`); jzon builds packed octets via flexi-streams but never displaces (its `(unsigned-byte 64)`/`(signed-byte 64)` tables are outside `packedIntElementWidth`'s 8/16/32 unsigned range). **The ceiling is exactly the fixed per-program constant, 382/392 bytes, regardless of program size.**

Why not built: a false negative does not fail to compile — the packed arm is simply absent and a program that reaches it anyway traps at RUN TIME (`ref.cast` on wasm, `ClassCastException` on the JVM) after looking correct at every compile step. Provably-safe whole-source-tree analysis is higher than it looks:
- **The JVM's analogous gate (`programUsesIntArray`/`programUsesFloatArray`, `JvmLispCompiler.java`) is NOT a pure AST walk.** `read-sequence`/`write-sequence` over a typed sequence injects an internal `%seq-int-vector` wrapper that allocates a packed vector WITHOUT appearing in the scanned program, so the gate ORs in `usesSeqIntVector` by hand; a fetched HTTP reply's `:body` and a served request's `:raw-body` are packed octet vectors the RUNTIME builds, so it ORs in `usesFetch`/`usesHttpHandler` too. A displacement gate needs the same audit independently — and the wasm backend, where the 382 bytes live, does not reuse the JVM's hand list (its `typedArrayCodes` gate, `LispMacroExpander.makeArrayElementTypeCodes`, is a bare AST walk with none of the three ORed in — an existing gap).
- **A first-class reference to `make-array` can carry `:displaced-to` without the keyword appearing where either scan looks.** `BuiltinFunctionWrappers.variadicMakeArray()` synthesizes a wrapper body that re-embeds a literal `(make-array dims :displaced-to (getf kw :displaced-to) ...)`, so a scan of the FULLY INJECTED program would catch it — provided wrapper injection happens before the scan and the wrapper is emitted into what the scan reads. That mechanism is JVM-only today (`grep -l BuiltinFunctionWrappers src/main/java/am/ik/rontolisp/codegen/wasm/*.java` is empty).

Both gaps would need closing and KEEPING closed as the wasm backend grows new ways to build a packed array or a displaced view, for a payoff capped at 382/392 bytes.

## Representation
### Interpreter (`LispArray`)
Mutable state (fields no longer `final`):
- `int fillPointer` — the fill pointer, or `-1` for none; when present it is the effective length, rank-1 only.
- `boolean adjustable` — the `:adjustable` flag, verbatim.
- `data` / `dimensions` non-final so `vector-push-extend` can reallocate.

Key methods: `effectiveLength()` (fill pointer if present, else `data.length`), `vectorPush` (returns the index or `-1` when full), `vectorPop`, `vectorPushExtend` (grows `data` + `dimensions[0]` when full), `setFillPointer`. `render()` (the `#(...)` printer) iterates `effectiveLength()`; `length` (in `Environment`) uses it too.

Displacement: `displacedTo` (a `LispVal` or null) + `displacedOffset`, both NON-final (`undisplace()` clears them in place); a displaced array's `data` is a shared empty array and all element access goes through `readFlat`/`writeFlat`, which walk the chain adding each hop's offset (the chain holds the OBJECT, not the storage, so target growth is followed). `totalSize()` (dims product) replaced `data.length` in every bounds check; `effectiveLength()` = fp or `totalSize()`. `become(other)` replaces dims/data/fillPointer in place.

`make-array` parses `:fill-pointer` (`t` = size, integer = that value, `nil` = none; rank-1 only), `:adjustable`, and ignores unknown keywords. New builtins live in `Environment.registerArrays`.

### JVM
An array is a `java.util.ArrayList` whose slot 0 holds a header `Object[]{dims, fillPointer, adjustable}` — `dims` the `Object[]` of Long dimension sizes (length = rank), `fillPointer` a `Long` or null, `adjustable` the RAW argument (null = nil, so `_adjustableArrayP` is a null test). Slot 4 may carry the REMEMBERED element type (`_arrayMakeTyped`, read by `_arrayElementType`); it is free on every non-displaced array because slot 3 — the displacement target — says whether it holds an offset instead, so the ordinary header grows to length 5 and no length TAG moved (`.kb/array-literals.md`). Data stays at slots `1..` (the `1 + flat` offset in `_aref*`/`_aset*` is untouched); every dims reader gained one extra `aaload 0` (`emitFlat2`, `emitFlatN`, `_arrayDims`, `buildToString`, `JvmLengthRuntimeBuilder`). Both header producers build the wrapper: `_arrayMake` (signature grew to `(dims, init, fillPointer, adjustable)`; `JvmArrayCompiler.compileMake` compiles the keyword value expressions or pushes null) and `JvmQuoteCompiler.compileQuotedArray` (literals: slots 1/2 null). `buildToString` + `_length` clamp the element count to the fill pointer.

**Header LENGTH is the tag**: 3 = ordinary boxed, 4 = character vector, 5 = displaced OR ordinary boxed WITH a remembered element type (told apart by slot 3), **6 = packed** (slot 4 free for the remembered type, so packing survives it), 7 = displaced STRING VIEW.

**A PLAIN general array starts PACKED.** When `_arrayMake` sees no fill pointer, no adjustability and an initial element that is nil or an in-range integer (a runtime decision, so `#'make-array`'s wrapper and `adjust-array`'s temp allocation take it too), the ArrayList holds ONLY a LENGTH-6 header `Object[]{dims, null, null, null, null, long[] data}` and the row-major elements live unboxed in the `long[]`, with `Long.MIN_VALUE` as the nil sentinel (storing that integer widens instead, so it stays representable). A random `aref` into a large general integer vector is then ONE probe into one flat primitive array instead of a dependent pointer chase (1.7 -> 55.5 ns/access from 10^3 to 10^6 elements before; ~3 -> ~12 ns now, SBCL-like).
- `emitResolveDisplacement`'s loop already ends on the null `header[3]`, so a packed header never reads as a displacement, and `_strv`/`stringp`'s `length == 4` test never sees it as a character vector. `_arrayDispOffset` gained a `header[3] != null` test (length > 4 alone would have answered null instead of 0 for a packed array).
- `_rmGet`/`_rmSet` — the single data-access primitives every accessor and the printer funnel through — branch on the tag AFTER the displacement walk (the header is already in a local, so the ordinary path pays one `arraylength` compare): packed reads `data[idx-1]` (sentinel -> nil), packed stores write an in-range `Long` unboxed.
- The first store that cannot pack (a non-integer, or the sentinel integer) calls **`_arrayWiden`**: the header becomes a length-5 `{dims, null, null, null, et}` (slot 4 carried over) and every `long[]` element is appended boxed (sentinel as null). The ArrayList object IS the array's identity, so every alias sees the widened array — widening is invisible, one O(n) copy, once. `_arrayBecome(a, b)` widens both operands up front (its element copy is `size()`-based) and `_charVecMake` widens before stamping the length-4 marker.
- Two non-helper consumers of the representation must move with any change to what the tag means: `JavaBridgeTemplate.marshal` (the `java:` interop sequence bridge) has its own packed branch, and `JvmIntFusionCompiler`'s aref leaf re-tests the same tag — ArrayList, `size() != 0`, `get(0) instanceof Object[]`, `length == 6` — bailing into `_aref1` otherwise (`.kb/jvm-int-fusion.md`).
- The fill-pointer surface never meets a packed array (packing requires fp == null, and those helpers error on a missing fill pointer first). The packed INT vectors' `long[]{width, ...}` values are disjoint — the array VALUE here is the ArrayList, so `instanceof long[]` is false and the iv -> fv -> general dispatch chains are untouched.
- Pinned by `JvmLispCompilerTest.compilePackedGeneralArrayWidensInvisiblyOnANonIntegerStore` / `compilePackedGeneralArrayNilAndSentinelInteger` / `compilePackedGeneralArrayRankNAndDisplacedView` plus the whole fill-pointer/adjust/displaced/copy-array set. The interpreter and both WASM backends keep their boxed general representation (the wasm general `aref`'s cost is size-INdependent dispatch, a different defect).

A DISPLACED array carries a 5-element header `Object[]{dims, fp, adj, target, offsetLong}` (7 for a string target; slots 1/2 null unless the view was given `:fill-pointer`/`:adjustable`) and holds NO data slots (`_arrayMakeDisplaced(dims, target, offset)`, bounds-checked against the target's dims product). Every data access funnels through `_rmGet(list, idx1based)` / `_rmSet(...)`: a loop `while header.length > 3 && header[3] != null { idx += header[4]; list = header[3] }` then `get/set(1+flat)`. `_aref1/2/N`, `_aset1/2/N` and `buildToString`'s element read end in `invokestatic _rmGet/_rmSet` (the builders take the generated class's `selfClass` for the methodref); `buildToString`'s no-fp element count and `_length`'s no-fp fallback use the dims product / `dims[0]` rather than `size() - 1`.

Static helpers in `JvmArrayRuntimeBuilder` (same array gate): `_fillPointer`, `_setFillPointer`, `_arrayHasFillPointer`, `_adjustableArrayP`, `_vectorPush`, `_vectorPop`, `_vectorPushExtend`, `_rmGet`, `_rmSet`, `_arrayMakeDisplaced`, `_arrayBecome`, `_arrayDispTarget`, `_arrayDispOffset`. Call sites are wired in `JvmArrayCompiler` + `JvmExprCompiler.compileCons`; `--optimize` (`JvmClassShaker`) keeps used helpers via the ordinary invokestatic call graph.

### WASM
The `TYPE_CELL` box holds a header `TYPE_CONS` of `(dims . (meta . data))`: `dims`/`data` are `TYPE_HASH_BUCKETS` arrays; `meta` is `(fillPointer-i31-or-null . (adjustableRaw . offset-i31))` (offset 0 for an ordinary array, 1 for the character-vector marker). The header's CAR is still the dims buckets array, so the array-vs-hash-table discriminator used by `%arrayp` / `WasmLengthCompiler` / the printer is unchanged, and `compileDims`/`emitFlatIndex` needed no change. Producers: `compileMake` (resolves `:fill-pointer` at runtime — null / bounds-checked i31 / `t` -> dims[0] — only when the keyword appears at the call site) and `WasmQuoteCompiler.compileQuotedArray` (meta `(null . (null . 0))`).

A DISPLACED array stores the TARGET CELL in the data slot and its offset in the meta chain (`compileMakeDisplaced`; bounds-checked against the target's dims product, traps when too small). Every data access site (`compileAref`/`compileAset`/`compileRowMajorAref`/`compileRowMajorAset`) runs the `emitResolve` walk: while the data slot `ref.test`s as `TYPE_CELL`, add the meta offset to the flat index and hop to the target's header. Because the walk re-reads each hop's CURRENT header, a view keeps aliasing a target grown in place. The printer (`WasmRuntimeBuilder.emitPrintArray`) gained the same walk (one extra i32 local, `baseSlot`, in `buildPrintValBody`/`buildPrincValBody`) and its no-fp element count uses the dims product; `WasmLengthCompiler` already used `dims[0]`. `compileAdjustableArrayP` reads `meta.cdr.car`; `%array-become` is three inline `struct.set`s; `%array-disp-target`/`%array-disp-offset` read the data slot and `meta.cdr.cdr`. The vector-push family DOES see displacement (a view may carry a fill pointer): its element access is `_arr_get`/`_arr_set` and its growth calls `_arr_undisplace` first.

The builtins are emitted INLINE in `WasmArrayCompiler` (`compileFillPointer`/`SetFillPointer`/`HasFillPointer`/`AdjustableArrayP`/`VectorPush`/`VectorPop`/`VectorPushExtend`/`ArrayBecome`/`DispTarget`/`DispOffset`; push-extend copies into a fresh buckets array with a loop and `struct.set`s the inner cons + dims[0]) — no new heap type, no new `FUNC_*` index, so the component blobs are untouched and Preview 1 / `--component` stay identical.

### `--no-gc` scalar WASM
Unsupported, like every array operation: the eligibility scan (`NoGcWasmCompiler.collectCallsCons`) names the operation in a clear compile error. Documented under the `--no-gc` section of `doc/*/compiling/wasm.md`.

## Wiring points (adjust-array / displacement)
`LispNames`: `ADJUST_ARRAY`, `ARRAY_DISPLACEMENT`, `ARRAY_BECOME` (`%array-become`), `ARRAY_DEFAULT_ELEMENT` (`%array-default-element`), `ARRAY_DISP_TARGET`/`ARRAY_DISP_OFFSET`, `DISPLACED_TO_KEYWORD`, `DISPLACED_INDEX_OFFSET_KEYWORD`. `PackageRegistry`: the two public names in `CL_FUNCTIONS`, the four `%`-names in `CL_INTERNALS`.
