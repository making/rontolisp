# Fill-pointer / adjustable / displaced arrays (`copy-array` surface)

The extended-array surface cl-utilities' `copy-array` touches — `make-array`'s `:fill-pointer` / `:adjustable` / `:displaced-to` / `:displaced-index-offset`, `fill-pointer` (+ `setf`), `array-has-fill-pointer-p`, `adjustable-array-p`, `array-element-type`, `vector-push` / `vector-pop` / `vector-push-extend`, `adjust-array`, `array-displacement`, `copy-array` — DONE and behaviourally identical on all four backends. `--no-gc` rejects all of it (`NoGcWasmCompiler.collectCallsCons`; `doc/*/compiling/wasm.md`).

## Shared semantics
- Only rank-1 arrays may have a fill pointer (`:fill-pointer t` = size, integer = that value, range-checked). It is the effective length (`length`, `#(...)` printing, the sequence view), while `aref` / `row-major-aref` reach the FULL backing store, strings included (`Environment.charRef` and `%schar-set` bound by `capacity()`).
- `vector-push-extend` grows any fill-pointer vector regardless of `:adjustable`; the flag is reported VERBATIM by `adjustable-array-p`, so a displaced view diverges from SBCL (which answers `T` for any non-simple array). Both conforming.
- `array-element-type` returns the type the array REMEMBERS being asked for; a displaced view's is its TARGET's. On the compile path it expands to the LITE `(if (stringp x) 'character t)` (`expandArrayElementType`) unless `usesFloatArray || usesIntArray || usesTypedArray`, when it routes to `compileElementType`.
- `%set-fill-pointer` is the internal `setf` target, wired in `expandSetf`. Interpreter/JVM errors carry `fn: message` text; WASM traps.
- First-class values go through `BuiltinFunctionWrappers.ARRAY_FILL_POINTER_FUNCTIONS`, gated like `HASH_FUNCTIONS` on `programUsesAnyArrayOp`. `#'make-array` is a variadic wrapper (`variadicMakeArray`) re-extracting keywords with `getf`; its `:element-type` is accepted and IGNORED — what makes cl-utilities' `apply #'make-array` work, and why it builds an unmarked vector for a character request.
- **Trap: `char`/`schar` PAST the fill pointer are three-way divergent** and deliberately uncovered by ci-spec — interpreter returns the slot, JVM throws a raw `String.offsetByCodePoints` exception, both WASM return `#\Nul` (no bounds check at all; writing past the end silently APPENDS).

## Strings as arrays
`make-array :element-type 'character` builds a mutable string everywhere and the whole fill-pointer surface runs on it unchanged. The marker survives `adjust-array` because become mutates the header in place: interpreter a mutable `LispString`; JVM a **length-4** header `Object[]{dims, fp, adj, null}` (`_charVecMake`), displacement being `header.length > 4`; WASM **meta offset i31 == 1** (ordinary 0).

- **Mutability is the MARKER's, not the fill pointer's**: no `:fill-pointer` leaves that slot NIL everywhere and `setf char`/`setf aref` still write every slot. The JVM used to default it to the capacity, so `(array-has-fill-pointer-p (make-string 3))` answered `T` there alone and could not be told from a `:fill-pointer`-built one — what `simple-string-p` asks (`.kb/declarations-type-checks.md`).
- **A plain `(make-string n)` IS a character vector**: `expandMakeString` lowers to `(make-array n :element-type 'character :initial-element c)`, and `make-sequence` reaches it via `expandMakeSequence`. **Trap it fixes**: the old lowering built an IMMUTABLE string, making the `(%arrayp seq)` test in `expandReplace` / `expandScharSetFunctional` false, so `(replace buf x)` took the FUNCTIONAL branch and had its result discarded in statement position — s-sql's `strcat` sent PostgreSQL a BLANK string, silently. If `make-string` ever builds anything else, that whole "allocate a buffer, write into it" class regresses (`PostmodernE2eTest`).
- Hence `Ctx.usesArrays` = `programUsesAnyArrayOp(program) || usesFloatArray || usesIntArray` (plus the forced-group term below), with `MAKE-STRING` and `MAKE-SEQUENCE` listed alongside `MAKE-ARRAY` since they lower to it during `compileExpr`, AFTER the scan.
- `eq`/`eql` on a make-string result answers content on interpreter and JVM, identity on WASM; unspecified in CL, deliberately uncovered.

**Normalization into the immutable runtime string** is on demand: JVM `_strv(Object)` (gated on `Ctx.usesArrays`); WASM `_charvec_to_str`, always emitted right after `FUNC_WRITE_STR_GC` (`FUNC_VEC_BASE`/`FUNC_USER_BASE` shifted by one, capture-aware scratch). Insert points: (subseq, string=/-equal, case/trim/concat, write-string, string designator, read-from-string, make-string-input-stream, intern, make-symbol) plus the shared runtime bodies (`_lispToString`, `_eqv`, `_equal`, `_hash`, `_print_val`, `_princ_val`) — NOT char/schar/elt, which read the ELEMENT (`.kb/string-index-cost.md`).

**A PREDICATE does not normalize**: the shape decision is `_charvec_p` (`FUNC_CHARVEC_P`, `WasmStringRuntimeBuilder.buildCharvecPBody`, right after `FUNC_CHARVEC_TO_STR`) — the eight `ref.test`s to the marker and nothing else. `stringp` calls only that and `_charvec_to_str` opens with it, so the marker invariant has ONE owner. **Unfinished**: other callers and `_strv` still re-render per call; caching would need every write to a MUTABLE character vector to invalidate.

**String mutation flows through shared expansions.** `expandReplace`, `expandFill` and `expandScharSetFunctional` branch at runtime on `(%arrayp seq)`: a vector (char vector included) is written in place via `%row-major-aset` + `elt`, an immutable string keeps the functional rebuild whose setf form still requires a variable place. The interpreter writes a string in place through `LispString.setCharAt`, a compile-path-only deviation. `lowerCharacterInitialContentsMakeArray` lowers rank-1 character `:initial-contents` to a fresh string copy BEFORE the general lowering; default `:initial-element` `#\Space`.

ONE exception: a string LITERAL is never written in place on any backend, `%schar-set` included (`.kb/string-write-runtime.md`). **Unfinished: `replace` / `fill` / `nstring-*` do not honour that and still corrupt a literal on the interpreter** (`nstring-*` are prelude Lisp over `%nstring-replace`; the RETURN value is correct on all four either way).

### Array-info readers accept every string representation
`array-dimensions`, `array-rank`, `array-total-size`, `array-dimension`, `array-row-major-index`, `array-has-fill-pointer-p` and `adjustable-array-p` accept the header-less string, the mutable character vector and the displaced string view everywhere. The shape readers and the row-major index lower through `array-dimensions` (`expandArrayRank` and friends), so ONE string arm per backend carries them (`_arrayDims`'s `instanceof String` arm, AHEAD of the `ArrayList` header cast; `compileDims`'s `ref.test TYPE_STRING`), and the predicates guard the header read with `emitHeaderSlotToBool` so a headerless string is nil, not a cast trap. The dimension is the **CAPACITY**, never `length`.

### A COMPUTED `:element-type`
A designator in a variable or from a call (`(stream-element-type s)`) used to fall through to the general array, and with `stringp` false a `read-sequence` into it read BYTES from a character stream. `lowerRuntimeElementTypeMakeArray` (tried BEFORE the `:initial-contents` lowerings) turns such a call into a runtime `member` dispatch: character designators pick the character allocation, anything else the general one. "Literal" means a `(quote ...)` form, the unquoted `(unsigned-byte 8)` shape, or a symbol in `LITERAL_ELEMENT_TYPE_NAMES`.

## The JVM array gate is a CONSEQUENCE, not a prediction
**Invariant: on the JVM the array runtime is emitted whenever the emitted bytecode calls it, no matter which lowering introduced the call.** A source-name scan alone cannot be right — several lowerings introduce an array primitive only during `compileExpr`, AFTER the scan, and method resolution is lazy, so the class verified and then threw `NoSuchMethodError` the first time the branch ran. The scan still decides `Ctx.usesArrays`, which changes CODE and not just emission, so it must be known before any body compiles; `JvmClassShaker.unresolvedSelfMethods` then reports own-class methods called but not declared, and a name matching a per-group roster (`JvmArrayRuntimeBuilder.METHOD_NAMES`, `JvmHashRuntimeBuilder.METHOD_NAMES`, the eval runtime's four + `_lookup`) RE-RUNS `compile` with that group forced on — each retry strictly grows the forced set, anything unmatched failing loudly. The hand-written rosters are pinned both directions by `JvmRuntimeGroupNamesTest`.

**Each lowering that dispatches over the sequence representations takes an `arraysExist` flag and drops the array arm when false** (interpreter and both WASM pass `true`; JVM passes `Ctx.usesArrays`) — that is what let the shaker check cover EVERY caller, injected wrappers included:

| lowering (`LispMacroExpander`) | what the flag drops |
| --- | --- |
| `expandCoerce` | the vector scan behind `'list` / `'string` (`coerceVectorToList`) |
| `expandElt` | the `aref` arm of the string/list/array dispatch |
| `expandMap` | the same `aref` arm in the per-element read |
| `seqResultDispatchForm` (private; `wrapSortForStringSeq`, `expandReverse`, `expandRemoveDuplicates`, `expandRemove(-If)(-Not)`, `expandSubstitute` forward it) | the `__seq_vec` binding and the `(coerce __seq_res 'vector)` rebuild |
| `expandSubseqCompat` | the whole rewrite (returns `null`; the compiler emits its plain `%subseq-core`) |
| `expandReplace` | the destructive `%row-major-aset` loop |
| `expandVectorp` | the whole ARRAY arm — it reads `array-dimensions`, and `vectorp`'s injected wrapper is in EVERY program until the shaker runs, so an ungated read put `_arrayDims` in `(print 1)` |

**The array-gated wrapper set is complete**: ten wrapper bodies (`fill`, `coerce`, `vector`, `read-sequence`, `write-sequence`, `svref`, `array-rank`, `array-dimension`, `array-total-size`, `array-row-major-index`) called the array runtime UNCONDITIONALLY and now reference-gate wrapper and runtime on the same fact (`.kb/eval-runtime.md`), all ten joining `ARRAY_FILL_POINTER_FUNCTIONS` and the three new ones also `usesGeneralArrayOp` + wasm's `programUsesAnyArrayOp`, so the two scans cannot drift. `expandClassDesignator` takes the same flag, `hashTablesExist`.

**`(setf (elt s i) v)` is the worked example**: `expandSetf`'s `ELT` branch yielded `(%aset seq i v)` for everything non-`consp`, so a STRING target reached `%aset` — `NoSuchMethodError` on the JVM, `cast failure` on both WASM, only the interpreter right. It now carries the three-way dispatch `(setf (aref s i) v)` has (`consp` -> `rplaca`, `stringp` -> the `schar-set` rebuild, else `%aset`), only a VARIABLE place taking the string arm, which is a CALL (`%schar-set-runtime`). The `_top$N` chunk budget dropped 40000 -> 24000 for it and is now stale.

## The growth policy of `vector-push-extend`
The capacity a full vector grows to is OBSERVABLE (`array-dimension` reads it back), so it is ONE policy for all four backends even though CLHS leaves the default extension implementation-dependent. Stated once, in `am.ik.rontolisp.ArrayGrowth` (SBCL 2.2.9's numbers): a SUPPLIED `extension` is added verbatim (`cap + ext`); with none the capacity DOUBLES (`GROWTH_FACTOR`) off a floor of `MIN_CAPACITY` = 1; `NO_EXTENSION` = 0 is the "not supplied" sentinel so ONE entry point serves both arities.

Generated code cannot call `ArrayGrowth`, so both compile paths EMIT the same arithmetic inline against its constants (`_vectorPushExtend`, whose `ext` is the sentinel when no third argument was given; `compileVectorPushExtend` + `emitDefaultGrownCapacity`). Growing by one per push makes a push loop quadratic, and the older `fill-pointer-arrays-cross-backend` case never reads a dimension after a growth run, which is why that divergence went unnoticed.

## A slot the growth OPENS holds the element type's zero
**Invariant: an array slot nobody wrote holds its array's remembered element type's own zero, on all four backends, no matter WHICH operation opened it — `make-array`, `vector-push-extend`'s growth, or `adjust-array`.** Those slots are below the DIMENSION, so `aref` may read them even above the fill pointer; opened with a RAW NULL they crashed a grown CHARACTER vector and read `NIL` out of an adjusted `double-float` vector.

ONE answer per element type (`ArrayElementTypes.defaultElement`), asked of the ARRAY rather than a literal designator — `%array-default-element` (`Environment.arrayDefaultElement`; JVM `_arrayDefaultElement`, reading the SAME header facts `_arrayElementType` reads IN THE SAME ORDER; wasm `emitDefaultElementForHeader` off the meta MARKER word, marker 1 checked ALWAYS since no `:element-type` scan can predict it, markers 2..7 gated on `Ctx.typedArrayCodes`). `expandAdjustArray` always spells `:initial-element`.

**The character fill is `#\Space`, not SBCL's `#\Nul`** (`.kb/array-literals.md`); the general (`t`) vector keeps `NIL` where SBCL answers `0`, deliberate. ci-spec `opened-slot-fill-cross-backend`.

## The adjusted COPY remembers the element type
**Invariant: `adjust-array` never changes an array's element type. An `:adjustable` array keeps its own identity and with it its type; a NON-adjustable one answers a FRESH array STAMPED with the adjusted array's type.** The stamp COPIES the type word rather than re-deriving the representation (a runtime `:element-type` designator would turn one allocation into the seven-arm dispatch and make `Ctx.typedArrayCodes` count every `adjust-array` program as every specialized width): `%array-adopt-element-type (new old)` moves one word. `LispArray.adoptElementType` is the one writer of `elementTypeCode`; JVM `_arrayAdoptElementType` writes the length-4 marker for a RANK-1 character type and header slot 4 otherwise, leaving an already-character-vector or displaced `dst` alone; wasm copies the meta MARKER word in one `struct.set`.

**An IMMUTABLE string is a legal `adjust-array` argument on the compile paths**; **a PACKED vector is still not** — interpreter and JVM signal `adjust-array: not applicable to a packed integer vector` / `... packed float array` (`_ivRequireGeneral` / `_fvRequireGeneral` via `emitRequireGeneralIfPacked`; a program with no packed float array emits no `_fvRequireGeneral`, so the default build stays byte-identical), while wasm has no custom trap-message channel for EITHER and traps `cast failure`.

## `sort`/`nreverse`/`stable-sort` keep a vector's fill pointer and identity
**Invariant: `sort`, `nreverse` and `stable-sort` permute a fill-pointered or adjustable vector/string IN PLACE — same object, fill pointer, adjustable flag and total size — on all four backends, matching SBCL.** `seqResultDispatchForm`'s vector/string arm used to answer a FRESH SIMPLE rebuild, so `(fill-pointer (sort v #'<))` signalled `array has no fill pointer` (via `practicals-1.0.3/Chapter27/database.lisp`).

- A second flag, `destructive`, on `seqResultDispatchForm`, private to the three permuting callers (`wrapSortForStringSeq`, `wrapNreverseForStringSeq`, `expandStableSort`). `false` (`expandReduce`, `expandRemoveDuplicates`, `expandRemove`, `expandRemoveIf(-Not)`, `expandSubstituteIf`) is unchanged: non-destructive by CLHS and NOT to be made identity-preserving.
- **The destructive rebuild is `(replace __seq_in <fresh-rebuild>)` — answering THAT CALL's result, not `__seq_in` forced**: for a vector `replace` returns its target, but for a STRING literal its string arm copies and answers the COPY, so `(progn (replace __seq_in <rebuild>) __seq_in)` answers the UNSORTED literal.
- The INTERPRETER takes a separate path, `Environment.seqResultDestructive`, since its native operators never routed through the expander's dispatch: it writes the three representations in place directly, takes the same `sourceLiteral()` -> `copyForBulkWrite()` branch, and does NOT touch the backing store beyond the active length.

**`delete` / `delete-if(-not)` / `nsubstitute` / `nsubstitute-if(-not)` are the OTHER side of the same bug**: these five had NO vector/string arm, so such an argument was a SILENT NO-OP (`(delete 1 (vector 3 1 2))` answered `#(3 1 2)`). Each now routes through a RUNTIME check (`deleteOrSubstituteDispatch`, `(or (stringp seq) (vectorp seq))`) into the `remove`/`substitute` family, so a vector/string comes back FRESH, not identity-preserved. On the interpreter THREE code paths per family had to move together (`Environment.removeValues`/`substituteValues`, `LispEvaluator.deleteIfValues`/`nsubstituteIfValues`, the `evalCons`/`compileCons` expansion path). **Unfinished**: `eq`-preserving `delete`/`nsubstitute` on a vector needs in-place compaction.

## adjust-array
`(adjust-array array new-dims &key initial-element fill-pointer)` on every backend: elements preserved at the subscripts valid in BOTH shapes (per-subscript, not flat); an `:adjustable` array is adjusted IN PLACE and returned itself (`eq`), otherwise a fresh array; without an explicit `:fill-pointer` the old one carries over (range-checked, so shrinking below it errors like CL); rank mismatch signals; `:displaced-to` AS A KEYWORD is rejected, a DISPLACED ARGUMENT is legal.

The n-dimensional copy logic stays OUT of per-backend codegen: interpreter an `Environment` built-in (`adjustArray`) over `LispArray.become(other)`; compile path `expandAdjustArray` over existing primitives plus `%array-become` (JVM `_arrayBecome`; WASM three `struct.set`s), `%array-default-element` and `%array-adopt-element-type`. `%array-undisplace` is called UNCONDITIONALLY, not only when `:adjustable`.

**Ordering trap**: that call must be PART of `a`'s own `let*` binding (`(a (%array-undisplace <array-expr>))`), not a later body statement. Every binding that reads `a` — `od` (`array-dimensions`), above all `newArr`'s `%array-adopt-element-type` stamp — must see the ALREADY-undisplaced state, because that word doubles as the offset while displaced and only becomes the resolved element-type marker after the undisplace; read one binding too early it silently answers "remembers nothing". As a body statement it crashed with `ClassCastException: String cannot be cast to ArrayList`, since `%array-undisplace` runs on EVERY argument including a literal immutable string — `_arrayUndisplace` and `compileArrayUndisplace` now open with the same string check `_arrayDispTarget` had.

Wiring for `%array-undisplace`: `LispNames.ARRAY_UNDISPLACE`, the `CL_INTERNALS` entry in `PackageRegistry`, `usesGeneralArrayOp`, and a case in `Jvm`/`WasmExprCompiler.compileCons`. No `Environment` registration — `adjust-array` is not expanded through `LispMacroExpander` on the interpreter, so the primitive is compile-path-only.

## Displacement (`:displaced-to`)
Lite semantics everywhere: no `:initial-element` / `:initial-contents` beside `:displaced-to` (compile-time `UnsupportedOperationException` on JVM/WASM since make-array keywords are literal; runtime error on the interpreter) — the one combination CLHS forbids. `:displaced-index-offset` requires `:displaced-to`; the view is bounds-checked at creation (`total + offset <= target total`); rank may differ from the target's; chains resolve transitively following the CURRENT storage of each hop, so a view keeps aliasing an adjustable target grown in place.

`array-displacement` returns target + offset as TWO values via the syntactic multiple-value tier: `isMvProducerForm` / `lowerMvProducer` read `%array-disp-target` / `%array-disp-offset` over one temp, and in an ordinary context `expandArrayDisplacement` yields the primary. No `%mv-spill` involvement.

### Displacing a STRING
Over a STRING the view is a **string view**: `stringp`, `length` n, the target's characters from k on, `array-displacement` reporting target and k — and NO copy. Views chain, each hop resolved at access time.

**The TARGET decides the shape, not `:element-type`.** The portable substring idiom (`cl-ppcre/util.lisp`'s `nsubseq`, hence every `regex-replace` with a FUNCTION replacement and every `:sharedp t` entry point) passes the target's own `(array-element-type sequence)`, a RUNTIME value, so a rule keyed on the element type would not fire for the one caller that matters: both compilers keep the `:displaced-to` branch AHEAD of the runtime-element-type lowering, and `eval/ClPpcreSharedSubseq`'s copying rewrite is retired (`ClPpcreE2eTest`).

**Writing through a view reaches the target's storage where the backend has one**: the mutable CHARACTER VECTOR is that storage and a `copy-seq`/`subseq` result IS one (`.kb/string-write-runtime.md`). A LITERAL (and `concatenate` / `string-upcase` / `format nil` results until their own flip) stays immutable: such a view READS through, and the first write PROMOTES the target slot to a character vector, leaving the original string value untouched.

Representations: interpreter `LispString.displacedTo` / `displacedOffset` / `viewLength`, `storage()` / `base()` walking the chain (a view has no fill pointer and is not adjustable, so `setFillPointer` / `vectorPushExtend` / `adjustCapacity` reject it); JVM header-LENGTH **7 = displaced string view** `{dims, null, null, target, offsetLong, null, null}`, accepted by `stringp`'s length-4 arm, with `header.length > 4 && header[3] != null` telling `_rmGet`/`_rmSet` they landed on a string (`_rmSet` promotes through `_strToCharVec`); WASM the TARGET STRING in the header's data slot. Offsets stay in CHARACTER units.

### A displaced view is not a BARE view
**Invariant: `make-array :displaced-to` accepts `:fill-pointer` and `:adjustable`, on all four backends, and the fill pointer is the VIEW's own.** Both header layouts already had the slots (JVM `{dims, fp, adj, target, offsetLong}`; wasm's meta chain `(fp . (adj . offset))`) with slots 1/2 simply null, so make-array only had to resolve the pair against the VIEW's own element count, never the target's. What needed work:
- **`vector-push` / `vector-pop` write and read THROUGH**, via the displacement-aware element primitives (`_rmGet`/`_rmSet`, `_arr_get`/`_arr_set`, `readFlat`/`writeFlat`) rather than the array's own storage, which a view does not have.
- **A full view UN-DISPLACES when it grows**: `vector-push-extend` past the view's span copies the contents into storage of its own and drops the displacement, `array-displacement` answering nil/0 from then on (SBCL 2.2.9's behavior). `LispArray`/`LispString.undisplace`, JVM `_arrayUndisplace`, wasm `_arr_undisplace` (`FUNC_ARR_UNDISPLACE`, appended after `FUNC_ARR_CHECK_RANK` so no index above shifts).
- **The shape and the element type survive it**: the JVM's header LENGTH is the tag, so 7 becomes 4 and 5 becomes 3, or 5 again with the resolved element type in the freed OFFSET slot; on wasm the freed OFFSET word becomes the chain end's own marker.

### The element type of a view, and of what it un-displaces into
**Invariant: a `:displaced-to` view answers the element type of the array it is a view OF, resolved through the whole chain; and un-displacing never changes that answer, on all four backends, whichever operation reaches it.** The keyword used to be parsed and dropped on the displaced arm, and an earlier wasm fix chain-resolved the target's type only at the un-displace, i.e. `adjust-array` CHANGING an element type.

The interpreter's displaced `LispArray` constructor inherits `target.elementTypeCode` at BIRTH (one hop IS the whole chain, so `undisplace()` needs no special case); JVM `_arrayElementType` HOPS (`while (header.length > 4 && header[3] != null) o = header[3]`) and `_arrayUndisplace` walks the same chain into a length-5 `{dims, fp, adj, null, et}`, no length TAG moving; wasm `emitRememberedElementType` opens with `emitResolve`'s walk, `_arr_undisplace` copying the chain end's marker VERBATIM. Slots a growth OPENS in an un-displaced view then take the RESOLVED type's zero.

**Two SBCL oracle traps**: it ENFORCES the element-type compatibility rontolisp does not check, so state a repro in the form SBCL accepts (the view spelling the SAME `:element-type` as its target); and a mismatched view asked only for its `array-element-type` is CONSTANT-FOLDED with the `make-array` deleted, so force the array to exist by reading an element.

### A PACKED vector is a displacement target
**Invariant: `make-array :displaced-to` accepts a PACKED integer vector or packed float array as the target, on all four backends, the view reading and writing that unboxed storage with the target representation's own element semantics.** It is an ordinary general-array view whose data slot holds the packed value — no new representation, no header-length or marker change. Interpreter: `LispArray.displacedTo` widened to `LispVal`, `readFlat`/`writeFlat` ending on a packed target. JVM: the same length-5 header with a `long[]` / `double[]` / `float[]` in slot 3, `_rmGet`/`_rmSet` dispatching `long[]` at `[1 + flat]` and `double[]`/`float[]` at `[1 + rank + flat]` before the String arm. wasm: `emitResolve`'s offset-fold test and `emitDataSlotIsTarget` became "the data slot is not the buckets array", `--simd` travelling through `buildArrGetBody` / `buildArrSetBody` / `buildArrUndisplaceBody`. The per-program cost of those arms is deliberately NOT gated.

**Two deliberate divergences from SBCL, both pre-existing**: an out-of-range integer stored through the view MASKS to the element width where SBCL signals a type error (`.kb/packed-integer-vectors.md`), plus the unchecked element-type compatibility. **Unpinned edge**: the VALUE a store THROUGH a view answers differs (interpreter as given, JVM as stored); the element that lands is the same everywhere.

## Representation
**Interpreter (`LispArray`)**: `int fillPointer` (`-1` = none; rank-1 only), `boolean adjustable` (verbatim), `data` / `dimensions` non-final so `vector-push-extend` can reallocate; `effectiveLength()` (fp else `totalSize()`), `vectorPush` (index, or `-1` when full), `vectorPop`, `vectorPushExtend`, `setFillPointer`, `become(other)`. Displacement: `displacedTo` (a `LispVal` or null) + `displacedOffset`, both NON-final (`undisplace()` clears them in place); a displaced array's `data` is a shared empty array and element access goes through `readFlat`/`writeFlat`, which walk the chain of OBJECTS, not storage, so target growth is followed.

### JVM
An array is a `java.util.ArrayList` whose slot 0 holds a header `Object[]{dims, fillPointer, adjustable}` — `dims` the `Object[]` of Long sizes, `fillPointer` a `Long` or null, `adjustable` the RAW argument (null = nil, so `_adjustableArrayP` is a null test). Slot 4 may carry the REMEMBERED element type (`_arrayMakeTyped`, read by `_arrayElementType`), free on every non-displaced array because slot 3 says whether it holds an offset instead (`.kb/array-literals.md`). Data stays at slots `1..`; `buildToString` + `_length` clamp to the fill pointer.

**Header LENGTH is the tag**: 3 = ordinary boxed, 4 = character vector, 5 = displaced OR ordinary boxed WITH a remembered element type (told apart by slot 3), **6 = packed**, 7 = displaced STRING VIEW.

**A PLAIN general array starts PACKED.** With no fill pointer, no adjustability and an initial element that is nil or an in-range integer (decided at runtime in `_arrayMake`), the ArrayList holds ONLY a LENGTH-6 header `{dims, null, null, null, null, long[] data}`, elements unboxed, `Long.MIN_VALUE` the nil sentinel. `emitResolveDisplacement`'s loop ends on the null `header[3]` so a packed header never reads as a displacement, and `_arrayDispOffset` needed a `header[3] != null` test. The first store that cannot pack calls **`_arrayWiden`**; the ArrayList object IS the array's identity, so widening is invisible. **Two non-helper consumers must move with any change to what the tag means**: `JavaBridgeTemplate.marshal`'s packed branch and `JvmIntFusionCompiler`'s aref leaf (`.kb/jvm-int-fusion.md`).

A DISPLACED array carries a 5-element header `{dims, fp, adj, target, offsetLong}` (7 for a string target) and holds NO data slots (`_arrayMakeDisplaced`, bounds-checked against the target's dims product). Every data access funnels through `_rmGet(list, idx1based)` / `_rmSet(...)`: `while header.length > 3 && header[3] != null { idx += header[4]; list = header[3] }` then `get/set(1+flat)`; the no-fp element counts use the dims product / `dims[0]`, not `size() - 1`.

Static helpers in `JvmArrayRuntimeBuilder` (same array gate): `_fillPointer`, `_setFillPointer`, `_arrayHasFillPointer`, `_adjustableArrayP`, `_vectorPush`, `_vectorPop`, `_vectorPushExtend`, `_rmGet`, `_rmSet`, `_arrayMakeDisplaced`, `_arrayBecome`, `_arrayDispTarget`, `_arrayDispOffset`; call sites wired in `JvmArrayCompiler` + `JvmExprCompiler.compileCons`, and `--optimize` keeps used helpers via the ordinary invokestatic call graph.

### WASM
The `TYPE_CELL` box holds a header `TYPE_CONS` of `(dims . (meta . data))`: `dims`/`data` are `TYPE_HASH_BUCKETS` arrays; `meta` is `(fillPointer-i31-or-null . (adjustableRaw . offset-i31))`, offset 0 ordinary, 1 the character-vector marker. The header's CAR is still the dims buckets array, so the array-vs-hash-table discriminator used by `%arrayp` / `WasmLengthCompiler` / the printer is unchanged.

A DISPLACED array stores the TARGET CELL in the data slot and its offset in the meta chain (`compileMakeDisplaced`, bounds-checked). Every data access site (`compileAref` / `compileAset` / `compileRowMajorAref` / `compileRowMajorAset`) and `emitPrintArray` run the `emitResolve` walk: while the data slot `ref.test`s as `TYPE_CELL`, add the meta offset to the flat index and hop to the target's header — re-reading each hop's CURRENT header is what keeps a view aliasing a target grown in place. Builtins are emitted INLINE in `WasmArrayCompiler`: no new heap type, no new `FUNC_*` index.
