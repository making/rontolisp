# `java:` interop (interpreter + JVM-compiler Java reflection bridge)

A fourth built-in package `java` (`LispNames.JAVA_PKG`, registered in `PackageRegistry`; does NOT use `cl`) with five functions — `java:new`/`java:call`/`java:static`/`java:field`/`java:proxy`.

Interpreter: wrapped host objects are a `LispVal` permittee `LispJavaObject(Object ref)` (prints `#<java <class>>`); the bridge is `eval/JavaInterop.java`, wired in `LispEvaluator.registerJava()` (registered alongside eval/load because `java:proxy` applies a user callback via the evaluator's `apply`).

**JVM compiler**: supported via an embedded bridge — `codegen.jvm.JavaBridgeTemplate` is a self-contained rewrite of `JavaInterop` against the compiled value representation (a wrapped host object is the raw reference; `"t"` = true; an ArrayList whose slot 0 is the `{dims, fillPointer, adjustable}` header = vector (clamped to the fill pointer when present); identical costs — KEEP THE TWO IN SYNC), whose project-compiled bytecode is read from the classpath by `JvmJavaRuntimeBuilder`, renamed into the default package as `RontoLispJavaBridge` (constant-pool Utf8 rewrite, `renameClass`), base64-embedded, and `Lookup.defineClass`'d at first use by the emitted `_javaInit` (guard field `_javaInited`; call sites in `JvmJavaInteropCompiler`; the template must have NO nested classes/records — lambdas are fine — and NO rontolisp imports), so the output stays a single `.class` (but needs a JRE ≥ the build JRE). `usesJava` forces `usesEval` (`java:proxy`/auto-proxied callables call back through `_apply` via `bind(Class)`), and threads a `JvmRuntimeBuilder.JavaPrint` into the lisp-to-string builders so wrapped objects print `#<java <class>>` (BigInteger, and HashMap when hash tables are used, still fall through to `toString`). Template `.class` registered in `resource-config.json`, so the native binary can COMPILE `java:` programs; INTERPRETING them still fails there (no reflection metadata — even `(java:static "java.lang.Math" "max" 3 7)` → `No such class`) — verified. WASM stays a `Cannot compile: java:...` error, and there is still no `BuiltinFunctionWrappers` entry (`#'java:call` is a compile error; interpreter allows it).

**Overload resolution is deterministic**: `select()` picks the constructor/method whose args marshal at the lowest total cost (`COST_EXACT` < `COST_WIDEN` < `COST_CONVERT` < `COST_NARROW` < `COST_BOXED` < `COST_PROXY`), ties broken by a stable signature string — never by `getMethods()` order. A single `marshal()` is the source of truth for both selection and conversion. `java:proxy` adapts a Lisp callable to an interface (dispatched as `(callable "method" arg...)`); a callable passed where an interface is expected is auto-proxied.

**Sequence marshalling + varargs**: a proper list / rank-1 vector marshals to `T[]` (element-wise via `marshalSequence`, incl. primitive arrays) or, for any `List`-compatible target, to a `java.util.List` of `Object`-boxed elements; per-element costs count toward the overload total (so string elements prefer `String[]` over `Object[]`). A varargs executable is tried both as-is and with the tail packed (`tryVarargs`, flat `COST_VARARGS` penalty so a fixed-arity interpretation wins; the packed signature gets a `*` suffix to keep the tie-break total). Java **array** results unmarshal to Lisp lists (recursively); a returned `java.util.List` stays a `LispJavaObject`. A method declared in a JDK-internal class (e.g. a `List.of` result) is re-resolved to an accessible superclass/interface declaration (`accessibleMethod`). Symbols/hash-tables/dotted lists/multidimensional (rank-2+) arrays are NOT marshalled.

Tests: `JavaInteropTest` (interpreter) and `JvmJavaInteropCompilerTest` (compiled, mirrors the same cases — keep them in step; both headless JDK classes only — `Math`/`StringBuilder`/`ArrayList`/`Runnable`/`Supplier`/`Comparator`). Examples: `examples/java-interop.lisp`, `examples/swing.lisp` (reusable grid-window helper in its own `defpackage swing`; consumers splice it with `(require :swing ...)` and call `swing:grid-window`/`swing:paint`/...), `examples/life-gui.lisp`. Docs: `doc/{en,ja}/guides/java-interop.md` + five `reference/functions/java-*.md` (runnable examples use headless pure-compute calls only — never a GUI form, which would hang `DocExamplesTest`).
