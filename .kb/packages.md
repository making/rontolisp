# Packages

A small namespace system with three built-in packages — `cl` (standard symbols), `cl-user` (default, uses `cl`), and `rontolisp` (does not use `cl`; owns `version` and the `list-*` introspection functions). Implemented as a single read/compile-time pass, `PackageResolver` (root `am.ik.rontolisp`), that runs before the evaluator and both compilers and rewrites every form into a canonical shape the backends already handle (bare names for `cl`/`cl-user` symbols; `pkg:name` for external members, `pkg::name` for internal ones, so canonical forms re-resolve to themselves; `*package*` stays the bare cl variable, read at RUN time; `(in-package P)` consumed and replaced by the runtime assignment `(setq *package* :P)` -- see the "`*package*` is a dynamic variable" section). Hard errors (`LispPackageException`): an unqualified `cl` symbol in a package that does not use `cl`, and a single-colon reference to a non-external member ("The symbol X is not external in the P package (use P::X)").

**External vs internal (CL `:`/`::` semantics)**: `LispPackage` carries an `externals` set (3-arg constructor = everything exported); `PackageRegistry.QualifiedName` carries an `internal` flag parsed from the double colon. Built-ins: `cl` exports `CL_EXTERNALS` (= `CL_SYMBOLS` minus the `%`-prefixed `CL_INTERNALS`; car/cdr compositions count as external via `isCarCdrComposition`), `cl-user` exports nothing (like `COMMON-LISP-USER`), `rontolisp`/`java` export every registered symbol. `pkg::anything` still interns permissively (member need not be registered); an unregistered member (e.g. a defun made under `(in-package rontolisp)`, or the `rontolisp::%json-*` helpers) is internal, so its canonical spelling is double-colon. The JVM method-name mangler maps each `:` to `$colon`, so `::` names compile fine.

**`defpackage` (user-defined packages)**: `(defpackage NAME (:use ...) (:export ...) (:nicknames ...) (:import-from PKG ...))` is a literal, top-level, read/compile-time directive exactly like `in-package` — `PackageResolver.resolveDefpackage` parses it, registers a `LispPackage` (exports = owned + external; later-interned symbols are internal, canonical `pkg::name`), and replaces it with a quoted package symbol. It does NOT switch the current package. Name/clause arguments are keywords, bare symbols, strings, or `#:name` uninterned symbols (the `#:` prefix is stripped in `designator`). `:documentation`/`:size` are parsed and ignored. `(:shadow name...)` records the names in `LispPackage.shadows` (also owned): `resolveUnqualified` checks `current.shadows(name)` BEFORE the `isClSymbol` branch, so inside the package the name always resolves package-locally (cl-ppcre shadows `digit-char-p` and `defconstant`; evalCons dispatches on the FULL resolved name, so a shadowed `pkg::defconstant` reaches the user macro, not the special form). `(:shadowing-import-from PKG name...)` is recorded as an IMPORT (todo-245; the two clauses share `collectImportFrom`, shadowing entries merged LAST so they beat a plain `:import-from` of the same name): the imports map is the FIRST thing `resolveUnqualified` consults -- before the shadow set, the cl table and the use list -- so a recorded import already has exactly the always-wins precedence CL gives a shadowing import (dbd-postgres takes `database-error-message`/`-code` from `cl-postgres-error` over its use list's dbi.error pair; pinned by `shadowingImportFromWinsOverTheUseList`). Hard errors: redefining an existing package (nicknames count), a `:use`/`:import-from`/`:shadowing-import-from` of a nonexistent package, a `:nicknames` colliding with an existing package/nickname, any other clause, and a non-top-level `defpackage` (explicit check in `resolveCons`). No `:use` clause = empty use list (SBCL-like; `cl` must be listed explicitly). The registry is per-resolver-instance, so a `defpackage`'d package never leaks between independent compiles; the backends only ever see canonical `pkg:name`/`pkg::name` strings, so no per-backend codegen was needed. `defpackage` is in `CL_SPECIAL_FORMS`, so it appears in `list-special-forms` (pinned in ci-spec, the three backend tests, and the doc pages — update all of them together when that set changes).

**Nicknames**: `PackageRegistry` keeps an instance `nicknames` map (nickname -> canonical name), seeded from the static `BUILTIN_NICKNAMES` map: `common-lisp` -> `cl`, `common-lisp-user` -> `cl-user`, `rl` -> `rontolisp`, `la` -> `linalg` and `quicklisp` -> `ql` (the seeded names are reserved: a `defpackage` named `rl` or taking `:nicknames :la` fails the existing `contains()` collision check). **`splitQualified` normalizes a built-in nickname in the package part** (static `canonicalBuiltinName`), which is what makes the nicknames work on the compile path: the pre-resolution passes that match `qn.pkg()` against a canonical package literal (the library splice scanners `JsonLibrary`/`LinalgLibrary`/`UrlLibrary`/`VecLibrary`/`UsocketLibrary`/`WitLibrary`/`HttpLibrary`, `LoadInliner`'s `ql:quickload`, `HttpHandlerInliner`, the `wasm-import`/`wit-import`/`wit-export` directive matchers, `LispMacroExpander.isAsyncSugarHead`) all run BEFORE `PackageResolver`, so without the normalization `rl:json-parse` never triggered the json.lisp splice and died with `Cannot compile: rontolisp:json-parse` (interpreter unaffected -- it lazy-loads post-resolution; pinned by `JvmLispCompilerTest.compileAndRunBuiltinNicknamesTriggerLibrarySplice`). The five library walkers also canonicalize their top-level `in-package` tracking through `canonicalBuiltinName` so bare names after `(in-package :rl)` are detected. User `defpackage :nicknames` stay instance-only (they cannot alias a built-in package, so no pre-pass ever needs them); `get`/`contains` resolve through `canonicalName()`, and `PackageResolver` canonicalizes explicitly wherever the raw spelling matters (`resolveQualified`'s pkg part, `resolveInPackage`'s stored `currentPackage`, `:use`/`:import-from` designators) so the `cl`-vs-other-package comparisons and the canonical output spelling always use the real name (`common-lisp:car` -> bare `car`).

**The prelude splice selects by SYMBOL, not by member name (2026-07-27)**: `LispPreludeLibrary.process` — the compile-path pass that prepends the prelude `defun`s a program references and skips the ones the program defines itself — runs its selection on a `new PackageResolver().resolveProgram(program)` copy, so a reference and a definition are matched as the symbols they resolve to. Member-name matching (what it did before) was a live correctness bug: alexandria — spliced by half of quicklisp, e.g. every `(ql:quickload "cl-postgres")` — defines its own `alist-hash-table` / `plist-hash-table` / `hash-table-alist` / `hash-table-plist`, and `ALEXANDRIA:ALIST-HASH-TABLE` counted as "the program already defines this", so the splice was skipped and the program's own `(rl:alist-hash-table ...)` compiled to a call-time `undefined function` error (`warning: the function RONTOLISP:ALIST-HASH-TABLE is undefined`). The bare-`cl` entries had the same hole against a `(:shadow #:equalp)`-style library defun. The interpreter never had it — it resolves a prelude name lazily, at call time, off the already-resolved symbol. Two deliberate asymmetries: the entry-to-entry edges of the fixpoint (`string<` -> `%string-compare`) stay member-matched, since the prelude sources are resolver fixed points that spell each other exactly as they define themselves; and a program that throws `LispPackageException` falls back to member matching, because a package error is not this pass's to report (the backends re-derive it one step later). Same shape, same reason as `LibraryDefunPruner`'s resolved copy (`.kb/library-defun-pruning.md`). The other splice pre-passes (`JsonLibrary`/`LinalgLibrary`/`UrlLibrary`/`VecLibrary`/`UsocketLibrary`/`GrayStreamsLibrary`/`HttpLibrary`) are unaffected: they trigger on a package-qualified name plus their own `in-package` tracking, never on a bare member. Pinned by `LispPreludeLibraryTest`.

**`define-package` (the uiop/mgl-pax defpackage variant, todo-241/245)**: a literal top-level `(uiop:define-package ...)` / `(mgl-pax:define-package ...)` -- the qualifier is required and must canonicalize to `UIOP` or `MGL-PAX` (`isDefinePackageOperator`); a bare `define-package` stays a user symbol -- is consumed by `PackageResolver.resolve` exactly like `defpackage` (dbi's package headers, trivial-utf-8's opener). One variant-only clause is supported, for dbi: `(:use-reexport PKG...)` uses the packages AND re-exports all their externals, riding the same import-redirect machinery the export-of-an-inherited-name pass records (`resolveDefpackage(cons, true)`); in a plain `defpackage` the clause stays a hard error, as do the variant's other extras (`:mix`, `:recycle`, redefinition tolerance) until a consumer needs them. Pinned by `definePackageIsConsumedLikeDefpackage` / `definePackageUseReexportUsesAndReexports` / `aBareDefinePackageIsNotTheVariant`. `mgl-pax:defsection` is consumed in the same place but ADDITIVELY (the form still resolves and expands through the shim macro): its `(SYMBOL LOCATIVE)` entries are exported from the current package (`consumeDefsectionExports`) -- mgl-pax's documented autoexport, and trivial-utf-8's ONLY export mechanism (pinned by `paxDefsectionExportsItsEntries`).

**`:import-from` (textual import)**: `LispPackage` gained an `imports` map (name -> source package; 4-/3-arg convenience constructors default it empty). `resolveUnqualified` consults `current.imports()` FIRST — before the `isClSymbol` branch, so `(:import-from #:common-lisp #:car)` works in a use-nothing package — and returns the source package's canonical spelling (bare for `cl`/`cl-user`). `resolveQualified` redirects the same way after the externality check, so exporting an imported name makes `mypkg:name` resolve to the original definition. Uninterned `#:g1`-style symbols pass through `resolveSymbol` unresolved (like keywords and `&`-markers).

**Use-list visibility**: `resolveUnqualified` checks `exports` (not `owns`) of used packages — CL semantics: `use` makes only external symbols accessible; symbol conflicts between used packages resolve first-wins in `:use` order (documented; real CL signals a conflict).

**Quoted data resolves against the current package (todo-202)**: `resolveCons` sends every `(quote DATUM)` datum through `resolveQuotedData`, which resolves each symbol inside it recursively — exactly what Common Lisp's reader does when it interns a quoted datum's symbols in `*package*`. That covers three shapes that used to be handled separately or not at all: (1) a `defmacro`/`macrolet` backquote template (the reader expands every backquote level into `list`/`cons`/`quote` calls before this pass runs), where a bare template symbol like cl-utilities' `(zero-length-p ,seq)` must resolve to the same canonical spelling (`cl-utilities::zero-length-p`) as the defun it names, and an exported local-function name (`collecting`'s `collect` labels binding) to the same single-colon spelling as its qualified call sites; (2) a lone quoted symbol in ordinary code — ironclad's `defdigest` writes plist entries under template-resolved indicators that `digestp` reads back via a body quote; (3) a quoted DATA TABLE whose symbols name functions or macros, which is what made postmodern load: `*result-styles*` is a `defparameter` of `(:rows list-row-reader all-rows)` triples in `config.lisp` that the `query` macro splices into its expansion, so `ALL-ROWS` has to be the same `POSTMODERN::ALL-ROWS` the `defmacro` registers (before this it stayed bare and every `pomo:query` died with "The function ALL-ROWS is undefined"). **Data position is more permissive than code position** (`inQuotedData`): the reader only INTERNS, so a `cl` symbol quoted in a package that does not use `cl` is that package's own symbol (`'(car x)` under `(in-package :rontolisp)` = `(RONTOLISP::CAR RONTOLISP::X)`) rather than the hard error the same names are in operator position, and a quoted `*package*` is the SYMBOL, not the current package's name. The ONE exemption is host-facing data (`inHostFacingData`): the options of a `rontolisp:wasm-import`/`wasm-export` directive are an export field name or a WIT type, never a Lisp symbol — but the directive's quoted NAME argument does name a function (the synthetic / wrapped defun), so `resolveWasmDirective` resolves it like a defun name (see `.kb/wasm-import.md`).

**An `:export` of an INHERITED name re-exports the used package's symbol (todo-202)**: `resolveDefpackage` records every exported name that the package does not shadow, does not `:import-from`, is not a `cl` symbol, and that some used package exports, as an entry in `LispPackage.imports` pointing at that used package. In Common Lisp `(:use :s-sql)` + `(:export #:sql)` exports the very same `S-SQL:SQL` symbol; resolution here is textual, and `resolveUnqualified` checks `current.owns()` (= the export list) BEFORE the use list, so without this postmodern minted a distinct `POSTMODERN:SQL` and every `pomo:sql` / `pomo:sql-compile` call — including the one `real-query` splices into each `query` expansion — died as an undefined function. Both `resolveUnqualified` and `resolveQualified` already redirect through the `imports` map, so nothing else changed. A re-exported `cl` symbol needs no entry: the `isClSymbol` branch runs before the `owns()` check and yields the bare name. **The recorded entry must point at the TRUE home, not the used package** (`trueHome`, 2026-08-01): a used package may itself hold the name only as a redirect (a re-export chain, or the closer-common-lisp overlay), and recording the intermediate package spells the exporter's own references under a package that names no definition — postmodern's MOP `defpackage` `(:use :closer-common-lisp)` + `(:export #:class-finalized-p)` resolved every internal `class-finalized-p` call to the undefined `CLOSER-COMMON-LISP:CLASS-FINALIZED-P` instead of the `closer-mop:` shim defun. `trueHome` follows the source package's own import entry (one hop suffices by induction: every recorded import already points at a true home), and the same guard applies to `:import-from` recordings. Pinned by `PackageResolverTest#{reExportOfARedirectedMemberRecordsItsTrueHome,importFromARedirectedMemberRecordsItsTrueHome}`. **`trueHome` also walks the source's USE list (todo-247)**: an `:import-from` may name a symbol the source package only INHERITS -- CL's import works on any ACCESSIBLE symbol (find-symbol semantics) -- so `(:import-from #:mito.class #:table-column-references-column)`, where mito.class merely uses mito.class.column and does not re-export the name, must reach the exporting package's symbol rather than mint a `mito.class::`-internal one nothing defines. When the source neither owns nor imports the member (and it is not a `cl` symbol), `trueHome` recurses into the first used package that exports it.

**UserMacroExpander resolves through its own evaluator's resolver**: on the compile path, `UserMacroExpander.expand` resolves every top-level form via `macroEval.resolvePackages` before matching/expanding, so a `defmacro` under `(in-package P)` registers its canonical qualified name and qualified call sites match; `in-package`/`defpackage` directives (in any package spelling, `cl:in-package` included) update the macro evaluator's resolver state but are kept VERBATIM in the output for the compilers' own resolution pass. A form the walk did not change keeps its ORIGINAL spelling (compared by `print()`): the resolved canonical form is not always re-resolvable — a `cl:` symbol canonicalizes to a bare name, which is an error to spell under a package that does not use `cl` (this bit the ci-spec corpus's `(cl:print ...)` under `(in-package rontolisp)`). Known residue: a macro EXPANSION spliced into a non-cl-using package region contains canonical bare cl names and would hit the same re-resolution error — macro consumers should live in cl-using packages.

**`load`/`load-system` scope `*package*` (no leak past a loaded file — todo-083)**: like CL binding `*package*` for the duration of `load`, a loaded file's internal `(in-package ...)` must not leak to the caller. `PackageResolver` has a package stack (`pushPackage`/`popPackage`). Interpreter: `LispEvaluator.loadFile` pushes before the per-file eval loop and pops in the `finally`, covering `load`/`require`/`asdf:load-system`/component files. Compile path: `LoadInliner.spliceFile` brackets a spliced file with internal `(%push-package)`/`(%pop-package)` marker forms (`LispNames.PUSH_PACKAGE`/`POP_PACKAGE`) — but ONLY when the file has a top-level `in-package` (`selectsAPackage`), so a plain-defun file is spliced byte-identically as before. `PackageResolver.resolve` consumes the markers (save/restore, then a quoted package symbol like `in-package`); `UserMacroExpander.isPackageDirective` treats them as package directives so its own resolver stack tracks the same save/restore and keeps them verbatim for the compilers' pass. Without this, a `defun` after `(asdf:load-system :cl-who)` was interned under `cl-who`, so an unqualified `'name` lookup (the `examples/net/http-handler-cl-who.lisp` shape) failed. Tests: `LispEvaluatorAsdfTest` (interpreter, `*package*` + post-load unqualified resolve), `LoadInlinerTest` (compile path + marker bracketing).

**Package-local nicknames are GLOBAL nicknames (2026-07-18)**: the `defpackage` `(:local-nicknames (nick actual)...)` clause and `uiop:add-package-local-nickname` both funnel into `PackageResolver.registerLocalNickname` — a plain nickname registration in the resolver's registry (no per-package scoping; collisions rejected like `:nicknames`, and re-registering the same nickname→same target is idempotent for the REPL). The uiop FUNCTION exists on the interpreter (`LispEvaluator`, third scope argument accepted and ignored), and a literal top-level call `(uiop:add-package-local-nickname 'nick 'pkg)` is additionally CONSUMED by `PackageResolver.resolve` like a defpackage (registered + replaced by the quoted target name), so the idiom works on every backend — the compiled runtimes never see the call. A non-literal call stays a runtime call (interpreter only). Pinned by `LispEvaluatorTest.uiopAddPackageLocalNicknameShortensAPackageName`, `JvmLispCompilerTest.compileAndRunUiopAddPackageLocalNickname`, ci-spec `uiop-add-package-local-nickname`.

**`use-package` is a read/compile-time DIRECTIVE, not a runtime mutation (2026-07-31, todo-038)**: `(use-package PACKAGES [PACKAGE])` widens a package's use list through `PackageResolver.usePackage(List<String>, String)`, which re-`define`s the target `LispPackage` record with the extended `useList` in the instance registry. It has to be a directive for the same reason `in-package` is: the use list is consulted by `resolveUnqualified` while the resolver walks the program, so an effect that only happened at runtime would be invisible to the very forms it is meant to affect — and invisible entirely on the compiled backends, which have no registry. A literal top-level call is therefore CONSUMED by `PackageResolver.resolve` (replaced by `T`, the standard function's value) exactly like `uiop:add-package-local-nickname`; `UserMacroExpander.isPackageDirective` lists it so the macro-expansion pass tracks the same state and keeps the form verbatim for the compilers' own pass. Arguments are literal designators: one, or a QUOTED list of them (an unquoted list is a call this pass cannot see through, so it falls through to a runtime call, which the interpreter's `LispNames.USE_PACKAGE` function — resolving through the SAME resolver, so it still affects the forms read after it — serves; the compiled backends report an undefined function, the documented limit). Only EXTERNAL symbols are inherited (`resolveUnqualified` checks `exports()`, the `defpackage` `:use` rule), re-using an already-used package is a no-op, and using a package in itself is an error. It is classified as a CL FUNCTION (`CL_FUNCTIONS`), which is why the `list-functions` count moved 341 -> 342 (pinned in ci-spec, `LispEvaluatorTest`, `JvmLispCompilerTest` x2, `WasmLispCompilerIntegrationTest` — change them together). Pinned by the `usePackage*` tests in `PackageResolverTest` / `LispEvaluatorTest`, `JvmLispCompilerTest.compileAndRunUsePackage`, `WasmLispCompilerIntegrationTest.usePackageInheritsTheExternalSymbols`, ci-spec `use-package`.

**`export`/`unexport` are read/compile-time DIRECTIVES too (2026-08-01, todo-225)**: `(export SYMBOLS [PACKAGE])` and its inverse funnel into `PackageResolver.exportSymbols(List<String>, String, boolean)`, which re-`define`s the target `LispPackage` with the rewritten `externals` (export also adds the name to `symbols`, and records the same re-export import redirect the `defpackage` `:export` clause does for an INHERITED name). They are consumed by `PackageResolver.resolve` exactly like `use-package` — same reason, same shape: which symbols are external is what `resolveUnqualified`/`canonical` consult while the resolver walks the program, and the compiled backends have no registry at run time. Same literal-argument rule (a designator or a QUOTED list; a computed one falls through to the interpreter-only runtime function, which resolves through the SAME resolver), same `UserMacroExpander.isPackageDirective` entry. **The one documented limit: export BEFORE you define.** A symbol is identified here by its canonical SPELLING, and exporting flips that spelling from `pkg::name` to `pkg:name` (`canonical`), so a `defun` made before the export keeps the internal spelling and a later `pkg:name` call site does not find it — the `defpackage` `:export` clause has no such problem because it precedes everything by construction. **Re-evaluation trigger**: this disappears the moment symbols stop being identified by spelling, i.e. with the intern table of `.todo/156`; a spelling-independent fix (aliasing, or a whole-program export pre-scan) would either scatter lookup fallbacks or diverge between the incrementally-resolving interpreter and the whole-program compile paths. Both are CL FUNCTIONS, so they are part of the `list-functions` count move to 362 (pinned in ci-spec, `LispEvaluatorTest`, `JvmLispCompilerTest` x2, `WasmLispCompilerIntegrationTest` — change them together). Pinned by `LispEvaluatorTest#{evalExportMakesASymbolExternal,evalUnexportMakesASymbolInternalAgain}`, `JvmLispCompilerTest#compileAndRunExportAndUnexport`, `WasmLispCompilerIntegrationTest#exportAndUnexport`, ci-spec `export-and-unexport`.

**`import` is a read/compile-time DIRECTIVE too, and the package-registry QUERIES are real (2026-08-15, todo-038 close-out)**: `(import SYMBOLS [PACKAGE])` funnels into `PackageResolver.importSymbols(List<String>, String)`, which re-`define`s the target `LispPackage` with the same `imports` redirect (member name -> `trueHome` source package) the `defpackage` `:import-from` clause records — so the two clauses and the function are ONE mechanism, and `resolveUnqualified` consults it first. Consumed by `PackageResolver.resolve` exactly like `export`/`use-package`: same literal-argument rule (a symbol or a QUOTED list of them; the argument keeps its QUALIFIER, which is the whole point — it names the source package), same `UserMacroExpander.isPackageDirective` entry, same interpreter-side runtime function for a computed call, same `expandRuntimeExport` (arguments for effect, then `t`) on the compile paths where the registry is frozen. An UNQUALIFIED argument is already a symbol of the current package and is a no-op, as in CL. **The three registry QUERIES** — `list-all-packages`, `package-use-list`, `package-used-by-list` — share one table, `PackageResolver.runtimePackageUseTable()` (every registered package's upcased canonical name -> the upcased names it uses, plus the `keyword` pseudo-package for the same reason `runtimePackageTable` carries it). The interpreter reads the LIVE registry through it; the compile paths bake it into `Ctx.packageUseTable` at the same single site `packageTable` is threaded and lower the calls in `LispMacroExpander.expandPackageQuery` — a constant for `list-all-packages` and for a LITERAL designator, otherwise an `assoc` keyed by the name of the package `find-package` answers (which is what makes a nickname, a string and a package value reach the same row), with an unknown designator signalling exactly as it does on the interpreter. A "package" is its keyword, so all three answer lists of the keywords `find-package` yields. `package-shadowing-symbols` is a `LispPreludeLibrary` defun answering nil over a `package-name` designator check: there is no symbol shadowing here (`:shadow` records names for RESOLUTION and mints no shadowing symbol; runtime `shadow`/`shadowing-import` and `unintern` are documented non-goals, `.kb/symbol-runtime-api.md`). The five names are CL FUNCTIONS, moving the `list-functions` count 394 -> 399 (pinned in ci-spec, `LispEvaluatorTest`, `JvmLispCompilerTest` x2, `WasmLispCompilerIntegrationTest` — change them together). **The divergence, and its reason**: the baked table is frozen at compile time, so a package a compiled program creates later is invisible to the queries there — the same freeze `find-package` has, for the same reason. Pinned by `PackageResolverTest#import*`, `LispEvaluatorTest#{importMakesASymbolAccessibleUnqualified,packageRegistryQueries*}`, `JvmLispCompilerTest#compileAndRunPackageRegistryQueries`, `WasmLispCompilerIntegrationTest#packageRegistryQueries`, ci-spec `package-registry-queries`.

**A COMPUTED `export` never reaches the resolver, so the single-colon spelling it would license stays an error**: `(export (intern "X" "PKG") "PKG")` after `(defun pkg::x ...)` does not make a later `pkg:x` compile — only a LITERAL export folds (`tryConsumeExport`), and resolution rejects the non-external spelling. The RUNTIME designator route already works (the `_lookup` alias rows serve `PKG:NAME` for every `PKG::NAME` defun, `.kb/symbol-runtime-api.md`), so the gap is purely the compile-time spelling. Deliberately NOT widened when the rest of the package API landed: the only shape that could license it is "a package some computed export targets exports everything", and this subset denies by default — a defun made under `(in-package p)` is not even in the registry's owned set, so the widening would have to accept ANY `pkg:x` there and would swallow typos. **Re-evaluate when** a library needs it (found while patching uiop from Lisp, which is no longer how uiop is served): `.todo/386`.

**`closer-common-lisp` (nickname `c2cl`) is a FLAT RE-EXPORT package (2026-08-01, the DAO/MOP milestone)**: seeded in `PackageRegistry` as the union of the `cl` externals overlaid with the `CLOSER_MOP_EXTERNALS` (closer-mop wins name collisions, e.g. `class-name` -> `closer-mop:class-name`, matching the upstream closer-mop library's package of the same name). Every member is recorded in `LispPackage.imports` pointing at its HOME package (`cl` or `closer-mop`), so `resolveQualified`/`memberSpelling` redirect textually — `c2cl:class-slots` IS `closer-mop:class-slots`, `c2cl:mapcar` the bare cl name; the package owns nothing of its own. Two consequences carried the design: (1) **using it implies using `cl`** — `PackageResolver.withImpliedUses` appends `cl` to the use list at `defpackage :use`/`use-package` time, because cl visibility is judged by a DIRECT use (`currentUsesCl`, `resolveQualified`'s inherited-cl branch); postmodern's DAO `defpackage` is `(:use :closer-common-lisp)` and must see `defun` unqualified. (2) **the use-list loops in `resolveUnqualified` redirect through a used package's `imports` map** (`usedExport`) — before this a re-exported member inherited through `:use` resolved under the re-exporting package's spelling (a distinct symbol), a latent bug for ANY re-export package, closer-common-lisp merely the first user whose overlay members (`class-slots`) must land on the `closer-mop:` shim defuns. The `C2CL` built-in nickname moved from `CLOSER-MOP` to this package (upstream c2cl always meant closer-common-lisp; existing `c2cl:class-slots` spellings resolve to the same place through the redirect). `C2MOP` stays on `closer-mop`. Pinned by `PackageResolverTest#{closerCommonLispQualifiedMembersResolveToTheirHomePackages,usingCloserCommonLispMakesClAndCloserMopVisible,useListReExportResolvesToTheHomePackage}` and the `closerCommonLispPackageServesTheDaoPackageShape` cases in `LispEvaluatorTest`/`JvmLispCompilerTest`/`WasmLispCompilerIntegrationTest`.

**The babel shim package records its babel-encodings members as import redirects (2026-08-04, todo-256)**: real babel `:use`s babel-encodings and re-exports `*default-character-encoding*` / `list-character-encodings`, so `babel:X` and `babel-encodings:X` are ONE symbol. The shim's two `PackageRegistry` packages used to both OWN the names, minting two distinct textual symbols: the shim's `defvar` spells `babel-encodings:`, http-body's `detect-charset` defaults from `babel:` — a loud undefined-symbol on the compile paths and a latent unbound-variable on the interpreter (the lack exercise simply never took that branch). The babel package now carries the two names in `LispPackage.imports` pointing at `babel-encodings`, the same shape as the bt2/closer-common-lisp redirects; the shim's own `(defun babel:list-character-encodings ...)` canonicalizes through the same redirect, so both spellings land on it. Pinned by `PackageResolverTest#babelSpellingsOfTheBabelEncodingsMembersResolveToTheirHome`.

**A COMPUTED `(find-package x)` is answered from a table baked at compile time (2026-07-28, todo-198)**: a literal designator still folds in `resolveCons` (the one pass with the registry); a computed one used to be an undefined-function stub on the compiled backends and is now `(cdr (assoc (string x) '(("CL" . :CL) ...) :test #'string=))` over `PackageResolver.runtimePackageTable()` — the designator table (`PackageRegistry.designatorTable()`: canonical names plus every nickname resolving to one, each also under its uppercase spelling, since `findPackageName` matches verbatim or after lowercasing) read AFTER `resolveProgram` so it covers every `defpackage` in the program, threaded into `Ctx.packageTable` at the single `new PackageResolver()` site of each compiler. Mechanics, the frozen-at-compile-time divergence and the sibling `find-symbol`/`fmakunbound` work: `.kb/symbol-runtime-api.md`.

`cl`'s symbol set is `PackageRegistry.CL_SYMBOLS` = union of `CL_SPECIAL_FORMS`/`CL_MACROS`/`CL_FUNCTIONS`/`CL_VARIABLES`/`CL_INTERNALS`/`CL_TYPES`/`CL_CONDITION_TYPES` (single source of truth). `CL_CONDITION_TYPES` is not a list of its own: it is `Set.copyOf(ClosRegistry.CONDITION_CLASS_NAMES)`, i.e. exactly what the registry SEEDS, so a condition class added to the hierarchy is a `cl` symbol by construction (2026-08-15, todo-380). It has to be: a condition name is what a `handler-case` clause, a `define-condition` parent and a RUNTIME `(typep c ty)` specifier all spell, so while `type-error` was a user symbol a `(:use #:cl)` package read it as `MY-PKG::TYPE-ERROR`, two packages naming one condition held two symbols, and the runtime type test -- which matches the registry's PLAIN class name by spelling -- answered nil (the literal specifier was fine, `findClass` strips the qualifier at compile time). The condition names join `CL_TYPES` in being external and non-callable, so the `list-functions`/`list-macros`/`list-special-forms` counts do not move. Introspection: runtime in `Environment.registerPackages`, compile-time constants in `Jvm/WasmIntrospectionCompiler` (`cl-user` = Pass-1 user defun names via `Ctx.userDefunNames`); shared logic in `PackageIntrospection`. `listNames`'s default case treats any non-built-in package as a user package: `list-functions` filters the candidates (runtime global function names / Pass-1 defun names) by the `pkg:` prefix and keeps the qualified spellings; `list-macros`/`list-special-forms` are empty. Consequence: the runtime cannot validate a designator (user packages live in the resolver registry), so a computed designator via `funcall` with an unknown package yields nil instead of an error. Adding a package is a registry change, not a resolver change. Limitations (README). Tests: `PackageResolverTest` (incl. the `::` cases, the defpackage clause/error cases and the json.lisp fixed-point pin) + package cases in the per-backend tests + the `defpackage-use-export` ci-spec case.

## `*package*` is a DYNAMIC variable (2026-08-15, todo-255) -- two faces, kept in step

Common Lisp's `*package*` is read when a form RUNS. Until 2026-08-15 the resolver
FOLDED a value-position `*package*` to `(quote CURRENT)`, where CURRENT was the
package current when the form was RESOLVED -- right at top level, wrong inside any
defun that outlives its file: alexandria's `maybe-intern` interned into ALEXANDRIA
for every caller (fast-http's multipart state constants went missing), and rove's
`set-test` -- `(pushnew name (slot-value (package-suite *package*) '%tests))`, run
at each `deftest` -- registered every test under `rove/core/suite/package`, so
`(rove:run-suite *package*)` found 0 tests; a `*package*` inside a macro
EXPANSION was never folded at all and read "unbound" on the interpreter. Two
narrow adaptations papered over the first (`eval.AlexandriaSymbols`, deleted in
the same pass; the macro-expansion package swap below, kept). The model now:

- **Value**: the package KEYWORD `find-package` answers (`:CL-USER`), so
  `(eq *package* (find-package ...))` holds, `(package-name *package*)` works, a
  hash keyed on packages (`:test 'eq`) works, and `(typep *package* 'package)` is
  true. `(print *package*)` prints `:CL-USER` (it printed `CL-USER`, a bare
  symbol not `eq` to `find-package`'s answer, before). `#.*package*` splices the
  keyword raw (self-evaluating), so sxql's `(intern name #.*package*)` still works.
- **Resolver (`PackageResolver`)**: a value-position `*package*` resolves through
  the GENERIC cl-symbol path -- bare `*PACKAGE*` when the current package uses
  `cl`, the usual undefined-symbol error otherwise; quoted it is the same symbol
  (`resolveQuotedData` no longer needs a special case). `(in-package P)` is still
  consumed (the resolution-time state is what decides which package a source
  symbol belongs to) but leaves `(setq *package* :P)` in its place
  (`packageAssignment`); the `%pop-package` restore of a spliced load leaves the
  same assignment for the SAVED package, `%push-package` leaves the old quoted
  constant (the run-time value already IS the current package). Top-level forms
  run in resolution order, so the two states agree at every top-level point.
- **Interpreter (`LispEvaluator`)**: the variable IS the resolver's current
  package -- ONE cell. `evalSymbolRef`/`symbol-value`/`boundp` read
  `currentPackageValue()` (before the dynamic store and the env), `setq` writes
  through `assignCurrentPackage` (a non-designator signals), and `evalLet`'s
  `*package*` binding is `rebindCurrentPackage` + restore in the `finally`. So
  everything that consults "the current package" -- a 1-argument `intern`,
  `read`, a lazily expanded macro -- and the value the program reads can never
  disagree. Consequences: a top-level `(setq *package* (find-package :foo))`
  makes the interpreter resolve the NEXT top-level form in FOO (CL's reader
  would too; the compile paths resolved the whole file up front, the documented
  divergence in `doc/*/reference/packages.md`); and it is the one special the
  interpreter does NOT thread-scope (`DynamicBindings` is per thread, the
  resolver is per evaluator).
- **Compile paths**: `LispMacroExpander.injectMvSpillGlobal` prepends
  `(defvar *package* :cl-user)` when the program READS the variable -- any
  mention other than the top-level `(setq *package* :P)` shape, or a
  `with-standard-io-syntax` (which expands to a `let` of it in Pass 2, after the
  scan) -- which makes it a global with a backing store and a proclaimed special,
  so a `let` of it is the ordinary shallow binding of
  `.kb/dynamic-special-variables.md` (dynamic-first reads, ThreadLocal on the
  JVM when bound). A program that only SWITCHES packages never observes the
  variable, so its assignments are DROPPED there instead (the
  `.kb/toplevel-statement-values.md` rule) and such a program stays
  byte-identical to one without `in-package` (verified: an in-package-only
  module compiled bit-for-bit equal before/after).
- **`with-standard-io-syntax`** now expands to `(let ((*package* :cl-user)) body...)`
  -- the trigger the old expander comment left ("the FIRST reader or printer
  control variable honored at run time must be bound here") fired.
  `*print-escape*`/`*print-readably*`/`*print-pretty*` are honored but still not
  rebound by it (documented deviation on the doc page).

**A user macro called from inside a FUNCTION BODY still expands with the macro's
DEFINING package current** (`LispEvaluator.UserMacro.definitionPackage`, swapped
in `expandMacroCall`, restored in the `finally`); a TOP-LEVEL macro call keeps the
current package. Re-decided in this pass and KEPT: CL expands a macro while
COMPILING the calling file, so `*package*` is that file's; the interpreter expands
LAZILY, at call time, and only a top-level call site still has its file's package
current -- so it is what a file-at-a-time compile does, and it is what
UserMacroExpander's macro-time evaluator gets for free (its resolver tracks the
calling file's directives). The `functionBodyDepth` counter (incremented around
every user-lambda body in `apply`) tells the two apart. Both halves are
load-bearing: fast-http's `callback-data` is used inside a defun of its own file
and expands `(alexandria:format-symbol t "~A-~A" :callbacks name)` into an accessor
call, while trivia's top-level `(lispn:define-namespace pattern function)` must
generate `TRIVIA.LEVEL2.IMPL::SYMBOL-PATTERN` -- the CALLING file's package. Known
approximation: a macro defined in P and called inside a function of a DIFFERENT
file Q gets P where CL would use Q. Pinned by
`LispEvaluatorTest#evalMacroBodyInAFunctionBodyRunsInItsDefiningPackage`,
`TriviaE2eTest` and `SxqlE2eTest`.
