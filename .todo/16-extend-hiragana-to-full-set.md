# Extend the hiragana demo toward the full kana set

**Status:** DONE for the "show all 46 best-effort" direction. The demo now covers
the full 46-char gojuon (あ〜ん, no dakuten/yoon), 24x24 input, MLP 576-20-46,
single-font templates (font-rendered by `glyphgen/GlyphGen.java`) + shift/noise
augmentation, weights baked into `infer.wasm`, browser canvas front-end.
Verified on all four backends (interpreter / JVM / WASM Preview1 / WASM
component) plus the browser. train-acc 1.0; clean font-rendered inputs classify
with ~0.99 confidence in the browser. The accuracy levers below remain as
future work; the items kept are the ones NOT taken.

**Key constraint discovered while doing this:** the JVM backend caps the baked
network size. A class-version-50 class with no StackMapTable verifies on JDK 25
only up to ~12.8k baked float constants (beyond that the verifier demands
stackmaps the backend does not emit; `infer.lisp` fails to load with
`VerifyError: Expecting a stackmap frame`). This is *below* the 65535
constant-pool limit and is the real ceiling. At 24x24 (576 inputs) it caps
`*hidden*` at ~20 (623*hidden + 46 weights). Higher resolution or more hidden
units run on the interpreter/WASM but break the JVM path. Documented in
`examples/hiragana/README.md`.

## What was done
- `glyphgen/GlyphGen.java` (+ `regen-glyphs.sh`): renders the 46 kana from
  "Hiragino Maru Gothic ProN", downsampled with the same crop/center/binarize the
  browser applies, and writes `prototypes.lisp`, `glyphs.js`, `samples/*.txt`
  from one run (single source -> no drift).
- `train-main.lisp`: 24x24, 576-20-46, 600 epochs. `infer-main.lisp`: 46 labels.
  Augmentation now combines several levers (each fixed a reported failure):
  - **Thicken (`dilate`)** -- hand strokes are heavier than the font; fixed ま->す.
  - **Multi-font** (`GlyphGen.FONTS`: Maru Gothic + Klee + YuGothic + Mincho) --
    different books render hane/harai differently; Klee/YuGothic give the hooked
    left radical real handwriting has. Display reference stays Maru Gothic (FONTS[0]).
  - **Affine warp (`warp-image`, rotation + shear)** -- slanted strokes; took
    に from rank-21 to recognized across all 4 fonts + bold + ±8deg rotation.
  ~2944 samples, train-acc 1.0. Glyphs are emitted as `(defun glyph-<r>-f<f> ...)`
  (not defparameter) so 184 literals don't overflow the JVM trainer's `main` method.
- `index.html`: imports `glyphs.js`, GRID=24, shows the top-8 scores; recognizes
  live as you draw (debounced).

## Remaining levers (NOT taken; would improve real-handwriting accuracy)
- Non-rigid / elastic warp (local stroke displacement). Rigid affine doesn't cover
  a glyph whose strokes slant independently or sit far apart (e.g. a very loose に
  with a hooked radical and two disconnected diagonal right strokes still misses).
- Bigger hidden layer for smoother decision boundaries -- blocked by the JVM
  constant ceiling at 24x24 (see above); today it would mean dropping the JVM
  infer path. Lifting the ceiling itself is tracked in
  `.todo/17-jvm-baked-constant-limit.md` (packed-data / quantization / stackmaps).
Original feasibility notes below, kept for whoever picks this up.

## Feasibility summary

**Mechanically easy.** The pipeline scales without new design:
- Templates are generated by a one-off font renderer (was `/tmp/Render2.java`,
  "Hiragino Maru Gothic ProN", 120px -> bbox-fit to 16x16 -> binarize at 0.35).
  Expanding the kana list from 5 to 46 auto-generates all glyphs; no hand art.
- Weights already chunked (`emit-chunk`/`emit-flat` in `train-main.lisp`), so the
  JVM 64KB per-method cap is fine at larger sizes. `infer.wasm` grows (~256KB for
  ~8k weights now -> ~1MB for ~30k weights); browser handles it.
- Files to touch: `prototypes.lisp` (kana list + glyphs), `index.html` (`GLYPHS`,
  `KANA`, `ORDER`), `infer-main.lisp` (`*labels*`), `train-main.lisp`
  (`*nclasses*`, maybe `*hidden*`). Keep `prototypes.lisp` glyphs and
  `index.html` GLYPHS identical (single source -> regenerate both from the
  renderer to avoid drift).

**Accuracy is the hard part.** Current "1 template/class + light augmentation +
16x16 binary + MLP" is essentially a template memorizer:
- At 16x16 binary, visually similar kana collapse together: は/ほ/ま, ね/れ/わ,
  る/ろ, さ/き, あ/お, etc. -> heavy confusion.
- Real handwriting won't match a single template; already at 5 classes the UX is
  "draw to match the reference". 46 classes makes mismatches far more frequent.
- `train-acc` will still read ~1.0 (it memorizes) while real-input accuracy drops.

## Levers to make 46 classes usable (cost order)

1. **Multi-font templates (biggest win).** Render each class from several
   installed JP fonts (Hiragino Sans, Maru Gothic ProN, Mincho ProN, BIZ
   UDGothic, Apple SD Gothic Neo, ...), so the net sees style variation, not one
   exemplar. ~6-8 fonts x 46 x augmentation.
2. **Stronger augmentation:** rotation, scale, stroke-width, elastic distortion
   (current is only ±1px shift + pixel-flip noise in `train-main.lisp`).
3. **Higher resolution (24-28px)** to separate similar kana -> input 576-784,
   weights balloon, training slower.
4. **Training time:** rontolisp MLP is non-vectorized; 46 classes x many samples
   x epochs on the JVM-compiled trainer goes from ~13s (5 classes/135 samples) to
   minutes+. Offline, so tolerable, but elastic aug pushes it further.
5. **Ceiling:** still synthetic-data + MLP; won't reach KMNIST/Kuzushiji-49 CNN
   accuracy. Real datasets are impractical to load in rontolisp (huge Lisp lists,
   no binary parsing) -> would need external preprocessing.

## Two directions (decide with the user)

- **"Show all 46" (best-effort):** gojūon + ん, multi-font + strong augmentation.
  Everything compiles and the full grid renders, but document honestly that
  accuracy is rough and similar kana get confused.
- **"Keep it accurate":** curate ~10-15 visually distinct kana (e.g.
  あ/き/さ/な/は/ま/や/ら/わ/ん) -> more classes while staying reliable.

## Acceptance

- Chosen class set trains offline, predictions identical across all four backends
  on the per-class samples, and the browser demo recognizes drawn input at a
