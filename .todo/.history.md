# Deleted todo items

A row is added whenever a `.todo/NNN-*.md` file is removed, recording the commit that
removed it. The commit itself is the detail; this table is the index. `Status` is
exactly `completed` or `cancelled` -- no prose. `Model` is the
model that did the WORK -- which is not always the model that removed the file (an item
can outlive the model that wrote it), and when the work was done by a subagent it is that
subagent's own model, NOT the orchestrating session's (a subagent inherits its parent's
`Co-Authored-By` trailer, so the trailer is a hint, not the answer).

## Claiming a number

Run `.todo/claim-number.sh "<why>" [count]` and use what it prints. Never pick a
number by reading `.todo/` -- a `git fetch` cannot close the window between the read
and another session's push, and two differently-named `.todo/NNN-*.md` files MERGE
cleanly, so the duplicate survives to be found days later (`.todo/633` and `.todo/634`
both happened on 2026-09-02, before this existed).

The counter is one file, `NEXT`, on the orphan branch `todo-seq`. Claiming is a push
to it, so two sessions racing for a number race for the same file and git rejects the
loser, which then re-reads and takes the next one. The script retries that itself and
uses plumbing only -- no checkout, no index, no stash, safe from any worktree with
uncommitted changes mid-task. `todo-seq` shares no history with `develop` and must
never be merged into it. Claim a block with `count` when filing several items at once.
A claimed number whose item is never filed just leaves a gap; gaps are fine, reuse is
not.

If a duplicate is found anyway (an item filed before this branch existed, or by a
session that did not use it), **the side with a LIVE file renumbers**, because a row
already written cannot: `git show <Commit>~:<File>` below is the invariant, and the
path in the recorded commit is the answer. So if one of the two is already deleted and
recorded, the still-open one moves, whichever was committed first; if both are still
open, the later commit's side moves. Renumber the file with `git mv` and re-point every
`.todo`/`.kb` reference to it. Read a row by its full file name, never by its number
alone.

To read a deleted item's content, take its row's `Commit` and `File` and run
`git show <Commit>~:<File>` -- `Commit` is the commit that removed the file, so its
parent still contains it. Every row must keep this invariant. Each `Commit` cell is
also linked as `https://github.com/making/rontolisp/blob/<commit>~/<file>` so the
deleted item can be read directly on GitHub.

Rows are split by month under `.todo/history/` to keep this index short. Append a new
row to the file for the month the deletion happens in (`.todo/history/YYYY-MM.md`),
creating that file with the same header/table shape as an existing one if the month is
new, and add a row below for it. A month file carries no entry count and the index's
`Entries` column is not maintained per deletion -- appending the row is the whole job.
