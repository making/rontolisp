# Make the large (21x21) maze-rl example fast enough to ship

**Status:** not done. Blocked on WASM hash-table performance.

`examples/maze-rl.lisp` currently ships a 15x15 maze (shortest path 42 steps),
which converges in seconds on all four backends. We briefly used a harder 21x21
*perfect* maze (single unique solution, shortest path 132 steps) but reverted it
because the **WASM backend was too slow** (~60s, vs ~1s JVM / ~12s interpreter).

## Why the big maze is slow on WASM

The hot loop is Q-table access (`q-get`/`q-set` -> `gethash`/`setf gethash`).
The WASM hash table is an **association list scanned with `_equal`**
(`WasmHashTableCompiler`), so every access is O(n). As the Q-table grows
(792 entries for the 21x21 maze) the whole training run degrades toward O(n^2).
The interpreter and JVM use a real `java.util.HashMap` (O(1)), so they stay fast.

**Primary fix: resolve [`11-wasm-hash-table-o1.md`](11-wasm-hash-table-o1.md).**
That task replaces the WASM alist with a real O(1) table and already lists
`examples/maze-rl.lisp` in its Definition of Done. Once it lands, the 21x21
maze should run on WASM in time comparable to the other backends. This is the
real lever; the options below are only fallbacks if 11 stays deferred.

## Fallback options (if TODO 11 is not done)

- Use integer state keys (e.g. `(+ (* row cols) col)` plus action) so hash keys
  are single i31 ints instead of 3-element lists -> shorter `_equal` walks and
  cheaper alist comparisons (still O(n), but a smaller constant).
- Reduce training cost (fewer episodes / lower `max-steps`); risks under-training
  on the harder maze.

## The 21x21 configuration to restore once it is fast enough

Perfect maze generated by recursive backtracking (seed 20260626), goal placed at
the farthest reachable cell from S (shortest path = 132 steps). Verified to
converge to 132 on all four backends with these hyper-parameters:

```lisp

```
