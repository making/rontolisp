# 518. A top-level form's LEXICALS are mirrored into the eval env on every assignment

Difficulty: Medium (the gate is one predicate in two sibling emitters; the work
is proving which names an `eval` can actually observe)

Child of `.todo/517`. Sibling of `.todo/519` -- both make the same measured cost
go away, from opposite ends, and either alone is worth most of it.

## The defect

`Jvm/WasmSetqCompiler.mirrorTopLevelGlobal` writes the assigned value into the
eval runtime's global environment (`_store` -> `_genv` on the JVM, `GLOBAL_ENV`
on wasm) so a later `eval` can read a global the compiled program set
(`.kb/eval-runtime.md`, `.todo/013`). The gate is `ctx.topLevel &&
evalStoreRef != null` -- **it does not ask whether the name is a global at all**.
Read the JVM emitter: the mirror call sits in BOTH arms, the global arm and the
one commented `// Plain local (not boxed)`. The wasm emitter is the same shape.

So every assignment to every lexical of a top-level form pays it, including
names no source line ever spelled. `(print (loop for i from 1 to N sum i))`
compiles to three `_store` calls per iteration -- `I`, `__loop_acc0`, and the
`while` cursor -- and `_store` is not a slot write: it is `_envLookup`, a linear
walk of an alist, followed by a `String.equals` per entry. `nreverse`'s
`__nrev_prev` / `__nrev_cur` / `__nrev_next` get the same treatment inside a
top-level `loop ... collect`.

An `eval` cannot observe any of these. `__loop_acc0` is generated by
`LispMacroExpander.LoopExpander` (`.kb/loop-iteration-heads.md`) and is not a
symbol in any package; `I` is lexical, and CL's `eval` sees only the null
lexical environment. Mirroring them is not conservative, it is wrong work.

## What it costs (2026-08-25, this machine)

`(print (loop for i from 1 to 100000000 sum i))` versus the identical loop moved
into a `(defun run () ...)`, where `ctx.topLevel` is false and the mirror is not
emitted:

| backend | top level | in `defun` | SBCL |
| --- | --- | --- | --- |
| JVM (`-o Prog.class`) | 2.798 s | **0.394 s** | 0.208 s |
| wasm-GC (`wasmtime run -W gc`) | 2.496 s | **0.833 s** | -- |

**7.1x on the JVM, 3.0x on wasm**, for bookkeeping that no program can read. The
same pair on `10^7 x (+ s (random 1000000))`: JVM 0.781 -> 0.397, wasm 1.94 ->
1.71. The measured effect scales with how many assignments the loop body makes,
which is why the pure-arithmetic loop shows it worst.

## What to build

Mirror a top-level assignment only when the name is a genuine global -- the name
is in `ctx.globalFields` / `ctx.globalIndices` (the dedicated backing store
`.todo/013` established), or is a declared special. A lexical of a top-level
`let`/`loop`/`do`/`dotimes`, and every macro-generated temporary, gets no mirror.
Both emitters move together; the interpreter is unaffected (it has one real
environment).

Watch the two shapes that make this less than a one-line change:

- A top-level `setq` of a name never declared anywhere is CL's implicit global
  and DOES need the mirror. It has a backing field today, so the
  `globalFields` test already answers it -- confirm that before relying on it.
- A special dual-bound by a special-named `let` already takes the separate
  `emitGlobalStore` / `dualWriteSpecialGlobal` path in the same method. Do not
  disturb it; the new gate sits only on the eval mirror.

## Acceptance

- `(print (loop for i from 1 to 100000000 sum i))` at top level runs within 10%
  of the same loop inside a `defun`, on the JVM and on wasm-GC.
- A program that does `(setq g 1)` at top level and then `(eval '(print g))`
  still prints `1` on all four backends -- the case the mirror exists for.
- A test pins that a top-level `(let ((x 0)) (setq x 1))` emits NO `_store` /
  `GLOBAL_ENV` write, and that a top-level `(setq g 1)` still emits one.
- `ci-spec.yaml` and `ExamplesE2eTest` byte-identical on all four backends.
